## 一、精简版

### 版本 A：偏架构与平台

**AI 原生需求交付平台 SpecHub（后端核心开发）** · Java / Spring Boot / LangChain4j / Redis / MySQL / K8s

独立设计并实现多 Agent 流式对话中枢与自动化交付流水线。采用「LLM 线程只写 Redis，Poller 线程只读推 SSE」的中转架构解耦 AI 推理与客户端连接，支撑断线续接、多端并发订阅与多实例部署；实现 flowId 级锁串行化的交付状态机，统一 QMQ / 轮询 / MCP 回调 / 人工面板四条异构事件通路，驱动 Claude Code CLI 在 K8s 沙箱内完成编码、CR、部署全链路。项目规模 928 类 / 769 模块。

### 版本 B：偏 AI 与检索

**AI 原生需求交付平台 SpecHub（后端核心开发）** · Java / LangChain4j / Elasticsearch / NebulaGraph / MCP

负责团队记忆系统（Neura）与 Agent 运行时。设计九阶段蒸馏流水线将对话文档转为结构化知识，用 Plan-first 协议约束 LLM 输出可复现性；实现十阶段检索管道，串联 BM25 + KNN 双路 RRF 融合召回、NebulaGraph 双向 BFS 图扩展、LLM 语义筛选与 Cross-Encoder 重排，每阶段配三档降级策略保障可用性。同时实现 MCP 动态挂载与 A2A 协议接入，打通外部工具生态。

## 二、标准版（STAR，主推）

### AI 原生需求交付平台 SpecHub

**技术栈**：Java 17 / Spring Boot / LangChain4j / Baiji SOA / Redis / MySQL / Elasticsearch / NebulaGraph / Kubernetes / MCP / QMQ
**角色**：后端核心开发　**规模**：928 类、769 模块

#### 背景（Situation）

需求交付链路上，澄清、架构设计、编码、CR、部署各环节割裂，人工串联成本高。目标是构建平台让 AI Agent 接管各环节，人只在关键决策点介入，实现「需求提出 → 代码上线」的端到端智能化交付。

#### 职责（Task）

负责 Agent 运行时、流式对话中枢、自动化交付流水线、团队记忆系统与多渠道接入五个方向的设计与落地。

#### 行动（Action）

**1. 流式对话中枢：Redis ZSet 中转架构**

单次 LLM 生成长达数分钟，直接把 `SseEmitter` 绑在 LLM 线程上会导致客户端断线即丢流、无法多端订阅、多实例部署时流绑死实例。设计「LLM 线程只写 Redis ZSet，Poller 线程只读 ZSet 推 SSE」的中转架构：`chunkSeq` 作 ZSet score，独立 state key 标记流状态，客户端可从任意 `fromSequence` 续接。抽象 `AbstractAgentChatStreamService`（1478 行）作为公共骨架统一收口锁管理、流初始化与双线程提交，`streamChat` 声明为 `final` 防子类破坏时序，子类只实现 7 个抽象钩子（`agentType` / `sessionKeyPrefix` / `streamModelName` / `artifactSavedChunkKey` / `artifactSaveToolNames` / `collectTools` / `buildSystemPromptForStream`），新增 Agent 自动获得全部基础能力。

配套解决三个稳定性问题：Redis `SET NX EX` + 随机 value 比对释放实现会话级非阻塞并发锁（Redis 故障时保守视为锁繁忙，不绕过互斥语义）；token 阈值触发 LLM 摘要压缩，配三级估算降级链（LangChain4j 原生 → 字符数近似 → 消息数兜底）保证压缩必定可触发；LLM 出错或 cancel 时自动为悬挂 `tool_call` 补合成 `tool_result`，避免下轮加载会话时因不成对触发 LLM API 400。

**2. 自动化交付流水线：多源事件驱动状态机**

实现 `DeliveryFlowEngine` 驱动两级节点流转：仓库级 lane `[CODING, CR, DEPLOY, API_TEST]` 各仓库独立推进，全部到达屏障后再进入 flow 级阶段 `[UI_TEST]`。难点在于四条异构事件通路（QMQ 消费 AI CR 结果、Captain 轮询构建发布状态、沙箱内 Claude 经 MCP 回调、人工面板操作）要驱动同一状态机：统一归一化为 `DeliveryEventPayloadKeys`，经 Correlator 关联到具体 flow/repoTask，收口到 Engine 单一入口；所有状态转换在 flowId 级分布式锁内串行执行，保证多实例一致性。多仓库场景用仓库级独立节点状态 + 屏障汇聚推进。提供 `resume` / `rollbackToCoding` / `reopen` 三种韧性操作，`fix_round` 触顶自动转人工介入避免无限重试。

**3. K8s 沙箱与安全边界**

封装沙箱生命周期（创建 → 轮询就绪 → 命令执行 → 销毁），支撑 Claude Code CLI 与 Skill 脚本运行。解决双层 SSE 解析问题：沙箱 execd 的 SSE 帧内层还套着 Claude CLI 的 stream-json 事件，实现 `ExecdStdoutUnwrapper` 解构外层帧后再识别内层事件。安全上把沙箱内 LLM 视为不可信主体：用不透明凭证换可信业务上下文（`DeliveryMcpSessionContextResolver`），LLM 无法伪造 requirementId / workspaceId；文件路径强制校验防遍历越权。

**4. 团队记忆系统 Neura**

*写路径*：九阶段蒸馏流水线（Evidence 准备 → 候选蒸馏 → 快照 → 残差 → 清理 → Topic 合并 → 关系生成 → 三库持久化 → Digest 生成）。核心矛盾是 LLM 输出不确定但蒸馏结果需可复现，解法是 **Plan-first 协议**：Planner 独占发现与筛选权，Generator 收敛为确定性一对一总结且无 Drop 权限（`candidate_id` / `type` / `title` / `chunkIds` 必须与 Plan 完全一致，任一不符则 Job 失败）；candidate ID 与排序由程序确定性分配而非模型生成。Topic 合并采用候选严格串行 + 全局单一工作视图即时回写，规避并发写冲突。跨 MySQL / ES / Nebula 三库写入先生成计划再依次执行，Digest 阶段 best-effort 不回滚主链路，outbox event 支持中断恢复。

*读路径*：十阶段检索管道，串联 LLM Query 改写、Evidence 与 Topic 双路召回（各自 BM25 + KNN 双查询后 Java 端 RRF 融合）、种子 Topic 合并、NebulaGraph 双向 BFS 1～2 跳图扩展、LLM 语义初筛与精筛、Cross-Encoder 重排。抽象 `SearchStage` 接口 + `PipelineDefinition` 构建器支持 Stage 动态增删替换；每个 Stage 声明 `ABORT` / `SKIP_ON_FAILURE` / `FALLBACK` 三档降级策略，Reranker 配断路器与规则评分兜底，保证任一外部依赖故障时检索链路仍可用。`EvidenceRecallSubStage` 设计为自适应 Stage，同一 Bean 在管道中出现两次，按上下文自动切换全量召回 / 带 topicIds filter 的补全召回。

**5. 多渠道与协议接入**

实现 MCP 动态挂载：`WorkspaceMcpResolver` 四步解析（绑定列表 → 工作空间凭证 → Token 三级优先级 → 额外 Header 注入），`McpClientRegistry` 按 `{mcpServiceId}:{workspaceId}:{headersFingerprint}` 复用长连接（凭证指纹入 key 使 token 轮换后自动重建），全链路软降级为空列表使 Agent 退化纯本地工具而非报错。实现 A2A 协议接入（JSON-RPC `message/send` / `tasks/get` / `tasks/cancel` + Agent Card 发现 + SSE 流式变体），使平台 Agent 可被任意第三方客户端标准化调用。飞书侧实现 TS Agent 用户级并发控制（按 `(workspaceId, userId)` 加锁使同一用户跨群聊/私聊互斥，30s TTL + 10s Watchdog 续期覆盖长任务，虚拟线程异步执行满足飞书 3s ACK 契约）与 CardKit 流式卡片更新（单卡片最多一个更新在途、chunk 折叠为全量快照、sequence 序号防旧覆新）。

#### 结果（Result）

- 打通「需求 → 澄清 → 设计 → 编码 → CR → 部署」全自动交付链路，Supervisor Agent 可无人值守驱动多仓库并行交付。
- 流式对话支持断线续接、多端并发订阅、多实例水平扩展，LLM 生成不受客户端连接状态影响。
- 团队记忆系统实现跨需求知识沉淀与检索复用，检索链路在任一外部依赖故障时保持可用。
- 平台通过标准 A2A 协议对外开放，飞书机器人等渠道零侵入接入。

## 三、详述版（面试展开）

### 3.1 项目定位

SpecHub 是 AI 原生需求交付平台，核心命题：**把交付链路上的角色（需求分析师、架构师、开发、测试）替换为专职 Agent，人只做决策与验收**。

平台三条对外通道：Baiji SOA RPC（前端 BFF）、HTTP SSE（流式对话）、A2A JSON-RPC（Agent 互操作）。内部四层：接入层 → Agent 层 → 业务服务层 → 基础设施层。

### 3.2 最能体现设计能力的三个决策

#### 决策一：为什么用 Redis ZSet 中转而不是直接推 SSE

**朴素方案**：LLM 生成一个 chunk 就往 `SseEmitter` 写一个。

**问题**：
1. 客户端断线 → emitter 失效 → LLM 线程写入抛异常 → 整轮生成白费（LLM 调用成本已产生）。
2. 用户刷新页面 → 新请求无法接上旧流，只能重新生成。
3. 多 Tab 打开同一会话 → 只有一个 Tab 能收到流。
4. 服务多实例部署 → 流绑死在处理请求的那个实例上，重连可能落到别的实例。

**中转方案**：LLM 线程只 `ZADD` 写 Redis，Poller 线程 `ZRANGEBYSCORE` 读 Redis 推 SSE。

`chunkSeq` 作 ZSet score 天然有序，客户端带 `fromSequence` 即可从任意位点续接；独立 state key 标记 `running` 供 Poller 判断终止；LLM 线程与 emitter 零耦合，客户端断开只影响 Poller，LLM 继续生成写完整份流。

**Poller 终止条件**（这里有个细节容易漏）：
- 读到含 `x_stream_final=true` 的 sentinel chunk → 立即 complete；
- state 为空且本轮 chunks 已拉完 → 补发 done chunk 后 complete（防 LLM 线程异常退出未写 sentinel 时 Poller 永久挂起）。

#### 决策二：Plan-first 协议如何解决 LLM 输出的不可复现

**问题本质**：蒸馏要求同样输入产出同样知识条目，但 LLM 是概率模型。若让单次调用同时负责「发现候选 + 生成内容」，模型可能这次发现 5 条下次 4 条，且顺序不定，无法做增量合并与幂等。

**解法**：职责切分 + 权限收缩。

| 阶段 | 权限 | 约束 |
|------|------|------|
| Planner | 独占发现、筛选、聚类、类型判定、Evidence 选择 | 输出 candidates 数组，**不生成 candidate_id** |
| 程序校验 | 确定性 | 校验字段/类型/chunk 存在性/标题唯一性，稳定排序后分配 `candidate-001` |
| Generator | 仅一对一总结 | **无发现、纠错、Drop 权限**；`candidate_id`/`type`/`title`/`chunkIds` 必须与 Plan 完全一致，任一缺项、重复、乱序即 Job 失败 |

关键在于「ID 与排序由程序而非模型决定」，以及「Generator 不能借用其他 Plan 或 Plan 外 Chunk 的内容」—— 把不确定性压缩到单一阶段，后续全部确定性。

另一个务实设计：文本字段超建议长度时**保留原文并告警，不截断不失败**（title 50 / conclusion 300 / summary 500 只是建议值），仅在超 8000 字符时按安全问题失败。避免模型轻微超长就中断整个蒸馏 Job。

#### 决策三：Stage 级降级策略如何保障检索可用性

检索链路依赖 LLM（改写/筛选）、ES（双路召回）、NebulaGraph（图扩展）、Reranker（重排）四类外部服务，任一挂掉都不该让检索完全不可用。

**解法**：`SearchStage` 接口强制每个 Stage 声明降级策略。

```java
public interface SearchStage {
    String name();
    boolean shouldSkip(SearchContext ctx);
    void execute(SearchContext ctx);
    DegradationPolicy degradationPolicy();   // ABORT / SKIP_ON_FAILURE / FALLBACK
}
```

策略分配体现了对「哪些能力是必需的」的判断：

| Stage | 策略 | 理由 |
|-------|------|------|
| QueryEmbedding | `ABORT` | 无向量则两路召回都做不了，是硬依赖 |
| 双路召回 | `ABORT` | 无候选集后续无意义 |
| 语义筛选 / 图扩展 / 精筛 | `SKIP_ON_FAILURE` | 都是**提质**手段，失败只是结果差些，不影响可用 |
| Rerank | `FALLBACK` | Cross-Encoder 挂了降级规则评分，仍有排序 |

补充细节：Query 改写虽在 ABORT 的 Stage 内，但内部自带 try-catch —— 失败则用原始 query 继续，不向外抛。这是「Stage 级策略 + Stage 内软降级」的两层保护。

### 3.3 飞书 Bot（Python，配套项目）

轻量协议适配层，把需求推进能力搬到聊天窗口。三个值得说的实现点：

**1. 双通道调用** — 查询类走 REST（cookie 鉴权 + `commonHeader` 注入 operator），推进类走 A2A JSON-RPC `/a2a/agents/{agentType}`。用标准协议而非私有接口，换渠道零成本。

**2. 状态机镜像与自动选 Agent** — Bot 侧不硬编码流程，`choose_next_agent()` 优先读服务端返回的 `nextAgentTypes`，缺失时按 `deliveryMode` 与状态兜底推断（极速模式有提案走 SUPERVISOR、无提案走 FAST_DESIGN；人工介入态走 SUPERVISOR；否则 REQUIREMENT）。服务端状态机演进不需要改 Bot。

**3. 容错设计**：
- `find_first()` 递归遍历任意嵌套 JSON 按 key 名取值，屏蔽服务端响应包装层级变化。
- SQLite 唯一键 + `IntegrityError` 捕获实现消息幂等（飞书 at-least-once 投递会重发），配 24h TTL 清理。
- 双回调入口：WebSocket 长连接（自动重连 + 状态埋点）与 HTTP webhook（含 `url_verification` 挑战响应），适配不同网络环境。
- 错误语义化：401/403 → 「登录态失效需重新 SSO」；`in-flight` → 「已有 Agent 在执行，请勿重复推进」，而非抛裸状态码。

## 四、技术点速查

按面试可能切入的方向归类。

### 4.1 高并发与分布式

| 技术点 | 实现 |
|--------|------|
| 分布式锁 | Redis `SET NX EX` + 随机 value，释放前比对防误删；Redis 故障保守视为锁繁忙 |
| 锁续期 | Watchdog `scheduleWithFixedDelay` 定期续期，防处理超时锁自然过期 |
| 状态机串行化 | flowId 级锁包裹全部状态转换，保证多实例一致 |
| 流中转 | Redis ZSet，`chunkSeq` 作 score，`ZADD` / `ZRANGEBYSCORE` |
| 并行编排 | `CompositeStage` 用 `CompletableFuture.allOf` + 超时控制并行执行子 Stage |
| 线程池隔离 | LLM 线程池与 Poller 线程池分离（`ChatStreamExecutors`） |
| 队列容量控制 | 自主答疑独立队列命名空间，per workspace/chat 容量上限，占满静默丢弃 |

### 4.2 AI 工程

### 4.3 检索与知识工程（RAG）

| 技术点 | 实现 |
|--------|------|
| 混合召回 | BM25 + KNN 双查询，Java 端 RRF 融合（`rank_constant` 默认 60，QConfig 可调） |

| 三库一致性 | 先生成写入计划再依次执行 MySQL / ES / Nebula；outbox event 支持恢复 |

### 4.5 稳定性与安全

| 技术点 | 实现 |
|--------|------|
| 三档降级策略 | `ABORT` / `SKIP_ON_FAILURE` / `FALLBACK`，Stage 声明式 |
| 断路器 | Reranker 不可用时快速失败转规则评分 |
| 软降级 | MCP 解析异常返回空列表，Agent 退化纯本地工具 |
| 中断恢复 | outbox event `startOrResume` 支持蒸馏从中断处恢复 |
| best-effort 阶段 | Digest 生成失败记录但不回滚主链路 |
| 不可信 LLM 边界 | 不透明凭证换可信上下文，LLM 无法伪造业务坐标 |
| 路径遍历防护 | Skill 文件路径强制校验限制在沙箱工作目录内 |
| 图注入防护 | Nebula VID 转义 |
| 凭证安全 | value 绝不入日志（任何级别），只记 count 与 keyName |
| 幂等 | 产物/提案按唯一键 upsert；Bot 侧消息 ID 唯一键去重 |
| 可观测性 | MDC 跨线程手动搬运；分阶段 Token/耗时结构化埋点 + ClickHouse |

### 4.6 工程质量

| 技术点 | 实现 |
|--------|------|
| 模板方法 | `AbstractAgentChatStreamService`（对话骨架）、`AbstractAsyncNodeHandler`（异步节点） |
| 策略模式 | `ScoringStrategy`（Rerank / 规则）、`DegradationPolicy` |
| 管道模式 | `SearchStage` + `PipelineDefinition` builder（支持 addBefore/addAfter/replace/remove） |
| 泛型 DAO 基类 | `AbstractBaseDao<T>` 封装 Trip DAL 通用操作，零 SQL 字符串 |
| 纯静态 Mapper | `*SoaMapper` 无 Spring 依赖，易单测 |
| 分层解耦 | 业务服务层不含 HTTP/SOA 依赖 |
| 显式编排 | 蒸馏九阶段顺序硬编码在方法内，不用 `@Order` 隐式排序 |
| 统一错误处理 | SOA 层 try-catch 转 Failure 状态，不上抛 |

## 五、面试高频追问准备

| 追问 | 回答要点 |
|------|----------|
| 为什么不用 MQ 做流中转？ | 需要按 seq 随机位点读取（断线续接从任意 `fromSequence` 开始），ZSet 的 score 范围查询天然支持；MQ 是顺序消费模型，重放和多订阅者独立位点都要额外设计。且流是短生命周期数据，ZSet 直接过期清理即可。 |
| Redis 挂了怎么办？ | 分锁场景保守返回「锁繁忙」而非放行，宁可拒绝请求也不破坏互斥语义。流中转场景 Redis 是硬依赖，这是明确的可用性取舍——换来的是水平扩展与断线续接能力。 |
| ZSet 会无限膨胀吗？ | 每轮对话开始时 `clearStream` 清空上轮；流数据是短期数据，配 TTL 兜底。 |
| 为什么 RRF 融合放 Java 端而不用 ES retriever？ | 融合逻辑在应用层可控可测（`RrfFusion.fuse` 可单测），`rank_constant` 走 QConfig 热调；也不绑定特定 ES 版本的 retriever DSL 支持度。 |
| 两级 LLM 过滤不是很贵吗？ | 精筛在当前默认管道中是注释掉的（代码里 `precisionFilterStage` 未启用），保留能力按需开启——先用便宜手段（向量阈值 + 重排）够用就不上 LLM。这是成本与质量的渐进权衡。 |
| Topic 合并为什么串行不并行？ | 合并要基于「已合并结果」做后续判断（避免两个候选各自与同一历史 Topic 合并产生冲突），串行 + 全局单一工作视图即时回写是正确性优先的选择。召回阶段是并行的，串行只用在有依赖的合并环节。 |
| 三库写入不一致怎么办？ | 先生成写入计划再依次执行，配 outbox event 支持中断恢复重放；Digest 阶段明确 best-effort。这是最终一致性设计，不追求强一致——知识库场景可容忍短暂不一致。 |
| 沙箱内 Claude 可以随意读文件吗？ | 不行。路径经 `SkillFilePathValidator` 校验限制在工作目录内；业务坐标不由 LLM 提供，而是用不透明凭证经 `DeliveryMcpSessionContextResolver` 换取可信上下文。 |
| 交付状态机为什么不用现成工作流引擎？ | 需求特殊：多仓库屏障汇聚、四条异构事件源归一化、三种韧性回退操作（attempt/fix_round 语义），通用引擎适配成本高于自实现；且状态转换要与业务事务边界对齐。 |
| 新增一个 Agent 要改多少代码？ | 继承 `AbstractAgentChatStreamService` 实现 7 个抽象方法（`agentType` / `sessionKeyPrefix` / `streamModelName` / `artifactSavedChunkKey` / `artifactSaveToolNames` / `collectTools` / `buildSystemPromptForStream`），公共工具、锁、流中转、会话压缩全部由基类提供；`streamChat` 是 `final` 的，子类无法破坏「抢锁 → 清流 → 双线程提交」的时序。 |
| 检索管道要插一个新 Stage 怎么办？ | `PipelineDefinition.builder()` 支持 `addBefore` / `addAfter` / `replace` / `remove`，按 Stage name 定位，不用改已有 Stage。 |
