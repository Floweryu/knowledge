# SpecHub 项目分析：功能、技术实现与技术难点

分析对象：

| 仓库 | 定位 | 技术栈 | 规模 |
|------|------|--------|------|
| `spec-hub/spec-portal-service` | AI 原生需求交付平台后端 | Java / Spring Boot / LangChain4j | 769 模块、928 类 |

## 一、spec-portal-service

### 1.1 产品功能

携程 IBU 的 **AI 原生需求交付平台**服务端，承载「需求提出 → 澄清 → 架构设计 → 提案 → 编码 → CR → 部署」的全流程多智能体协作。核心是让 AI Agent 接管交付链路上的各个环节，人只在关键决策点介入。

功能域划分：

- **工作空间（Workspace）** — 团队协作单元，聚合 Git 仓库、知识文档、成员权限、Agent 配置、MCP 凭证、飞书机器人绑定。
- **需求（Requirement）** — 交付主线实体，带状态机；产物（PRD / 架构 / 数据库设计 / API 契约）与提案（proposal + OpenAPI）按需求维度幂等存储。
- **多 Agent 协作** — RequirementAgent（需求澄清）、ArchitectAgent（架构）、ProposalAgent（提案）、FastDesignAgent（极速设计）、SupervisorAgent（交付督导）、TsAgent（测试）等，每个 Agent 有独立 System Prompt、工具集与会话。
- **Supervisor 自动化交付** — Supervisor Agent 驱动沙箱内的 Claude Code CLI 完成编码，再串联 AI CR、镜像构建、发布、UI 测试，形成状态机化的交付流水线。
- **Neura 团队记忆** — 把对话与文档蒸馏为结构化 Topic/Evidence 知识库，支撑跨需求的知识检索与复用。
- **飞书接入** — TS Agent 群聊/私聊接入 + 公共 Advisor 机器人（含自主答疑）。

### 1.2 整体架构

分层架构，AI 编排、业务逻辑、基础设施隔离：

```
接入层     SOA SpecHubService（Baiji RPC，50+ 方法）
           ChatStreamController（SSE 流式对话）
           A2aAgentController（A2A 协议 JSON-RPC）
           LarkOAuthController（飞书 OAuth 回调）
              ↓
Agent 层   AbstractAgentChatStreamService（对话骨架）
           SupervisorRelayService（Supervisor 流式中继）
           SpecAgentFactory（Agent 装配）
              ↓
业务服务层  RequirementService / WorkspaceService
           CodingTaskService / HandoffService
              ↓
基础设施层  Redis ZSet（流中转/锁）  MySQL（Trip DAL）
           Sandbox Server（K8s）    MCP Servers
           Elasticsearch + NebulaGraph（Neura）
```

对外通道有三条：Baiji SOA RPC（前端 BFF 调用）、HTTP SSE（流式对话）、A2A JSON-RPC（Agent 间互操作，第三方客户端如飞书 Bot 走这条）。

### 1.3 核心技术实现

#### （1）流式对话：Redis ZSet 中转架构

最关键的架构决策 —— **「LLM 线程只写 Redis，Poller 线程只读 Redis 推 SSE」**。

`AbstractAgentChatStreamService.streamChat()` 作为所有 Agent 的公共骨架：

```java
public final SseEmitter streamChat(long workspaceId, String userMessage, Long requirementId,
                                   String sessionId, String operator) {
    // 1. 抢 Redis 分布式锁（防同 session 并发）
    // 2. 清空上轮 Redis 流 + markStateRunning
    streamContentCapture.clearStream(finalSessionId);
    streamContentCapture.markStateRunning(finalSessionId);
    // 3. 提交 LLM 任务（fire-and-forget，只写 Redis）
    chatStreamExecutors.executeLlm(() -> doStreamChat(...));
    // 4. 提交 Poller 任务（读 Redis → 推 SSE）
    submitPoller(finalSessionId, 0L, emitter);
    return emitter;
}
```

三层 Redis 结构由 `StreamContentCapture` 管理：

| 结构 | Key | 作用 |
|------|-----|------|
| Chunk ZSet | `spec:stream:chunks:{sessionId}` | `chunkSeq` 作 score，`ZADD` 写入 / `ZRANGEBYSCORE` 读取 |
| 流状态 Key | `spec:stream:state:{sessionId}` | 值 `running`，Poller 据此判断流是否进行中 |
| 草稿 Key | 独立 Key | 实时提取 `<spec_document>` / `<decision_journal_document>` 标签内容，供产物保存工具读取 |

这个设计换来四个能力：客户端断开不影响 LLM 继续生成；刷新页面可从任意 `fromSequence` 续接；多 Tab 并发订阅同一份流；服务多实例部署时流不绑定实例。

#### （2）Supervisor 交付流水线状态机

`DeliveryFlowEngine` 驱动两级节点流转 —— 仓库级 lane `[CODING, CR, DEPLOY, API_TEST]`（每个仓库独立推进）+ flow 级阶段 `[UI_TEST]`（全部仓库到达屏障后统一执行）。`PipelineDefinition.successors(node)` 返回节点在所属 lane 内的后继，引擎据此按序判 `appliesTo`、不适用则记 `SKIPPED` 并找下一个适用节点。事件来源有四条通路（QMQ 消费 AI CR 结果、Captain 轮询构建/发布状态、Claude 通过 Delivery MCP 回调、人工面板操作），全部先经 `DeliveryEventIngestionService` 归一化为统一 payload key，再由 `DefaultDeliveryEventCorrelator` 关联到具体 flow/repoTask。

```java
public interface DeliveryFlowEngine {
    void onCodingReported(long flowId, long repoTaskId, CodingReport report);
    void onCrApproved(long flowId, long repoTaskId);
    void onCrChangesRequested(long flowId, long repoTaskId);
    void onDeployAppsReported(long flowId, long repoTaskId, List<String> appIds);
    void onDeployReleaseResult(long flowId, long repoTaskId, String appId, boolean success, String status);
    void onHumanInterventionRequested(long flowId, Long repoTaskId, String reason, String category);
}
```

设计要点：

- **多仓库屏障（barrier）汇聚** — 每个仓库（`spec_delivery_repo_task`）独立维护节点状态，全部到达同一屏障节点后才整体推进下一阶段。
- **flowId 级分布式锁串行化** — 所有状态转换在锁内执行，保证多实例下状态机一致。
- **异步节点模板方法** — `AbstractAsyncNodeHandler` 骨架负责置 `WAITING_CALLBACK` 并等待回调，子类只实现 `doTrigger`（触发外部动作）与 `classify`（结果分流）。
- **韧性操作** — `resume`（人工介入后恢复）、`rollbackToCoding`（回退重编码，attempt++/fix_round++）、`reopen`（DONE 后重开）；`fix_round` 触顶自动转 `WAITING_HUMAN`，避免无限重试。

#### （3）K8s 沙箱与 Skill 运行器

沙箱是执行隔离任务的容器环境，跑 Claude Code CLI 和 Skill 脚本。`SandboxServerClient` 封装创建、状态轮询、命令执行（SSE）。

Skill 端到端流程：从 OSG 市场下载 ZIP → 解压 → 上传沙箱（`SkillPackageDeployer`）→ 执行入口脚本 → `SandboxSseAggregator` 把 execd SSE 事件流聚合为 `ScriptResult`。

```java
// ok=true 仅当收到 execution_complete 事件；exitCode=0
// ok=false 时 exitCode 来自 error.evalue（parseInt 失败为 -1）
public record ScriptResult(boolean ok, int exitCode, String stdout, String stderr, long latencyMs) {}
```

`ExecdStdoutUnwrapper` 解构外层 execd SSE 帧拿到内层原始行，供 `ClaudeCodeStreamAdapter` 识别 Claude CLI 的 stream-json 事件 —— 这是 SSE 套 SSE 的双层流解析。`SkillFilePathValidator` 校验路径防遍历攻击。

#### （4）MCP 动态集成

两类 MCP：Agent 运行时动态挂载的**工作空间 MCP**（Git MCP、知枢 MCP、CGR CodeWiki MCP 等），以及 Supervisor 专用的**交付 MCP Server**。

`WorkspaceMcpResolver.resolve()` 四步解析：查 `spec_agent_mcp` 绑定列表 → 拉 `spec_workspace_mcp_config` 凭证 → 解析 Token → 注入额外 Header（按 QConfig `mcp_credential_mapping.json`）。

Token 三级优先级：

| 优先级 | 来源 |
|--------|------|
| 1 | 用户级 MCP token（按工号查 ADA，取首个 `status=active`） |
| 2 | 工作空间凭证表 `mcpHeaders` 中的 token |
| 3 | 两者均缺 → 该 MCP 条目**整条跳过** |

`McpClientRegistry` 以 `{mcpServiceId}:{workspaceId}:{headersFingerprint}` 缓存 `McpClient`，同工作空间多 Agent 复用长连接；headers 指纹入 key 保证凭证变更后自动重建连接而非复用旧凭证。整条链路**软降级**：mcpList 空 / workspace 缺失 / DAO 异常都返回空列表，Agent 退化为纯本地工具模式而非报错。

交付 MCP Server 侧，Claude Code 通过 `start_delivery`、`report_code_pushed`、`create_cadet_task`、`report_deploy_apps`、`escalate` 等内置 Tool 反向驱动后端状态机；`DeliveryMcpSessionContextResolver` 把不透明的沙箱凭证解析为可信业务上下文（requirementId / workspaceId / operator），避免沙箱内的 LLM 伪造业务坐标。

#### （5）Neura 团队记忆：写路径（蒸馏）

`NeuraDistillationWorkflow` 九阶段显式编排（顺序硬编码在编排器里，不依赖 Spring `@Order` 隐式排序）：

```
1. PrepareEvidence    提取清洗切分原始内容 → payload.evidence_new
2. DistillCandidates  沙箱内 LLM 生成 Topic 候选 → candidates.distilled
3. Snapshot           对比已落库数据生成历史快照与增删改差异
4. Residual           找出受失效 Evidence 影响的历史 Topic → candidates.residual
5. DeleteOldData      按快照清理失效 Evidence 及关联数据
6. MergeTopics        新增+残差候选与历史 Topic 合并，确定最终变更
7. GenerateRelations  计算 Topic 关系及边变更计划
8. PersistChanges     依次执行 MySQL、Elasticsearch、Nebula 写入计划
9. GenerateDigests    识别需求与风险（best-effort，失败不回滚主链路）
```

蒸馏本身采用 **Plan-first 两阶段协议**，把发现与生成职责彻底分开：

- **Planner** — 唯一的发现与筛选阶段。全量扫描 Chunk 两遍（先 Memory 类信号，再 Knowledge 类信号），聚类去重后应用五类判定树，输出 `{type, title, scope, reason_to_create, chunkIds}`。模型**不生成** candidate_id，由程序校验字段/类型/Chunk 存在性/标题唯一性后稳定排序并分配 `candidate-001`。
- **Generator** — 收敛为确定性的一对一总结，**无发现、纠错、Drop 权限**。必须按 Plan 顺序返回等量 items，`candidate_id/type/title/chunkIds` 必须与 Plan 完全一致，任一缺项/重复/乱序即 Job 失败。

五类 Topic 模型：

| Type | Group | 语义 |
|------|-------|------|
| `decision` | Memory | 已形成的接受/拒绝/选择/承诺，有问题、约束、取舍支撑 |
| `insight` | Memory | 从推理、观察、失败中形成的可复用认识 |
| `agenda` | Memory | 未关闭、需推进的事项（问题、风险、分歧、workaround） |
| `fact` | Knowledge | 有直接 Evidence 支撑、带主体/范围/时效的可验证陈述 |
| `concept` | Knowledge | 团队语境中的规范名称、定义、别名、边界 |

同一语义默认只产一个 Candidate；Memory 结论只有在会被独立查询、更新、Merge、过期或判断冲突时才额外投影为 fact/concept，避免同义副本。

`TopicMergeService` 的合并同样强调确定性：先放 Residual 再放 New Candidate 形成稳定 `C_all` → 任何 LLM/检索调用前校验 stableOrder 唯一性 → 一次批内 LLM 调用得到 `C_consolidated` → 并行 knowledgeSearch 召回历史 Topic → 构造全局单一工作视图（`TopicMergeWorkingView`）→ Candidate **严格串行**处理并即时回写工作视图。串行是刻意的：并行会让「候选 A 合并进 Topic X」与「候选 B 也想合并进 Topic X」产生写冲突。

#### （6）Neura 团队记忆：读路径（知识检索）

`KnowledgeSearchService` 组装可插拔 Stage Pipeline，无状态、无副作用、不写任何存储：

```java
this.defaultPipeline = PipelineDefinition.builder()
        .addStage(queryEmbeddingStage)
        .addStage(evidenceRecallStage)     // 首次：全量混合召回
        .addStage(topicRecallStage)
        .addStage(seedTopicMergeStage)
        .addStage(topicEnrichmentStage)    // 第一次：填充 seed topics
        .addStage(semanticFilterStage)
        .addStage(graphExpansionStage)
        .addStage(topicEnrichmentStage)    // 第二次：填充图扩展新发现
        .addStage(evidenceRecallStage)     // 第二次：带 topicIds filter 补召
        .addStage(rerankStage)
        .build();
```

Stage 抽象带**降级策略**，是这套 Pipeline 的核心韧性设计：

```java
public enum DegradationPolicy {
    ABORT,            // 失败终止 Pipeline
    SKIP_ON_FAILURE,  // 失败跳过本阶段，继续后续
    FALLBACK          // 失败切换备用实现
}
```

实现细节：

- **混合召回 + RRF 融合** — Evidence 与 Topic 各做两次 ES 查询（BM25 + KNN 向量），Java 端 `RrfFusion.fuse()` 融合，`rank_constant` 从 QConfig 读（默认 60）。Topic 侧 BM25 是 `title^4 + conclusion^2 + summary` 多字段加权。
- **Embedding 一次生成两路复用** — 2560 维向量只算一次，Evidence 与 Topic 召回共用。
- **自适应 Stage 复用** — `EvidenceRecallSubStage` 同一个 Spring Bean 在 Pipeline 中出现两次，依据 `ctx.topicCandidates` 是否为空自动切换「全量召回」与「带 `topic_ids` filter 召回」两种模式；`TopicEnrichmentStage` 同样复用两次，第二次通过 `existingMap` 保留第一次结果只 enrich 新增 ID。
- **NebulaGraph 图扩展** — 种子 Topic 转 vid（`"workspaceId:topicId"`，转义防注入），沿 `neura_topic_relation` 边双向 BFS 1~2 跳发现关联 Topic。
- **两级 LLM 过滤** — SemanticFilter（初筛，批量判相关性）+ PrecisionFilter（精筛，输出 relevance_score 按阈值 0.3 过滤）。
- **Rerank 与降级** — 先按 `vectorScore` 阈值（默认 0.5）截断，再用 Cross-Encoder（`NeuraRerankClient` + 断路器）评分，失败降级为 `RuleBasedScoringStrategy` 规则评分，最后 Top-N 截断（默认 30）。
- **workspace 强隔离** — 所有 ES / Nebula 查询前置 `workspace_id` 过滤，且仅返回 `status=active`。

#### （7）会话管理

- **压缩** — `DefaultChatSessionCompactor` 按 token 阈值触发：估算全部消息 token → 超 `maxInputTokens` 则从最新往前累计 `keepTokens` 作为保留窗口 → LLM 摘要被裁剪部分，写入 SystemMessage 的「Previous Conversation Summary」段。
- **Token 估算三级降级** — `TokenEstimatorFactory`：LangChain4j 原生估算 → 字符数近似 `(charCount+2)/3` → 消息数硬编码兜底（≥30 条保留 5 条）。保证压缩触发永不因估算失败而失效。
- **并发锁** — `RedisSessionConcurrencyGuard` 用 `SET NX EX`，聊天锁 key 为 `spec:chat:lock:{sessionId}`（其他业务锁走 `spec:chat:lock:{namespace}:{resourceId}`），value 为随机 requestId（释放时比对防误删）。抢锁失败**不排队**，直接回错误 chunk。Redis 故障时保守返回 `empty()`（视为锁繁忙），宁可拒绝也不绕过互斥语义。
- **工具修复** — `repairMissingToolResultsQuietly` 在 LLM 出错或 cancel 时自动补齐悬挂的 `tool_call`（生成合成 result），防止下轮加载会话时因 tool_call/tool_result 不成对触发 LLM API 400。

#### （8）飞书接入

两套独立链路：

**TS Agent（工作空间机器人）** — WebSocket 长连接（携程代理版 `CtripProxyLarkChannelConnector`）接收消息 → `FeishuMessageHandler` → `TsUserDispatcher` 按 `(workspaceId, userId)` 统一加锁（同一用户跨群聊/私聊共享一把锁，实现跨渠道互斥；锁 TTL 30s + 10s Watchdog 续期）→ 虚拟线程异步执行 → 调本服务 `/chat/stream` SSE → 汇聚后回复。获锁失败时直接回拦截提示，不入队等待。

共享的 `TsRedisLockHelper` 实现 `SET NX EX` 抢锁、`GET+比对 DEL` 释放、`scheduleWithFixedDelay` Watchdog 续期（处理时间长于锁 TTL 时不至于锁自然过期）。

**公共 Advisor 机器人 + 自主答疑** — 显式 `@bot` 走原有路径；普通群消息则进入保守的自主参与链路：Redis 有序集合保留每群最近 50 条上下文（7 天）→ 轻量 LLM 分类器判断是否该回答（只允许明确的代码问题与 Trip.com 用户研究问题；寒暄、闲聊、命令、机器人消息、未绑定群一律不触发）→ 把依赖上下文的问题改写为独立问题（引用无法解析则拒绝，而非编造上下文）→ 独立队列命名空间执行（每 workspace/chat 容量默认 3，占满静默丢弃，不影响显式流量）→ 结果聚合后按尾部元数据标记判断是否「找到有用信息」，只有有用结果才剥离元数据回复。

**CardKit 流式卡片** — `QueuedCardStreamingController` 把 Advisor 回答以流式卡片形式增量更新到飞书：

- `append()` / `setContent()` 只更新内存 buffer，共享 scheduler 合并 chunk 并在 SSE 消费线程**之外**发起阻塞的 CardKit 请求。
- 同一卡片**最多一个更新在途**，在途期间到达的 chunk 折叠进下一次全量内容快照。
- 终态更新（`finish` / `fail`）有界等待在途请求后发送，靠 CardKit **sequence 序号**保证迟到的旧内容更新无法覆盖终态卡片。
- 所有卡片更新 best-effort：失败只记 warn 并吞掉，绝不传播进消费管道。
- `runWithTraceContext` 手动搬运 MDC，保证异步线程里的日志仍带 trace 上下文。

#### （9）A2A 协议接入

`A2aAgentController` 实现 Agent2Agent 协议，让 SpecHub 的 Agent 能被外部标准化调用：

- `GET /a2a/agents/{agentType}/.well-known/agent-card.json` — Agent Card 发现
- `POST /a2a/agents/{agentType}` — JSON-RPC 2.0：`message/send`、`tasks/get`、`tasks/cancel`
- `POST /a2a/agents/{agentType}/stream` — SSE 流式变体

错误处理遵循 JSON-RPC 规范：`INVALID_PARAMS`、`METHOD_NOT_FOUND`、`TASK_NOT_FOUND`、`TASK_NOT_CANCELABLE`、`INTERNAL_ERROR`，且**始终返回 HTTP 200**，错误体现在 JSON-RPC error 对象里。

#### （10）数据模型与 DAL

主线：工作空间 → 需求 → 交付流。`AbstractBaseDao<T>` 封装 Trip DAL 通用操作（`queryBy` / `insert` / `update` / `delete` / `queryByPk` / `combinedInsert`），子类只加业务查询，**全链路零 SQL 字符串**。

几处值得注意的建模：

- `SpecChatMessage.chunkSeq` 关联消息覆盖的 Redis ZSet 区间上界，支撑断线精确续接。
- `CodingSessionPlaceholder` 枚举：三种编码来源（SUPERVISOR / CADET / CLAUDE）建骨架行时写带来源前缀的占位 `cadetSessionId`，既满足唯一索引约束，又避免 Cadet 回调误命中骨架行。
- Agent 配置两层架构：公共级（`workspace_id=0`）+ 工作空间级 Copy-on-Write；MCP 绑定与 Skill 挂载采用「**单层就近原则**」—— 工作空间级有记录就完全以它为准，没有则完全回退公共级，不做合并/去重/覆盖。
- `SpecOperationLog` 只追加写，不提供 update/delete 入口。

### 1.4 技术难点

| # | 难点 | 解法 |
|---|------|------|
| 1 | **LLM 长响应与 HTTP 连接生命周期不匹配** — 单次 LLM 生成可达数分钟，客户端断线/刷新/多 Tab 会丢流 | Redis ZSet 作中转，LLM 线程与 emitter 解耦；chunkSeq 支持任意位点续接 |
| 2 | **多实例下会话并发与状态机一致性** | Redis `SET NX EX` + 随机 value 比对释放；交付状态机全部转换在 flowId 级锁内串行 |
| 3 | **对话历史无限增长超出上下文窗口** | token 阈值触发 LLM 摘要压缩 + 三级 token 估算降级链 |
| 4 | **tool_call / tool_result 不成对导致 LLM API 400** | 出错或 cancel 时自动补齐悬挂 tool_call 的合成 result |
| 5 | **异构事件源驱动同一状态机** — QMQ、Captain 轮询、MCP 回调、人工面板四条通路 | 统一 payload key 归一化 + Correlator 关联 + 单一 Engine 入口 |
| 6 | **多仓库交付进度不齐** | 仓库级独立节点状态 + 屏障汇聚推进 |
| 7 | **沙箱内 Claude CLI 输出的双层 SSE 解析** | execd SSE 帧解构（`ExecdStdoutUnwrapper`）后再识别 stream-json |
| 8 | **沙箱内 LLM 不可信** — 可能伪造业务坐标、越权读文件 | 不透明凭证换可信上下文（`DeliveryMcpSessionContextResolver`）；路径校验防遍历 |
| 9 | **外部 MCP 服务不稳定不能拖垮 Agent** | 全链路软降级为空列表，退化纯本地工具；Client 按 workspace 复用长连接 |
| 10 | **LLM 输出不确定性 vs 蒸馏结果可复现** | Plan-first 协议：Planner 负责发现、Generator 无 Drop 权限；ID 与排序由程序确定性分配；字段超长只告警不截断不失败 |
| 11 | **Topic 合并的写冲突** | 候选严格串行处理 + 全局单一工作视图即时回写 |
| 12 | **多存储一致性** — 单轮蒸馏要同时写 MySQL、ES、Nebula | 先生成写入计划再依次执行；Digest 阶段 best-effort 不回滚主链路；outbox event 支持中断恢复 |
| 13 | **检索链路依赖多且都可能失败** — LLM 改写、ES、Nebula、Reranker | Stage 级三档降级策略（ABORT / SKIP_ON_FAILURE / FALLBACK）+ Reranker 断路器 + 规则评分兜底 |
| 14 | **飞书 CardKit 更新的乱序与限流** | 单卡片最多一个更新在途 + chunk 折叠为全量快照 + sequence 序号防旧覆新 + 终态有界等待 |
| 15 | **自主答疑的成本与噪音控制** | 轻量分类器前置 + 严格话题白名单 + 独立队列容量上限（占满静默丢弃）+ 有用性 gating |
| 16 | **跨异步线程的可观测性** | MDC 手动搬运；蒸馏各阶段 Token/耗时结构化埋点（`NeuraObservedStepRunner`）+ ClickHouse 日志 |

### 1.5 工程规范亮点

- **SOA 统一错误处理** — 所有方法 try-catch 转 `Failure` 响应状态，不上抛；`successStatus()` / `failureStatus(message)` 收口。
- **Mapper 层纯静态** — `*SoaMapper` 无 Spring 依赖，便于单测与复用。
- **业务服务层无框架依赖** — 不含 HTTP/SOA 依赖，入参契约 Request 出参 DAL 实体，可独立单测。
- **凭证安全** — value 绝不入业务日志（任何级别），只记 count 与 keyName；明文存储明确标注为 M1 限测试环境，生产需 M2 KMS。
- **编排顺序显式可见** — 蒸馏九阶段顺序硬编码在编排器方法里，注释说明「业务顺序必须一眼可见，不通过组件扫描或 Order 注解隐式决定」。

## 二、spechub-feishu-bot

### 2.1 定位与功能

Python 轻量服务，把 SpecHub 的需求推进能力搬到飞书聊天窗口 —— 让人在手机上用一句中文推进需求，不必打开 SpecHub Web。

支持四类中文指令：

| 指令 | 正则 | 行为 |
|------|------|------|
| `帮助` / `help` / `?` | — | 返回帮助文本 |
| `进度 123` / `状态 #123` / `查看 123` | `(?:进度\|状态\|查看)\s*#?(\d+)` | 聚合需求详情 + 交付状态 + 编码任务为一段可读摘要 |
| `推进 123 [workspaceId] [指令]` / `继续 123` | `(?:推进\|继续)\s*#?(\d+)(?:\s+(\d+))?(?:\s+(.+))?` | 自动选下一步 Agent 并调用 |
| `回复 123 <内容>` / `答复 123 ...` | `(?:回复\|答复)\s*#?(\d+)\s+(.+)` | 用上次会话的 sessionId/contextId 续聊 |

### 2.2 技术实现

模块职责清晰，七个文件各司其职：

```
app.py / wsgi.py          进程入口（gunicorn）
spechub_feishu_bot/
├── web.py         Flask 应用工厂、健康检查、事件回调端点、运行时启动
├── feishu.py      FeishuBot：token 管理、消息收发、WS 长连接、线程池
├── commands.py    指令解析（正则）与分发
├── spechub.py     SpecHubClient：REST + A2A JSON-RPC 调用、状态机推断
├── state.py       SQLite 会话与消息去重存储
├── config.py      环境变量配置（dataclass + from_env）
└── diagnostics.py 运行时诊断快照
```

**双通道接入**，靠 `DISABLE_FEISHU_WS` 切换：

1. **HTTP 事件回调**（默认，`disable_feishu_ws=True`）— `POST /feishu/events`，处理 `url_verification` challenge（兼容新旧两种 payload 形状）与 `im.message.receive_v1` 事件。
2. **WebSocket 长连接** — `lark.ws.Client` + `run_forever()` 无限重试（失败 sleep 10s），`start_background()` 起 daemon 线程。

**两种后端调用协议**：

- 查询类走 REST（`_api_post`），带 `spechub_token` cookie 与 `commonHeader`（operator / operatorNumber / operatorEmail）。
- 推进类走 **A2A JSON-RPC**（`send_agent`）：`POST /a2a/agents/{agentType}`，`method: "message/send"`，message 走 `parts: [{kind: "text", text: ...}]` 结构，metadata 带 workspaceId / requirementId / sessionId。

```python
payload = {
    "jsonrpc": "2.0",
    "id": f"feishu-{uuid.uuid4().hex[:16]}",
    "method": "message/send",
    "params": {"message": message, "metadata": metadata},
}
```

**客户端侧状态机推断**（`choose_next_agent`）—— Bot 不硬编码流程，而是从需求详情推断下一步：

```python
def choose_next_agent(self, detail):
    status = find_status(detail)
    if status in TERMINAL_STATUSES:      return None
    for agent in find_next_agents(detail):   # 优先服务端给的 nextAgentTypes
        if agent in AGENT_PROMPTS:       return agent
    if status in HUMAN_STATUSES:         return "SUPERVISOR_AGENT"
    if str(find_first(detail, "deliveryMode")) == "1":   # 极速模式
        return "SUPERVISOR_AGENT" if find_first(detail, "proposals", "proposalList") else "FAST_DESIGN_AGENT"
    return "REQUIREMENT_AGENT"
```

**容错的响应解析** — `find_first(value, *keys)` 递归遍历任意嵌套 JSON 找第一个匹配 key（大小写不敏感、跳过空值）。这样后端契约嵌套层级调整时 Bot 不需要跟着改，是刻意的松耦合取舍。

**SQLite 双表**：

```sql
sessions(requirement_id PK, agent_type, session_id, context_id, task_id, updated_at)
messages(message_id PK, created_at)
```

`remember_message()` 靠主键冲突做幂等去重，并顺手清理 24 小时前的旧记录：

```python
def remember_message(self, message_id: str) -> bool:
    """Return True once for a message id, False for duplicate delivery."""
    with self._lock, self._connect() as conn:
        conn.execute("DELETE FROM messages WHERE created_at < ?", (now - 86400,))
        try:
            conn.execute("INSERT INTO messages(message_id, created_at) VALUES (?, ?)", (message_id, now))
        except sqlite3.IntegrityError:
            return False
    return True
```

**Token 缓存** — `_get_tenant_access_token()` 在 `threading.Lock` 内做双重检查，提前 300 秒过期（`now + max(60, expires_in - 300)`）避免边界失效。

**安全与运维**：
- 三层准入：`FEISHU_VERIFICATION_TOKEN` 校验回调（兼容三处 token 位置）+ `ALLOWED_CHAT_IDS` 群白名单 + `ALLOWED_OPEN_IDS` 用户白名单。
- 健康检查暴露五个路径变体（适配不同网关前缀），只返回配置的**布尔存在性**（`bool(settings.spechub_token)`）而非值本身。
- `_sanitize_error()` 清洗错误信息再记录/上报。
- `SPECHUB_VERIFY_SSL` 默认值按 URL 域名智能推断（`.ctripcorp.com` 内网默认关闭校验）。

**并发模型** — 6 线程 `ThreadPoolExecutor`（`thread_name_prefix="feishu-command"`），回调线程立即 `submit` 后返回，保证飞书回调快速 ACK 不超时。

### 2.3 技术难点

| # | 难点 | 解法 |
|---|------|------|
| 1 | **飞书回调超时限制 vs Agent 调用耗时长** | 回调线程只做校验去重后 submit 线程池，立即返回 ACK |
| 2 | **飞书消息 at-least-once 重复投递** | SQLite `message_id` 主键冲突去重 + 24h 滚动清理 |
| 3 | **后端响应契约嵌套多变** | `find_first` 递归找 key，不依赖固定路径 |
| 4 | **多轮对话状态在无状态 HTTP 服务中保持** | SQLite 按 requirementId 持久化 sessionId / contextId / taskId |
| 5 | **Bot 不该重复实现服务端流程编排** | 优先信服务端 `nextAgentTypes`，仅在缺失时按 status + deliveryMode 兜底推断 |
| 6 | **并发推进同一需求** | 识别后端 in-flight 错误，转为「已有 Agent 正在执行，请稍后用『进度』查看」的友好提示 |
| 7 | **内网 SSO 登录态失效难辨识** | 401/403 与响应体 `redirectUrl` 双重判定，统一提示重新授权 |
| 8 | **WS 长连接不稳定** | `run_forever()` 无限重试 + 运行时状态记录（attempts / lastError / lastAttemptAt） |
| 9 | **多环境网关前缀不一致** | 健康检查注册五个路径变体 |
| 10 | **飞书 token 并发获取** | 锁内双重检查 + 提前 300s 过期 |

## 三、两个仓库的协作关系

```
飞书用户
   │ 中文指令（进度/推进/回复）
   ▼
spechub-feishu-bot（Python）
   │  查询：REST /api/workspace/requirement/detail 等（cookie 鉴权）
   │  推进：A2A JSON-RPC /a2a/agents/{agentType}（message/send）
   ▼
spec-portal-service（Java）
   │  A2aAgentController → A2aAgentInvocationService
   ▼
AbstractAgentChatStreamService → LLM + MCP Tools
   │
   ▼
Supervisor → K8s 沙箱 Claude Code CLI → 编码/CR/部署
```

职责边界清晰：Java 服务是重逻辑核心（Agent 编排、状态机、记忆系统），Python Bot 是轻量协议适配层（渠道接入、指令翻译、会话映射）。Bot 通过标准 A2A 协议而非私有接口接入，意味着后续换任何渠道（钉钉、Slack、CLI）都是同一套接法。
