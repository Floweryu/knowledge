## 一、流式架构

### 1.1 Redis ZSet 作为 SSE 流中转

**问题**：LLM 单次生成数分钟，直接把 `SseEmitter` 绑在 LLM 线程上产生四个缺陷 —— 断线丢流、刷新无法续接、多 Tab 只能一个收流、多实例部署时流绑死实例。

**方案**：双线程 + Redis 中转。

```
LLM 线程   ──ZADD──▶  Redis ZSet  ◀──ZRANGEBYSCORE──  Poller 线程 ──SSE──▶ 客户端
（只写）                                                （只读）
```

**三层 Redis 结构**：

| 结构 | Key | 说明 |
|------|-----|------|
| Chunk ZSet | `spec:stream:chunks:{sessionId}` | `chunkSeq` 作 score，天然有序，支持范围查询 |
| 流状态 | `spec:stream:state:{sessionId}` | 值 `running`，LLM 线程结束时 `clearState` |
| 草稿缓存 | 独立 Key | 实时提取 `<spec_document>` / `<decision_journal_document>` 标签内容 |

**骨架实现**（模板方法，`final` 防子类破坏时序）：

```java
public final SseEmitter streamChat(long workspaceId, String userMessage, Long requirementId,
                                   String sessionId, String operator) {
    Optional<LockHandle> handleOpt = sessionConcurrencyGuard.tryLock(agentType(), finalSessionId);
    if (handleOpt.isEmpty()) {
        SseWriter.sendDirectError(emitter, LOCK_BUSY_MESSAGE);
        return emitter;
    }
    streamContentCapture.clearStream(finalSessionId);      // 清上轮
    streamContentCapture.markStateRunning(finalSessionId); // 标记进行中
    chatStreamExecutors.executeLlm(() -> doStreamChat(...)); // 只写 Redis
    submitPoller(finalSessionId, 0L, emitter);              // 只读 Redis 推 SSE
    return emitter;
}
```

**Poller 终止条件**（防永久挂起）：
1. 读到含 `x_stream_final=true` 的 sentinel chunk → 立即 complete；
2. state 为空且本轮 chunks 已拉完 → 补发 done chunk 后 complete（兜底 LLM 线程异常退出未写 sentinel 的情况）。

**续接实现**：`POST /restful/chat/stream/resume` 带 `fromSequence`，Poller 从该 score 开始拉取。`SpecChatMessage.chunkSeq` 记录消息覆盖的 ZSet 区间上界，前端据此精确定位。

**可迁移经验**：任何「长耗时生成 + 客户端连接不可靠」的场景（AI 对话、大报表导出、批量任务日志）都适用。核心是**把流数据的生命周期从连接的生命周期中剥离**。选 ZSet 而非 List/Stream/MQ 的理由是需要按序号随机位点读取。

### 1.2 双层 SSE 解析

**问题**：Sandbox Server 的 execd 接口用 SSE 返回命令输出，而沙箱内运行的 Claude Code CLI 本身又以 stream-json 格式逐行输出事件 —— 外层 SSE 帧的 `text` 字段里装着内层的 JSON 事件行，且一个外层帧可能含多行或半行。

**方案**：两级解构。
- `ExecdStdoutUnwrapper` 把外层 execd SSE 帧解构为内层原始行内容（处理跨帧断行拼接）；
- `ClaudeCodeStreamAdapter` 在还原后的行流上识别 Claude CLI 的 stream-json 事件。

**事件聚合**（`SandboxSseAggregator` → `ScriptResult`）：

| 事件类型 | 处理 |
|----------|------|
| `stdout` / `stderr` | 顺序追加字符串 |
| `execution_complete` | `ok=true`，`exitCode=0` |
| `error` | 解析 `evalue` 为 exitCode，`ok=false`（parseInt 失败为 -1） |
| `init` / `ping` | 忽略 |

```java
public record ScriptResult(boolean ok, int exitCode, String stdout, String stderr, long latencyMs) {}
```

注意语义严谨性：`ok=true` **仅当**收到 `execution_complete` 事件 —— 流正常结束但没收到完成事件也判失败，避免把「连接中断」误判为「执行成功」。

### 1.3 飞书 CardKit 流式卡片更新

**问题**：飞书卡片更新是同步阻塞 HTTP 请求且有频率限制，而 SSE chunk 到达频率远高于允许的更新频率；并发更新还会乱序（旧内容覆盖新内容）。

**方案**（`QueuedCardStreamingController`）：

| 机制 | 实现 |
|------|------|
| 请求合并 | `append` / `setContent` 只更新内存 buffer，共享 scheduler 定期 flush |
| 单飞控制 | 单卡片最多一个更新在途，在途期间到达的 chunk 折叠进下次全量快照 |
| 防旧覆新 | CardKit sequence 序号递增，服务端丢弃低序号更新 |
| 终态保障 | `finish` / `fail` 有界等待在途请求后强制 flush |
| 故障隔离 | 所有卡片更新 best-effort，失败只 warn 不传播到消费管道 |
| 线程解耦 | 阻塞 HTTP 调用移出 SSE 消费线程，避免拖慢流消费 |

**跨线程可观测性**：更新在独立线程池执行，MDC trace context 手动搬运并在 finally 恢复：

```java
private void runWithTraceContext(Runnable task) {
    Map<String, String> previous = MDC.getCopyOfContextMap();
    try {
        if (traceContext == null || traceContext.isEmpty()) MDC.clear();
        else MDC.setContextMap(traceContext);
        task.run();
    } finally {
        if (previous == null || previous.isEmpty()) MDC.clear();
        else MDC.setContextMap(previous);
    }
}
```

**可迁移经验**：「高频事件驱动低频外部写入」的通用解法 —— buffer + 单飞 + 全量快照折叠 + 版本号防乱序。比简单限流好在不丢内容（折叠而非丢弃），比队列好在不积压（后来的快照包含先前所有内容）。

## 二、分布式与并发

### 2.1 会话级非阻塞分布式锁

**实现**（`RedisSessionConcurrencyGuard`）：

- 锁 key：聊天锁为 `spec:chat:lock:{sessionId}`；其他业务锁复用同前缀加命名空间 `spec:chat:lock:{namespace}:{resourceId}`
- 加锁：`SET NX EX`，value 为本次请求随机 requestId
- 释放：GET 比对 value 相同才 DEL，防误删他人锁
- 抢锁失败：**直接返回错误 chunk，不排队等待**（对话场景排队无意义，用户宁可立即知道「已有请求进行中」）
- **Redis 故障时保守返回 `empty()`**（视为锁繁忙）—— 宁可拒绝请求也不绕过互斥语义

**TS 消息统一用户级锁**（`TsUserDispatcher` + `TsRedisLockHelper`）：

早期设计是群聊 / 私聊两条独立路径（各自 workspace 级 / user 级锁），现已重构为**统一用户级分发器**：

| 项 | 值 |
|------|-----|
| 锁粒度 | `(workspaceId, userId)` —— 同一用户跨群聊和私聊**共享一把锁**实现跨渠道互斥，不同用户完全并行 |
| 锁 key | `spec:ts:user:lock:{workspaceId}:{userId}` |
| 去重 key | `spec:ts:msg:seen:{messageId}`，TTL 86400s（覆盖飞书 SDK 最长重试窗口） |
| 锁 TTL / 续期 | 30s TTL + 10s Watchdog 续期，覆盖 15 分钟长任务；进程崩溃后最迟 30s 自动释放 |
| 获锁成功 | 提交**虚拟线程**异步执行流式对话，立即返回（满足飞书 3s ACK 契约） |
| 获锁失败 | 回复固定拦截提示，**不入队等待** |

锁 value 为 `{requestId}:{acquireEpochMillis}` 复合 token，释放与续期时整体比对；Watchdog 续期走 `expire` 不覆写 value，故 acquire 时刻在续期中保持不变。释放走 GET + 比对 + DEL 三步，有极小 TOCTOU 窗口，不匹配时仅 warn（已明确记录为已知取舍，非疏漏）。

**设计演进值得注意**：从「按渠道分路径」改为「按用户统一」，是因为真正需要互斥的是**同一个人的连续提问**（上一问没答完就发下一问会导致会话错乱），而非渠道本身。同一用户在群里问完又私聊问，语义上仍是一个会话流。这是把并发控制的粒度对齐到业务语义而非技术分类。

**可迁移经验**：分布式锁的**失败方向选择**比实现更重要。锁服务不可用时，「保守拒绝」还是「乐观放行」取决于并发冲突的代价 —— 这里 LLM 重复调用有真实成本且会污染会话历史，故选保守。

### 2.2 状态机的多实例一致性

交付状态机所有转换在 **flowId 级分布式锁**内串行执行。事件来自四条通路：

```
QMQ（AI CR 结果）─┐
Captain 轮询 ────┤
MCP 回调 ────────┼─▶ DeliveryEventIngestionService（归一化 payload key）
人工面板 ────────┘        ↓
                    DefaultDeliveryEventCorrelator（关联 flow/repoTask）
                          ↓
                    DeliveryFlowEngine（单一入口，锁内串行）
```

**关键设计**：无论多少事件源，**归一化 + 单一入口 + 锁内串行**三件套保证状态机不会因并发事件产生非法转换。新增事件源只需接入归一化层，不动 Engine。

### 2.3 Topic 合并的写冲突规避

**问题**：一轮蒸馏有 N 个候选 Topic 要与历史 Topic 合并，若并行处理，两个候选可能各自决定与同一历史 Topic 合并，产生冲突。

**方案**：召回并行，合并串行。

```java
// 对全部 Consolidated Candidate 并行完成 knowledgeSearch
Map<String, TopicRecallResult> recalls = recallService.recallAll(workspaceId, consolidated);
// 用召回的初始快照构造全局单一 Topic 工作视图
TopicMergeWorkingView workingView = new TopicMergeWorkingView();
workingView.initialize(recalls);
// Candidate 严格串行处理，并即时把合法更新写回 workingView
```

后处理的候选能看到前面候选造成的变更（工作视图即时回写），因此判断基于最新状态。**把并行用在无依赖的 IO 阶段（召回），串行用在有依赖的决策阶段（合并）**。

## 三、AI 工程

### 3.1 会话压缩与三级 token 估算降级

**压缩流程**（`DefaultChatSessionCompactor`）：
1. `TokenEstimator` 估算全部消息 token 数
2. 超过 `CompactionPolicy.maxInputTokens` 阈值时，从最新消息往前累计 `keepTokens` 作为保留窗口
3. 调 LLM 对被裁剪部分生成摘要，写入 SystemMessage 的「Previous Conversation Summary」段

**三级降级链**（`TokenEstimatorFactory`）：

| 级别 | 方式 | 触发条件 |
|------|------|----------|
| 1 | LangChain4j 原生估算 | 正常 |
| 2 | 字符数近似 `(charCount+2)/3` | 原生估算不可用 |
| 3 | 消息数硬编码兜底（≥30 条保留 5 条） | 前两级都失败 |

**要点**：压缩是**必须成功**的操作（不压缩就会超上下文窗口直接失败），所以估算环节不允许「失败即放弃」。三级降级保证任何情况下都能得出一个可用的触发判断。

### 3.2 tool_call / tool_result 配对修复

**问题**：LLM 生成 `tool_call` 后若出错或被 cancel，会话历史里留下悬挂的 `tool_call` 没有对应 `tool_result`。下一轮加载会话时，LLM API 会因不成对直接返回 400。

**方案**：`repairMissingToolResultsQuietly` —— 出错或 cancel 时扫描历史，为悬挂 `tool_call` 生成合成 `result`。

**可迁移经验**：与有严格协议约束的外部 API 交互时，**中断路径要和正常路径一样保证协议完整性**。异常处理不只是记日志，还要修复状态使下次调用可用。

### 3.3 Plan-first 协议：约束 LLM 输出的可复现性

**核心矛盾**：蒸馏要求同输入产同输出（支持增量合并与幂等），但 LLM 是概率模型。

**解法**：职责切分 + 权限收缩 + 确定性环节程序化。

| 阶段 | 权限 | 关键约束 |
|------|------|----------|
| Planner | 独占发现、筛选、聚类、类型判定、Evidence 选择 | 输出 candidates，**不生成 candidate_id** |
| 程序校验 | 完全确定性 | 校验非空字段/类型枚举/chunk 存在性/标题规范化唯一性 → 稳定排序 → 分配 `candidate-001` |
| Generator | 仅一对一总结 | **无发现、纠错、Drop 权限** |

**Generator 的硬约束**：
- `candidate_id` / `type` / `title` / `chunkIds` 必须与 Plan 完全一致
- 不得包含 `decision`、`plan_changes`、`drop_reason` 字段
- 不得借用其他 Plan 或 Plan 外 Chunk 的独立内容（完整 Source 只用于理解指代）
- 任一缺项、重复、乱序或固定字段差异 → **Job 失败**（不静默修复，不推测语义）

**Planner 内部执行顺序**（一次调用内）：
1. 完整扫描全部 Chunk 发现 `decision/insight/agenda` Memory Signal
2. 再次完整扫描发现 `fact/concept` Knowledge Signal
3. 按语义身份聚类（可独立变化/替代/冲突/关闭/查询的输出拆分）
4. 边界确定后应用五类判定树（**不把判定树当全文扫描的短路优先级**）
5. 应用 Memory–Knowledge 投影规则去重
6. 选直接 Evidence，按首个 Chunk + 规范化 title 稳定排序

**五类 Topic 模型**：

| Type | Group | 契约 |
|------|-------|------|
| `decision` | Memory | 已形成接受/拒绝/选择/承诺，有问题、约束、方案或取舍支撑 |
| `insight` | Memory | 从推理、观察、实践或失败形成的可复用认识，保留 Evidence、过程、边界 |
| `agenda` | Memory | 尚未关闭、需推进的事项（问题、风险、分歧、workaround、拟议行动） |
| `fact` | Knowledge | 有直接 Evidence 支撑、带主体/范围/时间/条件的可验证陈述 |
| `concept` | Knowledge | 规范名称、定义、别名、边界、适用范围 |

同一语义默认只出一个 Candidate；Memory 结论只有在会被独立查询、更新、Merge、过期或判断冲突时才额外投影为 fact/concept，避免同义副本。

**长度策略（务实设计）**：建议长度 title 50 / scope 200 / conclusion 300 / summary 500，**超出时保留原文 + 输出告警（字段、Candidate、实际长度、建议长度），不截断不失败**；仅超统一 8000 字符时按安全问题失败。理由：模型轻微超长不该中断整个 Job。

**可迁移经验**：让 LLM 做确定性工作的通用范式 —— **把不确定性压缩到单一阶段，其余环节程序化**。ID 生成、排序、校验这类确定性操作绝不交给模型；对下游模型阶段做「权限收缩」（明确列出它不能做什么）比只描述它该做什么更有效。

### 3.4 蒸馏九阶段与多存储一致性

```
1. PrepareEvidence     提取、清洗、切分原始内容 → payload.evidence_new
2. DistillCandidates   沙箱内 LLM 生成候选 → candidates.distilled（仅处理本轮新增）
3. Snapshot            对比已落库数据 → payload.snapshots + evidence_delta，清理 evidence_new
4. Residual            按被替换/删除的旧 Evidence 找受影响历史 Topic → candidates.residual
5. DeleteOldData       依快照删除失效 Evidence 及关联数据
6. MergeTopics         新增 + 残差候选与历史 Topic 合并，确定最终变更
7. GenerateRelations   基于最终 Topic 计算关系及边变更计划
8. PersistChanges      生成并依次执行 MySQL / ES / Nebula 写入计划
9. GenerateDigests     识别需求与风险（best-effort，失败不回滚主链路）
```

**编排原则**（源码注释明确写出）：「业务顺序必须在编排器中一眼可见，不通过组件扫描或 `@Order` 注解隐式决定」—— 九个 `executeStage` 顺序调用，每个带业务语义注释。

**一致性设计**：
- 三库写入**先生成计划再依次执行**（计划可校验、可日志、可重放）
- `NeuraOutboxEvent` + `startOrResume` 支持中断后从上次位置恢复
- 阶段 9 明确 best-effort：Digest 失败被记录但不回滚已完成的 Topic 主链路
- 最终一致性而非强一致 —— 知识库场景可容忍短暂不一致

**残差机制**（值得注意的设计）：Evidence 被替换或删除时，依赖它的历史 Topic 需要重新合并。阶段 4 专门生成这类「残差候选」，与新增候选一起进入合并阶段。这解决了**增量蒸馏时历史知识的级联失效**问题。

### 3.5 可观测性埋点

`NeuraObservedStepRunner` 统一包装每个步骤，自动记录入参摘要与出参摘要：

```java
List<TopicMergeCandidate> consolidated = observedStepRunner.run(
        logContext, "merge_topics", "merge_internal_candidates",
        Map.of("candidate_count", candidates.size()),          // 入参摘要
        () -> candidateInternalMerger.mergeCandidatesInternal(candidates),
        value -> Map.of("merged_candidate_count", value.size()) // 出参摘要
);
```

蒸馏进度走 workflow `progress` → Java `[NEURA_DISTILL_PROGRESS]` 通道，事件包括 `planner_input_ready`、`planner_model_transport`、`planner_result_ready`（记完整规范化 Plan，最多 20 条）、`generator_raw_result_received`、`candidate_topics_ready`（最终数量 + 聚合 usage）。Token usage 分 input / cache creation / cache read / output / total 分别记录，配 ClickHouse 日志（`NeuraDistillationCkLogger`）。

**要点**：LLM 应用的可观测性重点是**每阶段的 token 消耗与耗时**（成本归因）以及**中间产物快照**（结果不符预期时能定位是哪个阶段的模型输出问题）。

## 四、检索与知识工程（RAG）

### 4.1 十阶段检索管道

```
1. QueryEmbedding      生成 2560 维向量（LLM 改写内部 try-catch，失败用原 query）
2. EvidenceRecall①     BM25 + KNN 双查询 → Java 端 RRF 融合（全量模式，默认 size 30）
3. TopicRecall         title^4 + conclusion^2 + summary 多字段 BM25 + KNN → RRF（默认 20）
4. SeedTopicMerge      Evidence 派生 topicIds + 直接召回 topicIds 合并去重，保留来源标记
5. TopicEnrichment①    ES mget 批量补全字段详情
6. SemanticFilter      LLM 批量判断相关性，过滤无关 Topic
7. GraphExpansion      NebulaGraph 双向 BFS 1~2 跳扩展
8. TopicEnrichment②    为图扩展新发现的 Topic 补全（existingMap 保留已填充的）
9. EvidenceRecall②     带 topicIds filter 的混合召回，按 chunkId merge 去重
10. Rerank             向量阈值截断 → Cross-Encoder 评分 → Top-N 截断
```

**核心约束**：无新增 MySQL 表、无 Redis 使用（完全无状态，请求无副作用）；所有查询前置 `workspace_id` 过滤实现租户隔离；仅返回 `status=active`；**Embedding 一次生成两路复用**。

### 4.2 Stage 抽象与三档降级

```java
public interface SearchStage {
    String name();
    boolean shouldSkip(SearchContext ctx);
    void execute(SearchContext ctx);
    DegradationPolicy degradationPolicy();
}

public enum DegradationPolicy {
    ABORT,            // 失败终止管道返回错误
    SKIP_ON_FAILURE,  // 失败跳过本阶段继续后续
    FALLBACK          // 失败切换备用实现
}
```

| Stage | 策略 | 理由 |
|-------|------|------|
| QueryEmbedding | `ABORT` | 无向量则两路召回都无法执行 |
| ParallelRecall | `ABORT` | 无候选则后续无意义 |
| SeedTopicMerge / SemanticFilter / GraphExpansion / PrecisionFilter | `SKIP_ON_FAILURE` | 优化性阶段，跳过只降低精度不影响可用 |
| TopicEnrichment | `ABORT` | 缺详情则后续 LLM 判断无依据 |
| Rerank | `FALLBACK` | Reranker 不可用降级规则评分 |

`PipelineExecutor` 统一遍历、埋点（每阶段耗时 + 候选数变化）、按策略处理失败。`PipelineDefinition.Builder` 支持 `addStage` / `addBefore` / `addAfter` / `replace` / `remove`，按 name 定位，插新 Stage 不动已有代码。

**并行子阶段**：`CompositeStage` 用 `CompletableFuture.allOf` + 超时并行执行子 Stage。Evidence 与 Topic 召回写入 Context 的字段互不重叠，无需同步。

### 4.3 RRF 混合召回

**做法**：对每个索引发两次查询（BM25 关键词 + KNN 向量），在 Java 端用 `RrfFusion.fuse(bm25Hits, knnHits, rankConstant, size)` 融合。`rank_constant` 从 QConfig 读取（默认 60）。

**为什么融合放 Java 端而不用 ES retriever DSL**：
1. 融合逻辑可单测（`RrfFusion.fuse` 是纯函数）
2. `rank_constant` 走配置中心热调，不用改查询
3. 不绑定特定 ES 版本的 retriever 支持度

**字段权重**：Topic 召回用 `title^4` + `conclusion^2` + `summary`，体现标题匹配的信号强度远高于摘要。

### 4.4 自适应 Stage 设计

`EvidenceRecallSubStage` 是**同一个 Spring Bean 在管道中出现两次**，按上下文自动切换模式：

| 执行时机 | 判断依据 | 模式 |
|----------|----------|------|
| Stage 2（ParallelRecall 内） | `ctx.topicCandidates` 为空 | 全量召回，filter 仅 `workspace_id` + `status` |
| Stage 9（PrecisionFilter 后） | `ctx.topicCandidates` 非空 | filtered 召回，filter 增加 `topic_ids` terms |

第二次召回与首次结果按 `chunkId` merge 去重（首次优先 `putIfAbsent`）。

**"孤儿 evidence" 处理**：首次全量召回的 evidence 即使关联 Topic 被 LLM 淘汰仍保留 —— evidence 与 query 的相关性由自身内容决定，后续 Rerank 的向量阈值截断会自然淘汰不相关的。这个判断避免了「Topic 被淘汰导致相关 evidence 被误杀」。

`TopicEnrichmentStage` 同理出现两次，无状态设计，第二次通过 `existingMap` 保留第一次已填充的候选，只 enrich 新增 ID。

**可迁移经验**：Stage 无状态 + 从 Context 读取当前状态自行判断行为，比为两种模式各写一个类更少重复；前提是判断依据必须清晰（这里是 `topicCandidates` 是否为空）。

### 4.5 图扩展

**Nebula 图结构**：
- 顶点 tag `neura_topic`：`workspace_id`, `topic_id`, `title`, `type`, `status`, `version`
- 边 type `neura_topic_relation`：`workspace_id`, `relation_type`, `reason`, `created_at`, `updated_at`
- vid 格式 `"workspaceId:topicId"`（由 `NeuraTopicGraphSchema.topicVid()` 生成，**经转义防注入**）

**扩展策略**：统一双向 BFS 1～2 跳，不区分关系类型。`relation_type` 由模型生成不限定枚举，`GraphRelation` 用统一 `DEFAULT_RELATION_CONFIDENCE = 0.5`。

**要点**：图查询的 VID 拼接同样有注入风险，与 SQL 一样需要转义 —— 这类非关系型存储的注入防护容易被忽略。

### 4.6 重排与成本权衡

**Rerank 三步**：
1. **向量阈值截断** —— `vectorScore` 低于阈值（QConfig `evidence.vector.similarity.threshold`，默认 0.5）直接移除
2. **Cross-Encoder 评分** —— `NeuraRerankClient` 调 Reranker 服务，配 `RerankCircuitBreaker` 断路器；失败降级 `RuleBasedScoringStrategy` 规则评分
3. **Top-N 截断** —— 按 `finalScore` 降序取前 N（QConfig `evidence.max.count`，默认 30）

**成本权衡的实证**：`PrecisionFilterStage`（LLM 精筛）在当前默认管道中是**注释掉的**：

```java
.addStage(graphExpansionStage)
.addStage(topicEnrichmentStage)
//                .addStage(precisionFilterStage)
.addStage(evidenceRecallStage)
.addStage(rerankStage)
```

保留能力按需开启 —— 先用便宜手段（向量阈值 + Cross-Encoder 重排）够用就不上第二道 LLM。这是渐进权衡而非一次性堆满。

`topK` 归一化 `Math.max(1, Math.min(topK, MAX_TOP_K))`，默认 10 上限 30，防调用方传入过大值拖垮服务。

## 五、协议与集成

### 5.1 MCP 动态挂载

**解析流水线**（`WorkspaceMcpResolver.resolve(agentId, workspaceId, sessionId)`）：

1. 查 `spec_agent_mcp` 拿该 Agent 的 MCP 绑定列表（单层就近原则）
2. 查 `spec_workspace_mcp_config` 拿 `(workspaceId, mcpServerId)` 对应 headers
3. 解析 Token（三级优先级）
4. `McpCredentialHeaderResolver` 按 QConfig `mcp_credential_mapping.json` 注入 `Private-Token`、`X-Tenant-Id` 等

**Token 三级优先级**：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 用户级 MCP token | `SessionOperatorStore` 取工号 → `McpTokenClient` 查 ADA，取首个 `status=active` 的 `tokenPrefix` |
| 2 | 工作空间凭证表 | `spec_workspace_mcp_config.mcpHeaders` 中的 token |
| 3 | 两者均缺 | 该 MCP 条目**整条跳过**，不纳入 client 列表 |

**ToolProvider 构建**：

```java
public ToolProvider buildForAgentRuntime(long agentId, long workspaceId, String sessionId) {
    List<ResolvedMcp> resolvedList = workspaceMcpResolver.resolve(agentId, workspaceId, sessionId);
    if (resolvedList.isEmpty()) return null;
    List<McpClient> clients = resolvedList.stream()
        .map(resolved -> mcpClientRegistry.getOrCreateForResolved(resolved, workspaceId))
        .filter(Objects::nonNull).toList();
    return clients.isEmpty() ? null :
        McpToolProvider.builder().mcpClients(clients)
            .toolNameMapper((client, toolSpec) -> extractServerName(client) + "_" + toolSpec.name())
            .build();
}
```

**软降级**：mcpList 空 / workspace 缺失 / DAO 异常 → 返回空列表，Agent 退化为纯本地工具模式（返回 `null` ToolProvider）而非抛异常。**外部工具生态的可用性不该决定核心对话能力的可用性**。

**Client 复用**：`McpClientRegistry` 以 `{mcpServiceId}:{workspaceId}:{headersFingerprint}` 为 key 缓存，同工作空间多 Agent 挂载同一 MCP 时复用长连接，避免重复握手。**headers 指纹入 key 是个关键细节** —— 凭证轮换后指纹变化自动触发重建，不会拿旧 token 的连接继续用；若只用 `{serverId}:{workspaceId}` 作 key，换 token 后会静默复用失效连接。

**工具名前缀**：`toolNameMapper` 加 serverName 前缀，防不同 MCP Server 的同名工具冲突。

### 5.2 交付 MCP Server：反向驱动

沙箱内的 Claude Code 通过内置 MCP Tools 反向驱动后端状态机：

| Tool | 说明 |
|------|------|
| `start_delivery` | 启动交付流程 |
| `report_code_pushed` | 上报 commit SHA、MR URL、branch |
| `create_cadet_task` | 回填 Cadet 真实 session ID |
| `report_deploy_apps` | 声明本次要发布的 app 集合 |
| `escalate` | 请求人工介入 |
| `read_*` | 读取需求产物 |

**安全设计（重点）**：`DeliveryMcpSessionContextResolver` 把不透明的沙箱凭证解析为可信业务上下文（requirementId / workspaceId / operator）。**业务坐标不由 LLM 提供** —— 沙箱内的 LLM 是不可信主体，若让它自报 requirementId，它可以操作任意需求。工具处理类只从解析出的可信上下文提取坐标。

`ClaudeCodeInterrupter` 管理进程中断：发 `SIGINT` 让 CLI 优雅收尾（保留 session state），用 `pkill -f 'claude -p'` 精确匹配避免误杀，幂等可重复调用。

### 5.3 A2A 协议接入

`A2aAgentController` 实现标准 A2A（Agent-to-Agent）协议，使平台 Agent 可被任意第三方客户端调用。

**端点**：

| 端点 | 说明 |
|------|------|
| `GET /a2a/agents` | 列出所有 Agent Card URL |
| `GET /a2a/agents/{agentType}/.well-known/agent-card.json` | Agent Card 发现（标准路径） |
| `POST /a2a/agents/{agentType}` | JSON-RPC：`message/send` / `tasks/get` / `tasks/cancel` |
| `POST /a2a/agents/{agentType}/stream` | SSE 流式变体 |

**JSON-RPC 错误处理**（符合规范的关键细节）：

```java
try {
    validateJsonRpc(request);
    AgentTypeEnum parsed = parseSupportedAgentType(agentType);
    JsonRpcResponse response = switch (request.method()) {
        case "message/send" -> handleMessageSend(id, parsed, request.params());
        case "tasks/get"    -> handleTaskGet(id, request.params());
        case "tasks/cancel" -> handleTaskCancel(id, request.params());
        default -> JsonRpcResponse.error(id, A2aErrorCodes.METHOD_NOT_FOUND, "Method not found");
    };
    return ResponseEntity.ok(response);
} catch (IllegalArgumentException e) {
    return ResponseEntity.ok(JsonRpcResponse.error(id, A2aErrorCodes.INVALID_PARAMS, e.getMessage()));
}
```

注意：**业务错误也返回 HTTP 200**，错误信息装在 JSON-RPC error 对象里（`METHOD_NOT_FOUND` / `INVALID_PARAMS` / `TASK_NOT_FOUND` / `TASK_NOT_CANCELABLE` / `INTERNAL_ERROR`）—— 这是 JSON-RPC 规范要求，HTTP 状态码不承载业务语义。

**取消的状态校验**：先查 task 存在 → 校验非终态（`A2aTaskStates.isTerminal`）→ `requestCancel` → 置 `CANCELED` 并保存。终态任务返回 `TASK_NOT_CANCELABLE` 而非静默成功。

### 5.4 飞书接入两条路径

**路径一：TS Agent 工作空间机器人**

WebSocket 长连接（携程代理版 `CtripProxyLarkChannelConnector`）接消息 → `FeishuMessageHandler` → `TsUserDispatcher` 统一按 `(workspaceId, userId)` 加锁（群聊私聊共享，见 2.1）→ 虚拟线程异步执行 → `TsAgentChatClient` 调本服务 SSE 接口 → 聚合后回复。

`WorkspaceBotService` 管理绑定（`spec_workspace_bot`），`create` / `update` 时校验凭证并重建 WebSocket 连接，`delete` 断开连接。

**路径二：公共 Advisor 机器人（含自主答疑）**

显式 `@bot` 走原有路径不变；普通人类消息走新增的自主路径：

| 机制 | 设计 |
|------|------|
| 上下文收集 | Redis sorted set 保留每 chat 最近 50 条（创建时间序，保留 7 天） |
| 轻量分类 | 可配的小模型判断是否该回复，用更小的近期消息窗口 |
| 话题白名单 | 仅限明确的代码问题与 Trip.com 用户研究/洞察问题；寒暄、泛讨论、命令、机器人消息、未绑定群一律不触发 |
| 问题改写 | 依赖上下文的问题改写为独立问题；**无法解析的指代直接拒绝而非编造上下文** |
| 队列隔离 | 独立队列命名空间，每 workspace/chat 容量默认 3，占满**静默丢弃**；显式流量保持原队列 |
| 有用性 gating | 自主路径专用的尾部 metadata 标记，仅「找到有用信息」的结果剥离 metadata 后回复 |
| 降级重试 | 卡片因超出表格组件限制被拒时，退化为纯文本重试一次 |
| 灰度 | shadow-mode 支持（只判断不回复，观察决策质量） |

**成本与噪音控制思路**：不能让每条群消息都触发昂贵的 Agent 调用，也不能让机器人频繁插话。多层前置过滤（绑定检查 → 轻量分类 → 话题白名单 → 队列容量 → 有用性 gating）逐级收窄，每层都比下一层便宜。

**明确 defer 的项**（写在提案里）：冷却时间、日限额、绑定缓存、message-id 预去重、原子化上下文维护、人工回复取消、显式/自主会话强隔离。**清楚记录不做什么与做什么同样重要**。

## 六、安全设计

| 风险 | 防护 |
|------|------|
| 沙箱内 LLM 伪造业务坐标 | 不透明凭证换可信上下文，业务坐标不接受 LLM 输入 |

## 七、Python Bot 技术点

### 7.1 容错的响应解析

**问题**：SpecHub 后端返回结构可能嵌套多层且字段名不统一（`workspaceId` / `workspace_id`、`nextAgentTypes` / `nextAgents`）。逐层 `data["x"]["y"]` 取值极脆弱。

**方案**：递归遍历 + 多别名 + 大小写不敏感 + 空值过滤。

```python
def find_first(value: Any, *keys: str) -> Any:
    wanted = {key.lower() for key in keys}
    for key, child in _walk(value):
        if key.lower() in wanted and child not in (None, "", [], {}):
            return child
    return None
```

`_walk` 递归产出所有 `(key, value)` 对，`find_first` 返回首个命中且非空的值。调用处 `find_first(detail, "workspaceId", "workspace_id")` 一行搞定。

**取舍**：牺牲了「精确路径」的严格性换取对后端结构变化的韧性。在「Bot 是外围适配层、后端契约可能演进」的场景下是正确权衡；核心链路不该这么做。

### 7.2 决策树式 Agent 选择

```python
def choose_next_agent(self, detail: Any) -> str | None:
    status = find_status(detail)
    if status in TERMINAL_STATUSES:
        return None                          # 终态不推进
    next_agents = find_next_agents(detail)
    for agent in next_agents:
        if agent in AGENT_PROMPTS:
            return agent                     # 1. 后端推荐优先
    delivery_mode = find_first(detail, "deliveryMode")
    if status in HUMAN_STATUSES:
        return "SUPERVISOR_AGENT"            # 2. 待人工介入交给 Supervisor
    if str(delivery_mode) == "1":            # 3. 极速模式
        proposals = find_first(detail, "proposals", "proposalList")
        return "SUPERVISOR_AGENT" if proposals else "FAST_DESIGN_AGENT"
    return "REQUIREMENT_AGENT"               # 4. 兜底
```

四级降级：后端推荐 → 人工介入状态 → 交付模式推断 → 兜底。**优先信任后端，后端没给才本地推断**，避免 Bot 与后端状态机逻辑重复实现导致不一致。

### 7.3 SQLite 幂等去重

**问题**：飞书事件回调可能重复投递，重复处理会重复调用 Agent（有真实成本）。

**方案**：主键冲突即重复。

```python
def remember_message(self, message_id: str) -> bool:
    """Return True once for a message id, False for duplicate delivery."""
    now = int(time.time())
    with self._lock, self._connect() as conn:
        conn.execute("DELETE FROM messages WHERE created_at < ?", (now - 86400,))  # 顺手清理
        try:
            conn.execute("INSERT INTO messages(message_id, created_at) VALUES (?, ?)",
                         (message_id, now))
        except sqlite3.IntegrityError:
            return False
    return True
```

利用主键约束做原子去重，比「先 SELECT 再 INSERT」无竞态。清理逻辑搭在写路径上，省掉定时任务。`threading.Lock` + 每次新建连接规避 SQLite 的跨线程限制。

**会话映射**：`sessions` 表以 `requirement_id` 为主键存 `agent_type` / `session_id` / `context_id` / `task_id`，支撑「回复」指令续聊 —— 让无状态的聊天窗口具备会话连续性。

### 7.4 双模式运行

同一份代码支持两种飞书接入：

| 模式 | 入口 | 适用 |
|------|------|------|
| WebSocket 长连接 | `bot.start_background()` 守护线程 + `run_forever` 异常重连（sleep 10s） | 无公网回调地址 |
| HTTP 事件回调 | `POST /feishu/events` | 有公网入口，无状态易扩容 |

`DISABLE_FEISHU_WS` 控制（**默认 True**，即默认走 HTTP 回调）。`start_feishu_runtime` 用 `_start_lock` + `_started` 标志防 gunicorn 多 worker 重复启动 WebSocket。

**URL 验证兼容**（新老两种飞书回调格式）：

```python
def get_url_verification_challenge(payload: dict) -> str | None:
    if payload.get("type") == "url_verification":            # 老格式
        return payload.get("challenge", "")
    header = payload.get("header") or {}
    event = payload.get("event") or {}
    if header.get("event_type") in {"url_verification", "endpoint.url_verification"} \
            or event.get("type") == "url_verification":       # 新格式
        challenge = payload.get("challenge") or event.get("challenge")
        if challenge is not None:
            return challenge
    return None
```

### 7.5 运维友好设计

**健康检查暴露配置态**（不泄漏 secret，只报布尔）：


多路径注册（`/`, `/health`, `/vi/health`, `/spechub-feishu-bot/health`）适配不同网关前缀规则。

**Token 缓存**：`tenant_access_token` 提前 300 秒过期（`now + max(60, expires_in - 300)`），配 `threading.Lock` 防并发重复获取。

**智能默认值**：

```python
# 内网域名默认关 SSL 校验（自签证书），外网默认开
```

## 八、可复用的设计范式总结

| 范式 | 适用场景 | 本项目应用 |
|------|----------|------------|
| **生成与消费解耦（中转存储）** | 长耗时生成 + 不可靠客户端连接 | Redis ZSet 中转 SSE |
| **模板方法收口时序** | 多个变体共享复杂固定流程 | `AbstractAgentChatStreamService`（`final` 方法 + 抽象钩子） |
| **归一化 + 单一入口** | 多异构事件源驱动同一核心逻辑 | 四通路事件 → `DeliveryFlowEngine` |
| **权限收缩约束 LLM** | 需要 LLM 输出可复现 | Plan-first：Planner 独占发现，Generator 无 Drop 权限 |
