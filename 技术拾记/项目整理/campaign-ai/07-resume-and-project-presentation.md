## 简历项目模板

### 项目名称

Campaign AI 营销活动智能搭建平台

### 项目简介

面向营销运营场景，基于 DeepAgents、LangGraph 和企业业务工具，将自然语言需求转化为活动创建、招商、选品、素材及页面搭建等多步骤操作，支持人工确认、多轮修改、执行恢复和结果评估。

### 技术栈

Python、FastAPI、DeepAgents、LangGraph、Pydantic、MCP / SOA、PostgreSQL、Redis Streams、AG-UI、Langfuse。

只保留能够解释调用链、关键配置与取舍的技术。本文重点核实的是编排、状态、选品、流式和评估；如果需要重点讲某个 MCP 集成，还应单独追踪对应网关和业务调用。

### 职责与技术贡献

- 设计 Main Agent 与领域子 Agent 的分层编排机制，统一接入 8 类业务能力，通过类型化计划更新、TaskSnapshot 和产物字段校验管理跨 Agent 状态。
- 实现选品业务的语义契约与确定性报文构造，将实体解析、业务校验、用户预览和写入收敛为可验证链路，处理部分失败与会话内重复创建风险。
- 基于 LangGraph interrupt 和 PostgreSQL checkpoint 实现人工确认及跨请求续跑，结合 Redis Streams 支持运行中断线重连、事件回放和停止控制。
- 实现 Skills 按需读取和权威状态动态注入，组织稳定提示前缀，并接入模型兼容的缓存控制与子 Agent Token 用量归因。
- 构建 Session 级离线评估流程，结合确定性产物校验与 LLM Judge，支持评分单元覆盖校验、长证据分片及失败案例报告。

一页简历建议从中选择 3～4 条，优先体现本人解决的问题，不必全写。

## 30 秒项目介绍

> 这是面向营销运营的 AI Agent 平台，目标是通过自然语言完成活动搭建中的多步骤操作。系统由 Main Agent 组织任务，领域子 Agent 执行业务，通过结构化状态和工具约束保证结果可检查。项目还处理了人工确认、执行恢复和会话级评估。我主要负责的是【填写真实模块】，重点解决【填写具体问题】。

## 2 分钟项目介绍

> 运营搭建活动需要在多个业务系统之间配置活动、招商、选品、素材和页面，需求还会在过程中反复修改。这个项目把用户需求交给 Main Agent 理解和组织，再委派给领域子 Agent。
>
> 我的工作重点是【本人职责】。以选品为例，模型负责理解筛选意图和查询业务实体，代码负责把语义定义转换为正确报文，并在预览和写入边界检查约束。这样可以把模型擅长的语义判断与可确定的业务规则分开。
>
> 在多轮执行中，我们使用结构化任务快照和 checkpoint 管理任务状态；对于长任务，通过独立执行任务和 Redis 事件回放支持连接断开后的继续查看。这里解决的是 HTTP 断线恢复，不能等同于进程故障自动接管。
>
> 评估上，任务是否完成依据终态与产物证据判断，推理和字段理解等语义质量使用会话级 Judge。当前我能提供的验证证据是【真实测试、实验或业务数据】，仍存在的边界是【选择一个真实限制】。

## 推荐准备的三个案例

### 案例 A：模型参数到真实业务执行

适合展现 Agent 应用设计能力。

- **问题：** 模型直接处理复杂报文时，容易混淆字段、枚举或数据源要求。
- **方案：** 定义产品线语义契约，代码构造报文，确定性校验回传可修正错误。
- **取舍：** 增加契约与 builder 维护成本，换取执行边界可测试。
- **证据：** 准备一个真实输入、语义对象、生成报文、校验失败和修复后的结果。
- **个人补充：** 哪些契约或规则由你实现？哪个测试能复现原问题？

### 案例 B：确认后恢复与重复副作用

适合展现状态机与可靠性理解。

- **问题：** 用户确认跨请求，恢复时节点重跑可能重复展示或重复写入。
- **方案：** 在明确的 interrupt 边界暂停，正确传递 checkpoint 配置，限制未完成状态回写，写入路径增加可证明的重复创建防护。
- **取舍：** checkpoint 不覆盖外部业务事务，仍需讨论结果未知窗口。
- **证据：** 准备首次调用、中断状态、resume 输入、恢复结果和调用次数断言。
- **个人补充：** 实际定位过哪种恢复错误？哪些副作用被重复触发？

### 案例 C：可信的 Agent 评估

适合展现质量工程和实验思维。

- **问题：** 单条回答评分看不到完整任务，模型自由给分可能遗漏问题或改变分母。
- **方案：** 汇总 Session，代码生成评分单元，Judge 返回证据化 verdict，代码校验覆盖并计分；任务完成采用产物契约判定。
- **取舍：** 分片评估增加调用成本，Judge 仍需人工校准。
- **证据：** 准备同一会话的 Bundle、单元清单、Judge 输出和失败报告。
- **个人补充：** 哪个错误评分促成改动？是否做过人工对照和重复实验？

以上是案例组织模板，不是对个人历史贡献的事实陈述。

## 技术交流前必须补齐的数据

| 指标 | 建议口径 | 常见误区 |
|---|---|---|
| 任务成功率 | 成功逻辑任务数 / 可评估终态任务数，同时报告总样本与覆盖率 | 把等待确认算失败，或隐藏不可评估样本 |
| 首次采纳率 | 按明确候选集统计首次输出被采纳的比例 | 把无反馈直接当采纳 |
| 业务效率 | 对相同任务比较人工与辅助完成耗时，注明是否含用户等待 | 挑不同难度任务对比 |
| 单任务成本 | 固定任务集，按实际模型与缓存计费口径计算 | 总 Token 下降等同费用同比下降 |
| 执行延迟 | 使用原始耗时样本计算 P50/P95，区分执行和墙钟时间 | 平均多个 P95 |
| 可靠性 | 明确断线、停止、重试、进程退出等场景及通过条件 | 用正常路径证明故障恢复 |

展示结果时，至少同时给出：样本数、时间范围、模型/代码版本、指标定义、失败案例。没有数据时，写实现能力，不写提升百分比。

## 容易被追问的表述边界

| 不建议使用 | 更准确的说法 |
|---|---|
| 多 Agent 全并行自治 | Main 语义编排，同步委派领域 Agent |
| 全链路 Exactly-once | 会话内重复创建防护，跨系统幂等另需验证 |
| 已实现强审批授权 | 预览门禁与确认交互，完整 payload 绑定尚不能据此证明 |
| 进程崩溃无感续跑 | HTTP 连接解耦与事件回放；进程接管未证明 |
| 所有事件实时无损持久化 | 高频增量批量持久化，异常时存在丢弃与恢复边界 |
| 完整 RAG 平台 | 当前明确实现 Skills 按需读取和动态状态注入 |
| 消除幻觉 | 用实体查询、契约校验和工具门禁降低执行错误风险 |
| 接入 Langfuse 就有完整评估 | 已有会话级评估代码，仍需数据集、人工校准和真实实验 |
| Token 成本降低 X% | 只有在固定任务集和真实 usage 对比支持时填写 |
| 本人从零主导全部系统 | 按真实分工说明设计、实现、协作和维护范围 |
