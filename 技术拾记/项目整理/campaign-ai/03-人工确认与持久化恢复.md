# 技术亮点 03：人工确认与持久化恢复

## 已实现机制

项目通过 LangGraph interrupt 与 AG-UI 交互表达部分业务确认流程，通过根图 PostgreSQL checkpoint 保存恢复所需的状态。嵌套子图编译时使用 `checkpointer=None`，在根图调用上下文中继承父 checkpoint 机制。

确认并非全部使用相同实现：选品预览使用 interrupt；Main prompt 也定义了普通对话中的阶段确认。分析时需要区分业务确认与图中断，不能把所有确认步骤都说成持久化 interrupt。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

创建业务资源前，用户可能先查看方案，过几分钟再修改条件或确认。两次交互属于同一个任务，却发生在不同 HTTP 请求中。只把历史聊天存下来，无法准确回答“停在什么步骤、等待哪个输入、哪些结果已产生”。始终挂住原 HTTP 请求等待用户，也无法可靠应对刷新与连接超时。

需要持久化的是**任务的执行状态与等待点**，而不仅是一段聊天文本；恢复后还必须知道哪些逻辑会重新执行。

### 2. 使用哪些技术，各自负责什么

| 技术或组件 | 职责 | 不负责的事情 |
|---|---|---|
| LangGraph `interrupt` | 在图执行中产生等待外部输入的中断 | 不自动判断自然语言是否表示同意 |
| LangGraph `Command(resume=...)` | 把后续输入交回原中断流程 | 不替代会话归属与权限检查 |
| Checkpointer / AsyncPostgresSaver | 保存并读取线程关联的图状态与执行信息 | 不保存 Python 进程的完整内存镜像 |
| PostgreSQL + psycopg 连接池 | 为 checkpoint 提供持久存储和连接管理 | 不与外部业务写入自动构成一个事务 |
| AG-UI 与项目请求解析 | 传递待确认内容及恢复输入 | 不自动成为任务调度器 |

Checkpointer 按线程保存图状态，适用于会话连续性和人工确认；跨线程的长期知识存储是另一类能力，不能把两者都笼统称为“记忆”。[LangGraph 持久化模型](https://docs.langchain.com/oss/python/langgraph/persistence)

### 3. interrupt 的核心语义

`interrupt(payload)` 会把可序列化内容交给调用方，配合 checkpointer 形成可恢复等待点。之后以原线程上下文提交恢复输入，运行时重新进入相应节点，并让中断调用获得恢复值。**它不是把执行指针冻结后从任意一行继续**；包含中断的节点会重新执行，嵌套调用还要考虑父调用节点的重入。[中断与恢复规则](https://docs.langchain.com/oss/python/langgraph/interrupts)

由此产生一个设计要求：中断前的代码必须考虑重复执行。校验草稿通常可以重做，发送通知或创建资源则必须考虑幂等。项目选品工具把预览内容放入 interrupt payload，避免在中断前额外发送一次不可控的展示副作用。

### 4. 从预览到执行的完整过程

1. 选品工具校验预览文字与决策说明，调用 `interrupt` 返回待确认内容。
2. 根图 checkpoint 保存恢复所需的状态；子图通过父图配置与命名空间参与恢复。
3. 前端展示预览，用户后续提交回复，入口解析为恢复输入。
4. 中断节点重新进入，工具取得用户回复，将预览池名和原始回复写入状态。
5. 模型根据回复继续修改、取消或调用写入工具；工具再次检查结构性条件。

这里第 4 步记录了交互事实，不等于对任意写入 payload 签发了强授权令牌。完整内容是否需要版本绑定，仍是应用层设计。

### 5. 为什么使用 PostgreSQL 连接池，仍有哪些限制

项目根图和嵌套子图可能同时访问 checkpoint。单连接会让并发命令相互影响，所以 `_postgres_checkpointer` 使用 `AsyncConnectionPool`，并设置取出前连接检查、归还时事务清理和特定 `OperationalError` 重试。连接检查成功后到实际写入前仍可能断连，因此检查本身不能替代错误处理。项目还关闭 Saver pipeline，以适配其代理连接场景。

这套设置解决的是存储访问问题，不能消除下面的窗口：**远端选品池已创建 → checkpoint 尚未记下成功 → 进程退出**。重试前仍需查结果或使用业务幂等键。并且，保存了状态并不代表系统已经实现自动寻找失联任务、重新领取并执行的调度能力。

与自己维护 `pending` 表和恢复接口相比，LangGraph 可以复用图状态、中断和嵌套执行机制；代价是必须掌握节点重入、线程标识和 checkpoint 命名空间。持久化组件能提供恢复依据，业务重复执行风险仍由应用处理。

### HTTP 请求如何变成恢复命令

源码节选：[request_parser.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/request_parser.py#L169)（第 169–180 行；片段省略外围上下文，不是独立运行脚本）。

```python
thread_id = body.get("threadId") or str(uuid.uuid4())
```

`_extract_resume_command` 从 `body.resume` 读取 interruptId、status 和 payload。真实 LangGraph interrupt ID 构成 ID → payload 映射，cancelled 转成 `approved=False`；历史 synthetic ID 走单值兼容。`build_graph_input` 在恢复路径直接返回 `Command(resume=resume)`，不把确认重新包装成普通用户消息再从头开始。

## 技术问题与回答

### Q1：长任务 Agent 如何跨请求等待人工确认？HTTP 会话、任务状态与 checkpoint 怎么分工？

**回答思路：** 用户可能隔很久才回复，业务等待不能等同于占住 HTTP 请求。项目将预览放入 interrupt，用根 checkpoint 保留图状态，后续请求通过 Command(resume=...) 续接。传输会话、图执行状态与远端业务资源各有生命周期。

**代码如何实现：** 预览工具把等待内容交给 `interrupt`，后续请求由 `build_graph_input` 生成 Command(resume=...)。根 Saver 由应用 lifespan 持有，并传给 Main；恢复依赖会话标识和已存图状态，而不是保留原来的 HTTP 调用栈。实现位置：[preview_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/preview.py#L139)、[build_graph_input](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/request_parser.py#L166)、[deepagent_lifespan](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/graph_runtime.py#L161)。

**深入追问：** 用户刷新或更换连接后，需要带回什么？原 threadId 和正确的恢复输入不可丢；HTTP 已重新建立不代表业务任务应该重新创建。

### Q2：Durable Execution 是从断点下一行继续吗？为什么恢复仍会重复副作用？

**回答思路：** 需要讲清节点重入，而不是把 checkpoint 描述成进程内存快照。项目 interrupt 前的校验可能重新执行；有副作用的逻辑必须安排在明确边界，并考虑重试幂等。恢复能力不自动消除远端成功而本地未持久化的窗口。

**代码如何实现：** 看 `preview_selection_pools` 的顺序：先做预览和 decisions 校验，再调用 interrupt，取到 reply 后才构造状态更新。因此恢复重入时，中断前校验可能重做；把写接口放在其前面就会引入重复副作用风险。这里没有把节点内任意 Python 局部变量当作可恢复进程内存。实现位置：[preview_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/preview.py#L139)、[test_none_checkpointer_resumes_same_subagent_across_two_interrupts](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_subagent_checkpoint_namespace.py#L152)。

**深入追问：** 把所有写入放到 interrupt 后是否就安全？仍可能在远端成功后、本地状态保存前失败；确认和幂等解决的是不同问题。

### Q3：嵌套 Agent 的 checkpoint 该共享还是独立？怎样避免两个状态源互相覆盖？

**回答思路：** 根据恢复边界选择，而不是每个 Agent 都创建一份持久实例。本项目 Main 是根图和根 Saver，子图在父配置中执行；额外独立存储可能改变任务隔离和恢复语义。这里的 None 要结合父图上下文解释，不能等同于完全没有 checkpoint。

**代码如何实现：** `_boot_runtime` 显式 `compile_subagent_graphs(checkpointer=None)`，根 Main 则接收真正 Saver。`build_subagent_selection` 在 None 分支 `g.compile()`，实际运行时依赖父调用配置。包装层 ainvoke 原样传 config，测试同时检查 thread_id、checkpoint_ns 和 tags 未被改写。实现位置：[_boot_runtime](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/graph_runtime.py#L35)、[build_subagent_selection](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L333)、[test_wrapper_preserves_parent_checkpoint_config_for_sync_invoke](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_subagent_checkpoint_namespace.py#L29)。

**深入追问：** 什么时候适合独立子 Agent 会话？独立服务生命周期、跨父任务长期对话等可能需要，但要重新定义命名空间、权限和结果合并；当前实现不能直接套用。

### Q4：多会话 Agent 如何隔离“新任务”和“旧任务恢复”，避免串草稿或串用户？

**回答思路：** 新委派应重新准备消息与领域输入，原任务恢复应关联原线程与中断 ID。项目有父配置透传和嵌套恢复测试，但这些只证明局部状态语义；会话访问授权还需入口检查，threadId 本身不是身份凭证。

**代码如何实现：** 新委派经过 `prepare_input` 重建本次消息与领域投影；中断恢复通过真实 interrupt ID 定位原等待点。嵌套测试分别断言两次新任务没有 private_marker 残留、同一任务两次恢复都能到达后续状态，证明这两个场景应分开验证。实现位置：[prepare_input](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L218)、[_extract_resume_command](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/request_parser.py#L73)、[test_none_checkpointer_starts_same_subagent_second_task_fresh](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_subagent_checkpoint_namespace.py#L105)。

**深入追问：** 同一个用户再次调用同一个领域 Agent，要沿用哪些数据？有效活动上下文可以保留，私有草稿是否沿用必须由任务语义决定，不能把同一个 Agent 名称当作同一个任务。

### Q5：Agent 在等待人类时，草稿能否立即成为其他 Agent 的输入？如何避免暂态结果污染？

**回答思路：** 待确认内容与已完成产物要分开。项目在中断结果上只向上传递消息及 interrupt，正常结束才校验和合并业务结果。这阻止暂态草稿被自动当成最终执行结果，但并不替代领域内部的完整状态设计。

**代码如何实现：** `_finish_result` 在发现 `__interrupt__` 时立即返回，只选择 messages 和 __interrupt__，完全绕过后续业务结果投影。只有非中断结果才调用 `_validate_result`，然后检查领域产物允许列表。因此待确认草稿不能借一次暂停直接被合并成 Main 的最终产物。实现位置：[_finish_result](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L129)。

**深入追问：** 如果下游只需要只读预览，能否共享草稿？可以作为另行设计的草稿契约，必须标明版本与未确认状态，不能复用正式产物字段造成歧义。

### Q6：HITL 应该使用结构化批准还是自然语言“好的”？如何处理修改与取消？

**回答思路：** 结构化动作能让交互意图更明确，自然语言更灵活但需要语义判断。项目解析器支持结构化 cancelled，选品又保留回复文本由模型解释；这不等于严格内容授权。风险越高，越需要把操作范围与确认记录绑定。

**代码如何实现：** 请求解析器把标准 cancelled 状态转换为 approved=False，但选品工具仍通过 `serialize_chat_input_reply(reply)` 保存原始回复文本，再由模型决定修改、取消或写入。要区分传输层的结构化取消与普通聊天里的自然语言判断；当前写入函数只检查池名预览记录和活动上下文。实现位置：[_extract_resume_command](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/request_parser.py#L73)、[preview_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/preview.py#L139)、[upsert_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L130)。

**深入追问：** 用户说“好的，但改成下周”算批准吗？包含修改时应重新形成并展示有效方案；当前模型语义解释仍存在风险，不能只看到“好的”就跳过变更确认。

### Q7：持久化 Agent 遇到数据库断连，重试应该放在哪层？会不会重复业务操作？

**回答思路：** checkpoint 存储错误应在相应存储边界处理，外部业务请求是否重试要另判。项目通过连接池、连接检查和 Saver 写入重试处理数据库连接问题。该层重试既不自动重发 SOA，也不把 SOA 和 checkpoint 放入一个事务。

**代码如何实现：** `_postgres_checkpointer` 使用 AsyncConnectionPool，借出前 check_connection、归还时 `_reset_conn` 清理未结束事务；ResilientPostgresSaver 在 aput/aput_writes 内捕获 OperationalError，并按 `_MAX_RETRY=3` 循环。check 成功到真正 execute 之间仍可能断连，所以还需要操作级处理。实现位置：[_postgres_checkpointer](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/graph_runtime.py#L66)。

**深入追问：** 连接探活成功为什么下一次 SQL 仍会失败？检查与执行之间存在时间窗口；因此探活不能替代操作级错误处理，也不能作为绝对可用性保证。

### Q8：业务写入与 checkpoint 不在同一事务时，如何处理“远端成功、本地未知”？

**回答思路：** 这是生产 Agent 的关键失败窗口。当前代码只能依据已记录产物去重；如果远端实际已写成功却尚未回写状态，恢复后不能假定安全重做。需要回查、幂等键或明确的未知状态处置，不能把 checkpoint 宣传为 Exactly-once。

**代码如何实现：** SOA 请求发生在 `_upsert_one`，成功产物返回后由选品 finalize 合并进 artifacts；checkpoint 写入发生在图运行时。两者不在同一事务，代码中的 `_created_keys` 也只能读取已经记录的产物。如果远端成功但本地还未记录，这个查询就不能识别已发生的写入。实现位置：[_upsert_one](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/upsertor.py#L195)、[finalize_selection_node](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L294)、[_created_keys](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L67)。

**深入追问：** 可以直接标记失败让用户重试吗？结果未知与确定失败应区分，盲目提示重试可能造成重复资源；本项目没有展示统一的跨系统事务方案。

### Q9：Agent 恢复执行时，身份凭据、会话权限和业务状态应该如何隔离？

**回答思路：** 业务 state 用于任务恢复，请求身份通过独立上下文绑定。项目以 ContextVar 传播 SSO，避免把原始 cookie 当作模型猜测的业务字段。恢复时还要确认当前操作者有权访问原任务和资源；有 threadId 或有旧 checkpoint 都不等于有授权。

**代码如何实现：** HTTP SSO middleware 在 `_call_next_with_sso_context` 调用 set_sso_context，并在 finally 清理；sso_context.py 用 ContextVar 保存请求级身份，`bound_sso_context` 还通过 token 恢复之前的上下文。该机制隔离运行身份，不等于检查 threadId 的业务归属；后者不能从 ContextVar 本身推导。实现位置：[_call_next_with_sso_context](../../../../../Workspace/ibu_campaign_copilot/campaign/middleware/sso_auth_middleware.py#L94)、[bound_sso_context](../../../../../Workspace/ibu_campaign_copilot/campaign/utils/sso_context.py#L108)。

**深入追问：** 用户权限在等待期间被收回怎么办？恢复写入应依据当前权限重新校验，而不能只依赖历史批准；是否每个外部系统已这样实现，需要逐项核对。

### Q10：如何做长任务 Agent 的故障注入测试，而不只测一次正常 resume？

**回答思路：** 覆盖连续 interrupt、新任务状态隔离、错误恢复 ID、客户端断开、进程退出及远端结果未知。现有内存 Saver 测试可以验证嵌套语义，真实 PostgreSQL 和副作用故障场景则需集成验证。测试设计应写明预期的状态与调用次数。

**代码如何实现：** 已有测试用 MemorySaver 构造父子 StateGraph，依次读取 first_interrupt.id、second_interrupt.id 并精确 resume，最终断言 SUCCEEDED；请求解析测试另验证真实 ID 的字典寻址与历史输入兼容。它们证明的是测试设计覆盖范围，本次只读源码，没有执行，也没有用真实 PostgreSQL 做进程故障注入。实现位置：[test_none_checkpointer_resumes_same_subagent_across_two_interrupts](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_subagent_checkpoint_namespace.py#L152)、[test_single_real_interrupt_id_stays_an_addressed_resume_map](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/test_request_parser_resume.py#L209)。

**深入追问：** 恢复成功但写接口被调用两次，算通过吗？不能只检查最后回复；还应验证产物数量、写入次数和重复副作用。本次仅阅读现有测试源码，未执行故障注入。
