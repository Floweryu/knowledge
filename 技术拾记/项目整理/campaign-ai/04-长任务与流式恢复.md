# 技术亮点 04：长任务与流式恢复

## 已实现机制

启用 Redis RunBus 时，`start_run` 启动进程内独立任务执行图，HTTP 流从本地队列读取事件。客户端断开时解除队列连接，后台任务继续运行；重连根据 Redis 中的运行信息选择实时回放或历史记录回放。

Redis 保存事件流、快照、运行元信息及控制消息；PostgreSQL checkpoint 保存图执行状态，二者职责不同。高频增量帧使用批量写入，结构性事件触发及时刷新。运行中快照采用明确的回放游标策略，避免丢失成对事件的开始帧。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

Agent 任务可能持续多个模型和工具调用。用户关闭页面、网络切换或网关断开连接后，会出现两个独立问题：后台业务是否还在执行，以及重连页面怎样补回没收到的事件。单纯将模型 token 通过流式接口发出去，并不能回答这两个问题。

还有协议层问题：文本和工具调用拥有 start/content/end 边界。重连后即使收到了后半段数据，也可能因缺少前面的开始事件而无法正确恢复页面状态。

### 2. 技术分层：谁管连接，谁管任务，谁管历史

| 技术 | 特点与职责 | 本项目中的使用 |
|---|---|---|
| FastAPI / StreamingResponse | 通过迭代器逐步生成 HTTP 响应体 | 承载流式响应，不自动保活业务任务 |
| SSE | HTTP 上服务器向客户端持续发送事件的传输方式 | 将 Agent 事件流交给前端 |
| AG-UI | 约定 Agent 与前端交互的事件语义 | 表达消息、工具调用、状态与运行生命周期 |
| `asyncio.Task` + Queue | 进程内协作式异步执行与事件交接 | 后台运行图，连接消费本地队列 |
| Redis Streams | 带有序 ID、可按游标读取的事件记录 | 保存运行事件并服务重连回放 |
| RunSupervisor / RunBus | 项目的任务管理与事件存取封装 | 处理启动、detach、回放、停止与终态 |

StreamingResponse 接收普通或异步迭代器并持续输出响应；AG-UI 则定义输出内容的事件语义，二者分处传输与交互协议层。[FastAPI 流式响应](https://fastapi.tiangolo.com/advanced/custom-response/)、[AG-UI 协议](https://docs.ag-ui.com/introduction)

### 3. asyncio 与 Redis Streams 的关键特点

**asyncio.Task 能与当前响应消费过程分开调度。** 项目使用 `create_task` 启动执行，并在 supervisor 中管理任务和连接。因此连接解除不必等于业务取消。但协程仍依赖同一个进程和事件循环；阻塞调用会影响协作调度，进程退出后内存中的 Task 也不会继续存在。[Python Task 机制](https://docs.python.org/3/library/asyncio-task.html)

**Redis Streams 可从指定 ID 继续读取记录。** `XADD` 追加事件，`XREAD` 读取游标之后的记录，支持等待新数据。与只把在线消息推送给订阅者相比，它能提供保留范围内的历史读取。项目事件路径采用 `XADD/XREAD`，不要把 Redis 的 consumer group、ACK 或消费者接管能力直接写成项目已经使用的功能。[Streams](https://redis.io/docs/latest/develop/data-types/streams/)、[XREAD](https://redis.io/docs/latest/commands/xread/)

代码还设置 maxlen 与 TTL，因此“写入 Stream”不等于永久保留；Redis 的落盘和复制配置也没有在本次核验，不能承诺任何故障下事件零丢失。

### 4. 正常连接和重连分别怎样工作

1. `start_run` 建立运行信息、初始快照与本地队列，启动 `_worker_loop`。
2. worker 运行图并产生事件，RunBus 保存事件；当前连接消费本地队列。
3. 高频 delta 可以暂存在批量器中，结构性事件促使及时刷新；不能笼统宣称每帧都已持久化后才交付。
4. 断线时 detach 当前连接。启用这条 RunBus 路径且原进程仍存活时，worker 可以继续执行。
5. 重连由 `attach_or_replay` 读取运行状态、快照和事件流，必要时补足终态表达。

例如，工具调用 T 的开始事件已经发出，但结束事件尚未发出。若快照不包含 T 的进行中状态，而游标又越过其开始事件，重连就会得到孤立的结束事件。项目限制运行期快照游标推进，回放本轮事件以保留边界；代价是可能重复读取更多数据。

### 5. 为什么不只用 WebSocket 或 Pub/Sub

换成 WebSocket 可以改变双向传输方式，却不会自动提供任务持久化、历史回放或副作用幂等。Redis Pub/Sub 适合在线通知，但连接离线期间的历史补发还需额外存储；Streams 在本项目承担这层记录能力。

技术贡献是把**执行、连接和事件记录**分开，并处理三者之间的不同步窗口。系统采用有限队列、增量批处理和协作式停止，也意味着要承认慢客户端丢帧、缓冲区溢出、停止不能回滚远端写入等取舍。若需要 Pod 崩溃后的自动接管，还要补任务持久调度、租约及幂等机制。

```python
task = asyncio.create_task(

        input_payload=input_payload,

# dataclass 是 frozen=False，直接赋值即可
object.__setattr__(active, "task", task)
register_active_run(active)

try:
    last_frame_at = time.time()
    async for frame in _with_keepalive(_drain_queue_to_client(queue)):
        last_frame_at = time.time()
        yield frame
finally:
    # HTTP 生成器退出（客户端断开 / 完成）：detach —— 不 cancel worker
    active.detached_queue = None
```

`start_run` 创建 worker Task，将它登记到 ActiveRun；HTTP 生成器只读取 queue。消费者退出时 finally 仅把 `active.detached_queue` 设为 None，没有调用 task.cancel。worker 的 `_fanout` 检查 queue 是否存在，再决定是否投递当前连接；业务生成器仍可继续运行。

因此独立的是协程生命周期，不是进程：任务仍属于当前事件循环。[test_start_run_survives_client_detach](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L368) 用 Event 卡住 worker，消费两帧后关闭客户端生成器，再放开 Event，最终断言运行完成且 Redis 中有 4 条事件。该测试使用替身生成器／测试 Redis 环境，不能替代 Pod 崩溃接管验证。

### Redis API 怎样用于事件记录和读取

源码节选：[run_bus.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_bus.py#L184)（第 184–198 行；片段省略外围上下文，不是独立运行脚本）。

```python
async def publish_event(self, run_id: str, frame: str) -> str:
    key = _k_events(run_id)
    try:
        r = await self._client.get_native(key)
        entry = await r.xadd(
            key,
            {"f": frame},
            maxlen=self._events_maxlen,
            approximate=True,
        )
        await r.pexpire(key, self._ttl_ms)
        return entry.decode() if isinstance(entry, bytes) else str(entry)
    except redis.exceptions.RedisError as exc:
        logger.warning("[run_bus] publish_event {} failed: {}", run_id, exc)
        return ""
```

一条 SSE frame 存在字段 `f`，XADD 返回的 entry_id 成为读取游标。这里设置 MAXLEN 与 TTL，事件不是无限保留。[RedisRunBus.tail_events](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_bus.py#L236) 循环 `xread({key: cursor}, block=xread_block, count=100)`，每读到一条就推进 cursor；应用层 block_ms=0 被映射为 redis-py 的 block=None，避免误传 0 导致无限等待。

### 快照与回放的边界怎样协调

源码节选：[run_supervisor.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L765)（第 765–772 行；片段省略外围上下文，不是独立运行脚本）。

```python
if bus is not None and _STATE_SNAPSHOT_MARKER in frame:
    await _flush_snapshot(
        bus,
        run_id=run_id,
        messages=messages_mirror.snapshot(),
        last_state_snapshot=last_state_snapshot,
        last_stream_id="0-0",
    )
```

这段运行期分支固定写 `last_stream_id="0-0"`，即使状态快照已更新，也不会把回放游标推进到可能切开工具 start/end 的位置。运行结束后的 finally 则会用最终 stream ID 写快照。这两个阶段必须区分，不能说所有快照永远使用相同游标。

[attach_or_replay](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L967) 仅在 meta.status=running 时使用 Redis 快照和 tail；其他状态走历史 DAL 回放。tail 意外缺终态时，先读最新 meta，再尝试 Stream 尾帧，最后读 checkpoint 的 pending interrupt 重建相应终态。回放补齐的是前端协议，不会重新执行 SOA。

### 高频事件与慢客户端怎样处理

`_RedisFrameBatcher.push` 对 CONTENT/ARGS 入缓冲，满足时间窗口后 flush；priority 帧先 flush 已缓冲增量，再单条 publish。`_flush_locked` 合并相邻同 `(type, id_field, id)` 的 delta，仅按 Redis 返回的 entry ID 数量移除已确认帧。`_fanout` 的本地 queue 使用 put_nowait，QueueFull 时只记录告警；缓冲达到硬上限也会丢弃旧增量，所以不能用注释中的“Redis-first”推导所有客户端已见帧都已持久化。

## 技术问题与回答

### Q1：生产 Agent 为什么要解耦推理执行与客户端连接？SSE 或 WebSocket 能自动解决吗？

**回答思路：** 传输协议解决数据如何到达页面，执行生命周期决定页面离开后业务是否继续。项目使用独立 asyncio Task 执行图，HTTP 消费队列事件。换用 WebSocket 不会自动获得后台运行、持久调度和恢复，需要逐层说明实现。

**代码如何实现：** `start_run` 用 create_task 启动 `_worker_loop`，HTTP 流调用 `_drain_queue_to_client`；finally 仅清空 active.detached_queue。业务执行者与响应消费者由两个协程承担，这才让断开响应不必取消 worker。只返回 StreamingResponse 并不自动获得这个关系。实现位置：[start_run](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L853)、[_drain_queue_to_client](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L359)。

**深入追问：** 为什么没有连接也可能继续写业务？因为 detach 不等于取消任务；产品应区分关闭页面与显式停止，不能让用户误以为网络断开就撤销操作。

### Q2：Agent Runtime 的内存队列与持久事件流怎样分工？为什么不能只用 Pub/Sub？

**回答思路：** 本地队列承接当前连接，Redis Streams 保存保留范围内的事件，供后续连接按游标读取。单纯在线通知不能替代历史补发。项目有增量批处理，因此客户端看到某帧不意味着那帧此刻必已落到 Redis，更不能把 Redis 写入等同于任意故障下永久保存。

**代码如何实现：** `_worker_loop._fanout` 先调用 batcher.push，再对本地队列 put_nowait；RunBus.publish_event 使用 XADD，重连使用 tail_events 的 XREAD。需要注意 batchable 的 push 可能只入内存缓冲，本地队列已收到时 Redis 未必已写完，不能只照搬该函数的旧注释。实现位置：[_fanout](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L705)、[push](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L328)、[RedisRunBus.tail_events](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_bus.py#L236)。

**深入追问：** 消息投递顺序和业务执行顺序是同一回事吗？不是。还要区分生成、缓冲、Redis 确认和客户端收到的时刻，以及中间的失败窗口。

### Q3：Session Log、Context Window、checkpoint 与事件回放有什么区别？这算完整 Event Sourcing 吗？

**回答思路：** 模型上下文是本轮输入视图，checkpoint 是图恢复状态，SSE 事件和快照用于页面恢复。当前项目的 Redis 流有保留限制，且业务写入未由它作为唯一事实源重建，不能据此称为完整 Event Sourcing。应描述已有分工，不照搬托管 Agent 平台的完整架构。

**代码如何实现：** 根图的 Saver 由 `_postgres_checkpointer` 创建，存的是图恢复状态；RunBus 的 publish_event 和 write_snapshot 则处理 SSE frame、messages_snapshot 与 state_snapshot。attach_or_replay 在缺终态时调用 graph.aget_state 读 pending interrupt，是两类存储协作的具体位置，而非共享事务。实现位置：[_postgres_checkpointer](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/graph_runtime.py#L66)、[RedisRunBus.write_snapshot](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_bus.py#L280)、[attach_or_replay](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L967)。

**深入追问：** 能直接拿 SSE 历史恢复所有业务状态吗？不能。展示事件未必包含完整图配置或外部副作用信息，仍需 checkpoint、业务查询和明确恢复协议。

### Q4：AG-UI 流式工具调用为什么必须保持事件边界？断线重放如何避免孤立的 END？

**回答思路：** 前端消费的是有关联 ID 和生命周期的事件，不只是文本。若回放游标越过 start，而快照没有表达对应进行中对象，后续 end 就失去上下文。项目运行期固定游标从本轮起点回放，代价是更多数据与保留范围依赖。

**代码如何实现：** worker 收到 STATE_SNAPSHOT 时传 `last_stream_id="0-0"`，并不使用此时最新事件 ID。attach_or_replay 从快照中的该字段开始 XREAD。本轮从头回放能保留开始事件，但前提是事件仍在保留范围；终态 finally 使用最终 ID，与运行期策略不同。实现位置：[_worker_loop](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L665)、[attach_or_replay](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L967)、[test_mid_run_snapshot_never_advances_offset](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L984)。

**深入追问：** 是否可以只记“最后显示了哪个 token”？这无法覆盖交错的工具调用与状态事件；应按协议对象及事件顺序设计恢复测试。

### Q5：流式 Agent 怎样降低事件写入成本，又不破坏工具调用和前端状态？

**回答思路：** 优先合并可拼接的相邻文本或参数增量，结构性 start/end、终态和快照需要保留顺序。项目按事件类型和关联 ID 合并，不能跨不同工具或消息拼接。写入次数减少是否带来总体收益，还应测延迟、恢复完整性和资源开销。

**代码如何实现：** `_split_delta_frame` 解析 type、messageId/toolCallId 和 delta，形成三元组 key；`_merge_delta_frames` 只在相邻 key 相同的情况下拼接 delta。遇到不同 ID、不同 type 或不可解析帧会先输出已有分组，保持顺序。工具开始／结束等边界帧不进入这个合并集合。实现位置：[_split_delta_frame](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L189)、[_merge_delta_frames](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L219)。

**深入追问：** 把所有事件攒一秒再发是否更省？可能增加关键状态可见延迟；项目区分 batchable 与 priority，不是对所有事件采用统一延迟。

### Q6：Agent 输出比前端消费快，怎样设计背压？有界队列是不是就不会丢数据？

**回答思路：** 有界队列只限制内存，满时怎样处理才决定可靠性。当前 put_nowait 满时继续执行并告警，Redis 缓冲也有丢弃旧增量的上限；它选择保护执行可用性，不能承诺无损。需要把缺帧和恢复能力作为独立指标。

**代码如何实现：** start_run 创建有界 Queue，`_fanout` 调 put_nowait，QueueFull 时记录告警并继续；batcher 在达到 `_BATCH_BUFFER_HARD_CAP` 时删除最旧增量。这两处防止等待慢客户端或无限增长，但都明确存在实时帧或缓冲增量损失的可能，不能解释成无损背压。实现位置：[start_run](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L853)、[_fanout](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L705)、[push](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L328)。

**深入追问：** 更严格的交付语义要补什么？可讨论确认、重放窗口、限速和明确的失败通知；这些不能由 Queue(maxsize=...) 自动推导。

### Q7：用户点击停止，为什么 Agent 可能仍产生业务副作用？Cancellation 与 Compensation 怎样区分？

**回答思路：** 取消控制本地任务是否继续，补偿处理已完成的外部效果。项目在事件边界协作式检查 stop_event，已经发出的 SOA 请求不会因本地停止自动撤销。应向用户准确区分停止后续执行、当前调用结果未知和需要另行补偿。

**代码如何实现：** `_stop_watcher_loop` 读取 RunBus 控制流，收到 kind=stop 就设置 stop_event。worker 在下一次消费到 frame 时检查 Event，尝试 gen.aclose 并发送 stopped 终态。若上游调用迟迟未返回到帧边界，停止就不能即时生效；这条路径也没有远端业务回滚调用。实现位置：[_stop_watcher_loop](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L639)、[_worker_loop](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L665)。

**深入追问：** 停止请求能否做到立刻生效？取决于工具是否及时返回控制权、底层是否支持取消；本项目不能依据 Event 标记承诺所有外部调用即时停止。

### Q8：长时间自主 Agent 如何在 Pod 崩溃后接管？为什么有 Redis 和 checkpoint 仍不够？

**回答思路：** 持久数据提供恢复依据，接管还需要发现失联任务、唯一领取、租约、执行版本及副作用幂等。当前 worker 是进程内 Task，重连函数读取事件而不自动重建 worker，所以只能说明断线续跑和显式恢复基础，不能宣称自动故障迁移。

**代码如何实现：** `start_run` 将 asyncio Task 存进进程内 ActiveRun；attach_or_replay 根据 Redis meta 读事件，没有在这里创建新的图执行任务。Redis 可以保存已写事件，根 checkpoint 可以供显式恢复，但上述代码不构成持久队列领取、租约和自动失败接管协议。实现位置：[start_run](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L853)、[attach_or_replay](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L967)。

**深入追问：** 增加任务队列后是否就解决了？至少还要考虑重复领取、过期 worker 继续写入和结果未知窗口；这些属于进一步架构设计。

### Q9：Agent 前端显示成功、后端却仍待确认，如何保证终态语义一致？

**回答思路：** 结束事件、业务成功和等待人工确认不能混用。项目 tail 缺终态时读取最新 meta、Stream 尾帧及 pending interrupt，再分别生成相应事件。对终态补偿的评估应检查语义分支，而不是只确认页面停止转圈。

**代码如何实现：** attach_or_replay 在未见终态时重读 get_meta，若已 finished/error/stopped，则尝试 peek_last_frame；再失败才 aget_state 并提取 pending interrupts，分别输出等待确认、停止、错误或结束事件。它保留分支语义，不把网络回放成功直接等同业务执行成功。实现位置：[attach_or_replay](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/run_supervisor.py#L967)、[test_attach_or_replay_terminal_from_checkpoint_pending_interrupts](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L618)。

**深入追问：** 能否在所有超时后统一补 RUN_FINISHED？不能。会掩盖错误、取消或等待状态，甚至让用户错误地认为远端资源已完成。

### Q10：生产 Agent 的可靠性评测除了“最终答案正确”，还应覆盖哪些交互故障？

**回答思路：** 至少覆盖客户端断开、慢消费、事件截断、重复重连、停止、终态缺失与进程退出。项目已有 detach、回放边界和终态补偿测试入口，但没有据此完成生产故障验收。应同时记录任务结果、事件完整性和副作用次数。

**代码如何实现：** `test_start_run_survives_client_detach` 先关闭客户端生成器，再放开 Event 让 worker 继续，检查 finished 和事件数量；`test_replay_from_seed_offset_keeps_start_before_end` 检查回放边界；终态补偿另有独立测试。本次只核对测试源码，不宣称这些测试在当前环境已通过。实现位置：[test_start_run_survives_client_detach](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L368)、[test_replay_from_seed_offset_keeps_start_before_end](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L1035)、[test_attach_or_replay_terminal_recovered_from_xrevrange](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_run_supervisor.py#L595)。

**深入追问：** 只统计重连成功率够吗？不够。还应看恢复耗时、重复或缺失事件、状态一致性，以及失败和超时样本，避免只统计能恢复的会话。
