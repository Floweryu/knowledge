# 技术亮点 06：会话级 Agent 评估体系

## 已实现机制

评估脚本按 Session 汇总多个 Trace，构建 Session Bundle，再按指标与 Agent 范围投影证据。确定性指标与语义指标采用不同路径：任务成功依据终态和产物，计数与耗时由代码计算；推理、字段推断、采纳等语义维度使用 LLM Judge。

代码生成固定 Evaluation Units，Judge 返回逐单元判断，程序验证是否遗漏、重复或返回未知单元，再计算指标。超出请求大小限制时，将证据分片扫描再汇总；评分请求共享并发上限，指标失败进行隔离，结果生成总览、明细和失败案例报告。

该脚本评估已有会话，不会重新执行 Campaign Agent。重复评估同一会话能分析 Judge 波动，但不能证明 Agent 多次真实执行的稳定性。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

一次会话里，模型可能说“已完成”，工具却没有返回合法产物；也可能因为等待用户确认而暂停，但业务尚未失败。只看最后一句回答或一次 HTTP 成功状态，无法判断任务质量。

另一个问题是评估器本身：直接让模型给总分，可能漏掉某次用户修改，也可能每次选不同的评分对象。需要把“任务有没有完成”“模型理解是否正确”“评估结果是否覆盖了该评的内容”拆开处理。

### 2. 使用哪些技术，各自负责什么

| 技术或方法 | 角色 | 项目中的职责 |
|---|---|---|
| Langfuse | LLM 应用观测与评估平台 | 承载会话、Trace、Observation、usage 和评分记录 |
| Session Bundle | 项目自定义证据结构 | 汇总多个 Trace，统一清理、排序和组织 |
| 确定性规则 | 可程序化事实判断 | 状态、错误、产物 ID、调用计数和时间计算 |
| LLM-as-a-Judge | 语义评价方法，不是特定框架 | 根据 rubric 判断理解、推断和采纳等质量 |
| Evaluation Units + Pydantic | 固定评分对象与输出结构 | 生成单元、解析结果并校验覆盖 |
| asyncio Semaphore | 本地并发控制 | 限制实际评估请求数量，配合指标失败隔离 |

Langfuse 中，Observation 表示一次具体操作，Trace 组织一次执行的相关操作，Session 可以聚合多轮交互对应的 Trace。这个层次适合追踪跨请求任务，但平台不会仅凭观测数据自动知道什么算“选品成功”。[Langfuse 数据模型](https://langfuse.com/docs/observability/data-model)

### 3. 为什么规则判定与 LLM Judge 必须分工

**规则适合可精确定义的事实。** `_task_verdict` 先找非中断的终态片段，再检查 TaskSnapshot、错误与该 Agent 的产物契约。任务还在等待、快照缺失或未配置产物口径时返回 `not_evaluable`。不能通过模型自述补齐缺失的证据。

**Judge 适合语义问题。** 例如用户要求某个筛选范围，Agent 的解释和最终选择是否遵循该要求，需要结合上下文判断。rubric 指评分规则；它要说明判定对象、成功条件和证据要求。Judge 会有偏差，因此需要人工标注校准，而不是把模型评分视为客观真值。

**固定单元使覆盖可检查。** 项目先生成应该评估的 `unit_id` 清单，让 Judge 逐单元返回结果，再检查重复、遗漏和未知 ID。Pydantic 检查结果结构，覆盖校验检查评分对象集合，程序最后计算分数。这三层检查的职责不同。

### 4. 用一个包含等待和失败的例子说明口径

假设同一会话中有三个逻辑任务，仅作教学示例：

| 任务 | 记录中的证据 | 确定性判断 |
|---|---|---|
| A | `succeeded`、无错误、存在合规产物 ID | pass |
| B | 只有等待确认的 interrupt | not_evaluable |
| C | 已结束，但缺少必需产物 ID | fail |

任务成功率按可评估任务计算：`1 / (1 + 1) = 50%`；同时应展示可评估覆盖率 `2 / 3` 及 B 的排除原因。只报 50% 会隐藏还有一个任务未结束，直接报 1/3 又把等待等同失败。若可评估数为 0，应明确无可计算样本，不能当成 0% 或 100%。

即使 A 判为 pass，也只说明执行证据满足产物契约；如果池内容不符合用户需求，语义评分仍可能不通过。这正是多维评估的必要性。

### 5. 长会话为什么需要证据分片

当前流程先按指标和 Agent 筛选证据，再生成固定单元；超过请求大小限制时，把证据拆成带 ID 的片段，逐片扫描相关事实，再汇总到原单元。它类似“先局部提取、后全局归并”的方法，具体调度和覆盖校验由项目实现，不是 Langfuse 自动完成。

分片优于静默截断之处在于可以保留尾部的修改和最终结果；代价是调用次数增加，跨片关系可能在汇总时丢失。返回了全部 unit_id 也只证明输出覆盖完整，不能证明 Judge 正确理解全部证据。

### 6. 框架能力之外的技术贡献

最值得说明的是**评分口径和证据链的工程化**：整合完整会话、定义逻辑任务与产物、固定单元、验证覆盖、暴露不可评估原因，并保留失败案例。Langfuse 提供记录与实验基础，项目定义业务含义。

这套脚本评估已有会话，不会重跑被测 Agent。对同一历史 Session 重复调用 Judge，只能分析评估器波动。若要证明新版本更好，需要两个业务版本实际执行固定任务集，再统一比较成功率、覆盖率、语义质量、成本和耗时；本次文档扩写没有执行这些实验。

### Judge 的结构化返回怎样被验证

源码节选：[judge_support.py](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_support.py#L475)（第 475–500 行；片段省略外围上下文，不是独立运行脚本）。

```python
def _validate_unit_coverage(
    score_name: str,
    expected_units: list[dict[str, Any]],
    results: list[JudgeUnitResult],
) -> None:
    expected_unit_ids = {str(unit["unit_id"]) for unit in expected_units}
    returned_unit_ids = [result.unit_id for result in results]
    duplicate_unit_ids = sorted(
        {
            unit_id
            for unit_id in returned_unit_ids
            if returned_unit_ids.count(unit_id) > 1
        }
    )
    if duplicate_unit_ids:
        raise ValueError(
            f"{score_name}: duplicate evaluation unit IDs: {duplicate_unit_ids}"
        )
    returned_unit_id_set = set(returned_unit_ids)
    unexpected_unit_ids = sorted(returned_unit_id_set - expected_unit_ids)
    missing_unit_ids = sorted(expected_unit_ids - returned_unit_id_set)
    if unexpected_unit_ids or missing_unit_ids:
        raise ValueError(
            f"{score_name}: evaluation unit coverage mismatch; "
            f"missing={missing_unit_ids}, unexpected={unexpected_unit_ids}"
        )
```

`expected_units` 来自程序生成的 manifest，`results` 来自结构化 Judge 输出。代码先拒绝重复，再比较未知和遗漏集合；类型正确的结果仍可能因覆盖不全被拒绝。[evaluate_batch](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L692) 捕获可拆批的覆盖错误后拆成更小批次，单单元仍失败则抛出；[_make_parallel_judge_evaluator](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge.py#L121) 在指标边界隔离异常，返回空结果并记录错误。因此报告缺少某指标时，不能当成成功或零分。

[_build_evaluation](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L824) 从代码归并的 numerator/denominator 计算 Evaluation：平均类指标走均值，比例类走百分比，并附 manifest hash、覆盖信息和逐单元结果。最终分数不是模型自由生成的总分。

## 技术问题与回答

### Q1：Agent Evals 为什么要同时看执行轨迹与最终结果？只给最终回答打分会漏掉什么？

**回答思路：** 完整任务可能包含澄清、预览、修改和恢复。最终文本可能很好看，却掩盖工具失败或绕过确认；单个中断又可能被误判为失败。项目按 Session 聚合多 Trace，再按指标投影，让结果证据与过程证据能够一起分析。

**代码如何实现：** `build_session_bundle` 对所有 Trace 排序后逐个 `_normalized_trace`，携带 previous_state 和 previous_interrupts，并用 seen_message_ids 去重；`project_session_bundle` 再按指标和 Agent 投影。因此一次确认前与恢复后的记录能被放到同一证据集合，而不是各自独立判断。实现位置：[build_session_bundle](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/bundle.py#L1068)、[project_session_bundle](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/units.py#L1268)。

**深入追问：** 是否应该强制 Agent 走一条固定轨迹？不应把合理的替代路径判错。需要固定业务不变量与最终条件，只有必须遵循的授权和安全步骤才强约束。

### Q2：Agent 说“完成了”或工具返回 HTTP 200，为什么都不能作为任务成功标准？

**回答思路：** 成功口径必须落到任务终态、无执行错误和领域产物条件。项目还对图片目标与 QC 作特殊判断，对等待和证据不足保留不可评估。HTTP 或工具层完成只说明一层调用结束，不代表用户目标已经正确实现。

**代码如何实现：** `_task_verdict` 先找最后一个非 interrupt 片段，取 TaskSnapshot；等待状态和缺失证据返回 not_evaluable。可评估时计算 `status == "succeeded" and no_error and artifact_ok`，artifact_ok 由 Agent 专属产物规则得到，而不是检查模型说了“完成”。实现位置：[_task_verdict](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/task_success.py#L299)、[_task_artifact_evidence](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/task_success.py#L215)。

**深入追问：** 远端产物 ID 存在就一定满足用户需求吗？仍不一定。参数与业务内容是否正确要单独评估，必要时回查外部系统；不能用存在性代替语义质量。

### Q3：LLM-as-a-Judge 怎样与规则评分、人工标注配合？更强的 Judge 就足够了吗？

**回答思路：** 确定性状态、计数和时间用代码计算，语义理解使用带 rubric 的 Judge，人工样本用于校准与解释分歧。项目实现了前两条路径，但没有据此证明与人工高度一致。更强的模型也不能补救含糊标准或缺失证据。

**代码如何实现：** 任务成功路径调用 `_task_verdict`，延迟路径从 timing_samples 创建 Evaluation；语义指标则使用 JudgeAgentRunner，把 SystemMessage/HumanMessage 发给 structured model。前两类不需要 Judge 再判断状态和时间，语义质量也不应由是否存在 ID 代替。实现位置：[_task_verdict](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/task_success.py#L299)、[_make_timing_evaluator](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/timing.py#L95)、[_invoke](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L333)。

**深入追问：** 如何验证 Judge 偏差？固定人工标注集，查看一致率及分歧类型，并检查对表达方式、顺序或长度的敏感性；这些属于建议实验，不是已产出的指标。

### Q4：怎样防止 Agent 评估“分母漂移”或只挑容易的部分打分？结构化评分能解决 Reward Hacking 吗？

**回答思路：** 先由代码确定评分对象，再让 Judge 给逐项结果，最后由程序算分。项目的 Evaluation Units 和 manifest 限制评分范围，却不能自动防止被测 Agent 投机或 Judge 语义误判。应把统计完整性与对抗鲁棒性分开讨论。

**代码如何实现：** `project_session_bundle` 先写 evaluation_units 和 unit_manifest；Judge 返回逐单元结果，`_reduce_unit_results` 按指标归并，`_build_evaluation` 再计算均值或百分比并附覆盖率。固定单元把评分对象与统计口径留在代码里，但单个 verdict 仍可能判断错误。实现位置：[project_session_bundle](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/units.py#L1268)、[_reduce_unit_results](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_support.py#L142)、[_build_evaluation](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L824)。

**深入追问：** 如果 Agent 为了高分伪造成功文本怎么办？使用结构化终态与产物证据降低文本自述影响；更严格的远端回查与对抗任务仍需另行验证。

### Q5：Judge 返回 JSON 合法且每个 unit_id 都齐全，是否就代表评估可信？

**回答思路：** 类型校验与覆盖校验只能检查输出结构及评分对象，没有证明模型正确读取证据。项目拒绝重复、未知和遗漏单元；语义可信度仍需证据追溯、人工抽检和对抗样本。评估输入中的恶意指令也不能因来自历史 Trace 就被当成评估规则。

**代码如何实现：** `_validate_unit_coverage` 比较 expected_unit_ids 与 returned_unit_ids，先检查重复，再检查 unexpected/missing；测试让假模型返回空 results，断言 evaluations=[] 且日志包含 coverage mismatch。返回类型合法不代表覆盖合法，覆盖合法也不代表语义判断正确。实现位置：[_validate_unit_coverage](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_support.py#L475)、[test_judge_evaluator_rejects_incomplete_unit_coverage](../../../../../Workspace/ibu_campaign_copilot/tests/scripts/test_langfuse_session_evaluation.py#L1676)。

**深入追问：** 怎样检验 Judge 没被候选内容诱导？可构造包含伪造评分指令的受控样本，并核对 verdict 与证据。当前覆盖校验不是 Prompt Injection 检测器，不能把两者混为一谈。

### Q6：超长 Agent 轨迹怎么评估？分片 Judge 会不会漏掉跨轮修改和最终结果？

**回答思路：** 先按指标与 Agent 投影，再分片提取相关证据并汇总到固定单元。项目使用请求字节阈值和扫描／归并路径，避免直接静默截断；但跨片关系仍可能在汇总中丢失，需要保留定位和做完整轨迹对照实验。

**代码如何实现：** `evaluate_batch` 用 render_direct_request 得到 size，与 max_input_bytes 比较；超限调用 evaluate_with_evidence_shards 扫描所有分片并归并。如果单个 unit 连扫描请求的基础内容都装不下就抛 ValueError，多个 unit 则先 split_batch。这里按字节限制，不是直接按 Token 数判断。实现位置：[evaluate_batch](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L692)、[evaluate_with_evidence_shards](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L619)。

**深入追问：** 摘要更短是否说明评估成本优化成功？还应检查判定一致性与漏证据率，尤其关注最后修改、取消及失败样本；当前没有这项量化收益结论。

### Q7：成功率很高但大量任务 not_evaluable，能说明 Agent 已经可靠了吗？

**回答思路：** 不能只报可评估子集的分数。项目将等待、缺快照等记录排除出成功率分母，因此必须同时报告样本总量、可评估覆盖率和排除原因。数据采集失败和真正还在等待也应分开解释，避免把难例排除后美化成绩。

**代码如何实现：** `_task_verdict` 对未配置产物契约、纯 interrupt、缺少终态快照及等待状态返回 not_evaluable；`_task_success_metadata` 单独统计 pass/fail/not_evaluable，并以 pass+fail 作为可评估分母。应同时解释排除原因，不能把剩余样本的高分描述成全部任务都成功。实现位置：[_task_verdict](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/task_success.py#L299)、[_task_success_metadata](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/task_success.py#L354)。

**深入追问：** 两个版本可评估覆盖率不同还能直接比较成功率吗？需要先对齐任务与筛选口径，展示覆盖差异，必要时单独分析共同样本和新增失败；不能只取较高百分比。

### Q8：Agent Evals 本身怎样保证可重复和可扩展？限流、失败隔离会如何影响结果？

**回答思路：** 固定输入证据、模型与规则版本，记录调用错误及缺失指标。项目共享 Semaphore 限制实际 Judge 请求，并隔离单个指标异常；这防止局部失败拖垮整批，但返回空结果需要显式观察，不能默认为通过。

**代码如何实现：** `_make_parallel_judge_evaluator` 创建一个共享 Semaphore，逐指标 run_metric 用 try/except 隔离异常，再 gather 结果。实际限流在 JudgeAgentRunner._invoke 的 `async with self.semaphore` 中，因此不只是给外层实验配置并发数字。失败指标返回 [] 并记录错误，必须关注缺失结果。实现位置：[_make_parallel_judge_evaluator](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge.py#L121)、[_invoke](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge_runtime.py#L333)。

**深入追问：** 评估并发越大为什么结果可能更不稳定？服务限流、超时、重试和资源竞争会引入额外失败。比较版本时应保持执行条件一致，并区分基础设施错误与模型质量。

### Q9：pass@k、pass^k 与单次成功率有何区别？反复运行 Judge 能证明 Agent 稳定吗？

**回答思路：** pass@k 关注 k 次实际尝试中至少一次成功，pass^k 关注 k 次都成功；业务执行通常还要考虑重复尝试的成本和副作用。当前 repeat_runs 反复评估历史 Session，不会重新执行 Agent，所以只能研究 Judge 波动，不能据此计算真实多次执行的可靠性。 两种可靠性口径见 [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)（2026-01-09）；本项目尚未据此产出实际 pass@k/pass^k。

**代码如何实现：** `run_experiment` 把 task 设为 `_passthrough_task`，该函数只返回 session_id 与 source=historical_session_bundle。repeat_index/repeat_runs 记录重复评估维度，并不会调用 build_main_agent 重做业务。A/B 的新执行数据需要另外生成，当前脚本负责按相同口径评估。实现位置：[run_experiment](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge.py#L343)、[_passthrough_task](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/judge.py#L300)。

**深入追问：** 要比较两个业务版本应该怎么做？固定任务与起始环境，分别生成多次真实执行的新会话，再按同一口径评估；不要把同一条历史记录评十遍当成 Agent 成功十次。

### Q10：如何同时衡量 Agent 的质量、延迟、成本和人工介入，而不是只追一个成功率？

**回答思路：** 分别记录业务成功、语义质量、可评估覆盖、实际模型费用、执行耗时和用户等待。项目已有原始耗时与 Token 归因入口，但不是所有维度都已形成完整报告。比较时需要同一任务集，失败与超时不能被静默排除。

**代码如何实现：** `_completed_subagent_task_samples` 按 subagent_type/task_call_id 聚合，求各 active segment 的 duration_seconds 之和；`_make_timing_evaluator` 保存原始秒数，`percentile_nearest_rank` 排序后取 ceil(p/100*n) 对应样本。执行片段之和与包含用户等待的墙钟时长不同，总体 P95 也不能由各 Session P95 平均得到。实现位置：[_completed_subagent_task_samples](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/bundle.py#L975)、[_make_timing_evaluator](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/timing.py#L95)、[percentile_nearest_rank](../../../../../Workspace/ibu_campaign_copilot/scripts/langfuse_eval/timing.py#L14)。

**深入追问：** TTFT、工具执行耗时与任务完成 P95 能混用吗？不能。它们衡量不同等待阶段；总体 P95 应由统一口径的原始样本计算，不能平均各 Session 的 P95。
