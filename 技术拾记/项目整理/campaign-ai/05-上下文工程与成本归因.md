# 技术亮点 05：上下文工程与成本归因

## 已实现机制

按 2026-10-26 本地 commit `3fef0b6db` 核对，Main 在活动类型确定后通过 `effective_knowledge` 保存业务流程知识，并由 middleware 注入；补充资料通过 `load_campaign_reference` 读取。领域子 Agent 通过各自的 Skills 和参考读取工具获取规则。Main 当前装配未配置文档旧版所述的 CompositeBackend 与 `/skills/` 路由。

Main 的 middleware 每次调用模型时从当前状态派生上下文，将静态提示、知识快照与动态状态分块。当前时间按 Asia/Shanghai 生成到秒，位于动态块；仅 Anthropic 客户端附加对应的 cache_control 标记。旧文档的“十分钟窗口取整”与该本地基线不符，已更正；这不代表核实了线上部署版本。

运行结束后，系统调度 Langfuse 子 Agent Token 归因，按 observation 树识别领域执行消耗和根 Agent 自身消耗。这个机制提供分析依据，不等于已经取得特定节省比例。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

每次模型调用需要的信息并不相同：业务规则相对稳定，活动 ID、计划和产物会随工具执行变化；领域参考资料只在特定任务中需要。全部塞进 prompt 会增加重复输入，完全依赖聊天历史又可能让模型采用旧状态。

因此要同时回答三个问题：**本轮应提供什么信息、信息什么时候刷新、重复内容怎样减少处理成本**。此外，还需要知道消耗来自 Main 还是某个子 Agent，才能决定先优化哪里。

### 2. 使用哪些技术，各自负责什么

| 技术或方法 | 特点 | 本项目落点 |
|---|---|---|
| LangChain middleware | 在模型调用等生命周期位置插入逻辑 | `wrap_model_call` 注入上下文，`after_agent` 调度统计 |
| 结构化状态投影 | 从 state 派生本轮模型视图 | 活动、计划、已生成页面等动态上下文 |
| 稳定知识快照 | 将选定业务流程保存在会话状态中 | `effective_knowledge` 与 `build_main_knowledge` |
| Skills 与受限参考读取 | 按任务读取领域资料，限制文件访问范围 | 领域 Agent 工厂、`read_reference`、Main 的专用 reference 工具 |
| Anthropic Prompt Caching | 复用满足条件的相同请求前缀 | 对静态块和知识块设置 `cache_control` |
| Langfuse observation 树 | 关联不同调用及 usage | 归集领域子树消耗与 Main 自身消耗 |

middleware 的价值是把上下文组装放在调用边界，避免由模型自行决定是否记起刷新状态；框架提供扩展位置，组装哪些字段由项目实现。[Middleware](https://docs.langchain.com/oss/python/langchain/middleware/overview)

### 3. Prompt Caching 的特点与误区

Prompt Caching 复用的是请求的相同前缀计算，并不是把某次回答原样返回，也不是替应用缓存最新业务数据。缓存断点之前的内容改变，会影响对应前缀复用；将频繁变化内容放在稳定块之后，有助于保留稳定前缀。[Prompt Caching 原理](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

本项目 `_system_message_with_context` 依次放置静态提示、`effective_knowledge`、当前时间和活动状态。前两类块在支持的 Anthropic 客户端上设置 `{"type":"ephemeral","ttl":"5m"}`；动态块不设置该标记。时间每次按秒生成，放在缓存断点之后，并没有做十分钟取整。

设置了标记不代表请求必然命中，也不代表模型更理解业务。命中情况、Token 与费用变化要看真实 usage 和服务计费口径；本次没有运行成本实验。

### 4. 一个多轮任务如何组织上下文

1. 活动类型确定后，`confirm_campaign_type` 解析对应知识并写入 `effective_knowledge`。这是会话状态中的快照，不是每次模型调用都读取外部最新资料。
2. 每次模型调用前，`build_main_context` 根据当前 state 提取活动 ID、计划、页面产物等字段；`build_main_knowledge` 读取已确定类型的知识。
3. middleware 将稳定知识与动态事实分块交给模型，降低模型从旧消息中重建事实的负担。
4. Main 委派领域任务时，包装层缩小消息历史；领域 Agent 根据自己的规则和读取工具补充资料。
5. 根 Agent 运行结束后调度 Token 归因，把领域 observation 子树内的生成调用归到相应 Agent，区分 Main 自身消耗。

例如，活动刚创建成功，本轮模型应看到新的活动 ID；稳定流程知识无需随着这个 ID 一起重新组织。反过来，如果外部人员改了活动，state 也可能过时，涉及真实更新时仍要查询校准。

### 5. 与 RAG、长对话和性能优化的区别

| 做法 | 解决什么 | 本项目应怎样表述 |
|---|---|---|
| 全量追加聊天历史 | 保留对话过程 | 不能保证模型能准确找到当前有效事实 |
| state 投影与知识分块 | 明确本轮事实、减少无关上下文 | 已有具体 middleware 与契约实现 |
| 按文件读取 Skills/reference | 获取范围明确的规则资料 | 不据此宣称具备向量检索和重排 |
| Prompt Caching | 降低部分重复前缀的处理成本 | 有标记与结构支持，收益仍需测量 |
| 按 Agent 归因 | 定位调用消耗来自哪里 | 提供优化依据，不自动完成优化 |

这里的工程价值是**设计信息的生命周期与边界**。知识快照有稳定性，也有更新滞后风险；裁剪子任务消息能减少干扰，也可能遗漏约束；整文件读取可减少碎片调用，却可能增加单次输入量。应将成功率、调用量、延迟和费用一起比较。

## 代码实现拆解

### middleware 怎样改变一次真实模型请求

源码节选：[middleware.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L199)（第 199–218 行；片段省略外围上下文，不是独立运行脚本）。

```python
@wrap_model_call(state_schema=MainAgentState)
async def inject_main_context(request: ModelRequest, handler):
    """Append authoritative state and checkpointed knowledge to every model call."""

    context = build_main_context(request.state)
    knowledge = build_main_knowledge(request.state)
    current_time = datetime.now(ZoneInfo("Asia/Shanghai")).isoformat(
        timespec="seconds"
    )
    cache_control = _MAIN_CACHE_CONTROL if _supports_cache_control(request.model) else None
    updated = request.override(
        system_message=_system_message_with_context(
            request.system_message,
            context,
            knowledge,
            current_time,
            cache_control=cache_control,
        )
    )
    return await handler(updated)
```

`request.state` 是本轮图状态；`build_main_context` 派生业务字段，`build_main_knowledge` 读取已确定类型的知识。`request.override(system_message=...)` 构造本次调用使用的新请求，再交给 handler。这段代码并没有把 system prompt 回写成新的业务 state；它修改的是模型输入视图。

### Token 归因怎样避免把子任务算到 Main

[_sum_descendant_usage](../../../../../Workspace/ibu_campaign_copilot/campaign/observability/langfuse_subagent_stats.py#L206) 先按 parent_observation_id 构建 children 索引，再从领域根 ID 向下遍历，只累计 GENERATION 的 usage；[_sum_root_own_usage](../../../../../Workspace/ibu_campaign_copilot/campaign/observability/langfuse_subagent_stats.py#L234) 对每条生成记录沿祖先链检查，排除位于 matched_ids 子任务下面的记录。`score_subagent_tokens` 挂在 Main 的 after_agent，调度失败只记录告警并返回 None，不向业务 state 写入评分结果。

这套实现解决的是归属和可解释性。缺失父子关系、usage 上报不完整或不同模型计费方式，仍会影响统计解释；没有实际样本时不能给出费用节省比例。

## 技术问题与回答

### Q1：Context Engineering 与 Prompt Engineering 有什么区别？为什么长上下文模型仍会丢约束？

**回答思路：** 长窗口扩大容量，不保证模型稳定识别当前有效规则。上下文工程还要决定哪些历史、状态、工具和资料在本轮出现，以及何时刷新。项目通过动态 state 投影、稳定知识块与子任务消息裁剪组织输入；不能仅靠更长 prompt 替代这些边界。

**代码如何实现：** `inject_main_context` 在每次模型调用前读取 request.state，并通过 request.override 替换 system_message；`create_subagent_skill_deep_agent` 则决定领域目录、skills、工具和 middleware。一个决定本次提供哪些事实，一个决定资料如何取得，所以不是只修改一段静态 prompt。实现位置：[inject_main_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L200)、[create_subagent_skill_deep_agent](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/skill_agent.py#L108)。

**深入追问：** 裁剪后如何防止丢掉用户之前的约束？应为跨轮仍有效的字段建立结构化承载，并用多轮修改任务验证；压缩后的文本更短并不自动代表质量更好。

### Q2：Agent Skills、MCP 和 Tools 各自解决什么？Skills 能替代 MCP 吗？

**回答思路：** Skills 组织任务知识和操作步骤，Tools 是可执行能力，MCP 标准化工具／资源的接入。它们可以组合，不能互相替代授权和业务校验。项目领域工厂加载 Skills 与读取工具，另有 MCP 工具加载器建立连接、获取工具并按配置过滤；不能把 Skill 文档读到就认为业务接口已经调用。

**代码如何实现：** Main 只注入当前已确定活动类型的 effective_knowledge，额外参考使用 load_campaign_reference；领域工厂以 subagent_root 绑定 read_reference。规则不必全塞给所有 Agent，但会引入读取调用与漏读风险。确定性规则仍在 builder 和 upsert 门禁中执行。实现位置：[build_main_knowledge](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L60)、[load_campaign_reference](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/tools/document_reader.py#L69)、[create_subagent_skill_deep_agent](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/skill_agent.py#L108)。 MCP 路径另见 [build_mcp_connections_for_skill](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/mcp_tools.py#L58) 和 [get_mcp_tools_for_skills](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/mcp_tools.py#L114)：从请求上下文绑定身份，构造 streamable_http 连接，调用 MultiServerMCPClient.get_tools()；只有 allowed 非空时才过滤工具。该读取是源码分析，本次未连接这些服务。

**深入追问：** 按 Skill 配置工具是否等于最小权限？还要看空白名单与服务端授权语义。当前 MCP 加载器仅在 allowed 非空时过滤，所以不能笼统宣称默认拒绝全部工具。

### Q3：Agentic RAG、文件式 Skills 与 Memory 怎么选？项目的 read_reference 属于哪一类？

**回答思路：** 先看任务需要查什么。确定路径的规则文件适合按需读取；跨会话事实需要明确持久化与访问策略；规模化检索才需要进一步设计召回、排序和权限过滤。当前核实了精确路径读取与会话知识快照，不据此宣称完整向量 RAG 或跨会话长期记忆。

**代码如何实现：** 本专题可核验的入口是 read_reference(file_path) 和知识快照注入：前者按精确文件路径读取，后者从 state 取得现有文本。它们没有在这些入口中执行 embedding、向量召回或重排。RAG 不要求一定用向量，但不能据此宣称项目已具备一整套未核对的检索评估链路。实现位置：[make_read_reference](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/tools/read_reference.py#L20)、[build_main_knowledge](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L60)。

**深入追问：** RAG 是否必须用向量数据库？不必须，关键词或其他检索方式也可用于检索增强。关键是资料如何被找到、使用和验证，不能用组件名称代替能力证明。

### Q4：Agent Memory 和权威业务 state 如何区分？为什么历史聊天不能作为唯一事实源？

**回答思路：** 记忆可以保留历史经验与偏好，业务 state 应表达当前任务的有效事实；外部系统仍可能在会话之外变化。项目每次从 state 派生模型视图，减少从历史消息重建 ID 的负担。读到旧记忆或旧快照不代表当前还有权限、资源仍存在或内容未变。

**代码如何实现：** `build_main_context` 每次从 MainAgentState 取 main/sub_campaign_id、activity_plan 和 page_files 等信息；`inject_main_context` 每次调用该函数，而不是复用启动时生成的一份 JSON。工具更新 state 后，下一次模型请求即可看到新视图；外部系统独立变化仍需查询校准。实现位置：[build_main_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L74)、[inject_main_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L200)。

**深入追问：** 怎样防止 Memory Poisoning 或旧事实覆盖新事实？需要来源、时间、适用范围与更新策略，并在关键写入前回查。当前不能把知识块的不可信标签等同于完整记忆治理。

### Q5：Prompt Cache 缓存的是答案、知识还是请求前缀？怎样兼顾命中率与业务新鲜度？

**回答思路：** Prompt Cache 复用满足条件的相同请求前缀计算，不把旧回答直接当新回答。项目把静态提示与知识快照放前面，动态 state 和时间放后面，并按客户端能力设置标记。要同时看真实缓存 usage、任务正确性和费用，不能只优化缓存命中率。

**代码如何实现：** `_system_message_with_context` 先复制原 system content blocks，再加知识块，最后加时间和动态 JSON；缓存标记放在静态末块和知识块上。测试直接断言 state_block 不含 cache_control，也不含 effective_knowledge，说明两种内容确实被拆开。实现位置：[_system_message_with_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L143)、[test_main_knowledge_lives_in_its_own_cacheable_block_separate_from_state](../../../../../Workspace/ibu_campaign_copilot/tests/agent/main/test_middleware.py#L273)。

**深入追问：** 把最新活动状态也缓存起来是否更省？前缀组织不能让业务状态停止刷新；缓存有效期也不等于事实有效期，更不能替代实时查询。

### Q6：时间戳、工具列表和动态状态会怎样影响 Prompt Cache？缓存 TTL 等于数据 TTL 吗？

**回答思路：** 缓存依赖请求前缀，频繁变化内容若放在断点前可能破坏复用。项目当前时间按秒生成但置于动态块，静态和知识块在前；它没有十分钟取整。缓存 TTL 描述缓存寿命，知识快照是否过时则由其刷新机制决定。

**代码如何实现：** `inject_main_context` 使用 datetime.now(ZoneInfo("Asia/Shanghai")).isoformat(timespec="seconds")，再把时间传给动态块。该值变化不会改变前面静态块的文本；缓存是否实际命中仍需服务 usage。代码没有十分钟取整，也没有用 prompt 中的时间替代业务执行时校验。实现位置：[inject_main_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L200)、[_system_message_with_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L143)。

**深入追问：** 知识文档更新后，已有会话会立即看到吗？不一定。effective_knowledge 是状态中的快照，不能因缓存过期就推断它会重新读取最新资料。

### Q7：上下文隔离和 handoff 如何权衡？子 Agent 只拿任务摘要会不会丢失用户意图？

**回答思路：** 隔离减少跨领域干扰，但委派必须携带仍然有效的约束、活动上下文和产物引用。项目保留本次任务消息、raw_user_brief 及投影后的共享信息。需要用“中途改需求、取消旧条件、再次委派”的案例验证，而不是只比较消息数量。

**代码如何实现：** `prepare_input` 找最后一条 HumanMessage，把 child_state.messages 改为单条消息列表，再保留 raw_user_brief 并把 user_brief 设为本次委派描述。它缩短的是对话消息通道；其他共享字段先 deepcopy 后再投影，不是把全部共享 state 都清空。实现位置：[prepare_input](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L218)。

**深入追问：** 模型委派摘要遗漏条件时，结构化状态一定能救回来吗？只有该条件已被正确编码且投影保留时才可能；不能把存在 state 等同于意图绝不丢失。

### Q8：长任务的工具结果太大，整文件读取、裁剪和 Compaction 应该怎样取舍？

**回答思路：** 整文件读取减少碎片调用，但可能带来单次输入膨胀；裁剪应保留任务所需证据；Compaction 还要考虑不可逆的信息损失。本项目明确提供整文件读取与大小限制，未在本轮核实完整的压缩策略，因此不宣称已经实现某种长期记忆压缩收益。

**代码如何实现：** `read_reference` 仅接收 file_path，先 resolve 并 is_relative_to 校验目录，再检查存在和文件大小，最后 read_text 读取全部文本。超过 MAX_FILE_SIZE 或路径越界返回 Error 字符串，不会正常读取后再截断。测试分别覆盖没有 offset/limit 参数、越界和超大文件。实现位置：[read_reference](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/tools/read_reference.py#L33)、[test_read_reference_no_offset_limit_params](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_read_reference.py#L57)、[test_read_reference_path_traversal_blocked](../../../../../Workspace/ibu_campaign_copilot/tests/agent/test_read_reference.py#L69)。

**深入追问：** 什么时候该拆文件，什么时候该做检索或摘要？先根据资料主题和读取模式判断，并验证关键约束能否找回；不要仅把大小上限调大，也不要静默截掉末尾规则。

### Q9：Prompt Injection 能靠 system prompt 或“不可信数据”标签解决吗？代码里有哪些真正边界？

**回答思路：** 标签有助于区分数据与指令，但安全还依赖工具权限、文件范围、参数校验、身份和写入门禁。项目有对应的局部机制，不能据此声称通过完整攻击测试。应明确外部文档、工具结果和委派信息各自如何进入模型与执行边界。

**代码如何实现：** system 消息里用 BEGIN/END 标记包裹不可信知识和状态，但执行边界仍在代码：Main 的 _FS_PERMISSIONS 拒绝通用文件读写，领域 read_reference 限制真实解析路径，写接口仍检查活动和预览记录。这些机制分工保护不同边界，文本标记本身不是授权或沙箱。实现位置：[_system_message_with_context](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/middleware.py#L143)、[build_main_agent](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L198)、[read_reference](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/tools/read_reference.py#L33)。

**深入追问：** 恶意资料要求读取凭据或绕过预览时应该怎样验证？用受控对抗样例检查工具是否被调用、参数是否越界及写入是否发生；拒绝文本本身不足以证明没有副作用。

### Q10：Agent Token 和成本怎么归因到 Main、子 Agent 和工具？怎样避免优化后便宜但更不可靠？

**回答思路：** 先按 observation 树统计生成调用，再区分输入、输出、缓存和模型价格；工具等待与额外模型轮次也影响总成本。项目已有领域子树与 Main 自身 Token 归因。优化应在固定任务集上同时比较成功率、费用、耗时和人工介入，不用总 Token 一个数字替代效果。

**代码如何实现：** `_sum_descendant_usage` 从子 Agent 根 observation 向下遍历，仅累计 GENERATION；`_sum_root_own_usage` 排除已匹配子任务祖先下的生成调用。这样能区分某领域反复调用与 Main 本身规划消耗。函数返回的是计数及 input/output/total Token，不直接计算真实账单。实现位置：[_sum_descendant_usage](../../../../../Workspace/ibu_campaign_copilot/campaign/observability/langfuse_subagent_stats.py#L206)、[_sum_root_own_usage](../../../../../Workspace/ibu_campaign_copilot/campaign/observability/langfuse_subagent_stats.py#L234)。

**深入追问：** 如何判断该换模型、压上下文还是减工具轮次？先找消耗与失败集中位置，做单变量对照；当前统计提供定位依据，不直接证明某项优化最有效。
