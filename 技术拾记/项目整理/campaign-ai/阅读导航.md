## 项目定位

面向营销运营的 AI Agent 平台，将自然语言需求转化为活动创建、招商、选品、优惠券、秒杀、图片、页面、报名通知及广告投放等业务操作。核心技术主线是：**语义编排、确定性执行、人工确认、状态恢复和会话评估**。

项目价值应围绕“模型如何可靠地操作真实业务系统”展开。框架名称用于说明实现方式，不能代替技术问题、设计取舍和结果证据。

## 问题与技术对照

| 专题 | 原始问题 | 使用的技术／框架 | 关键特点与项目补充 |
|---|---|---|---|
| 多 Agent 编排 | 跨领域任务会补充和修改，共享状态容易相互影响 | DeepAgents、LangChain、LangGraph、Pydantic | 委派与有状态执行；项目补任务契约、输入投影和回写校验 |
| 可靠工具执行 | 自然语言正确不等于接口报文和业务操作正确 | Tool Calling、Pydantic、builder／guard | 运行时校验；项目补领域映射、预览门禁与逐池结果处理 |
| 人工确认与恢复 | 用户回复跨请求，执行需要保留等待点 | LangGraph interrupt、PostgreSQL Saver、psycopg | 持久化状态与恢复输入；项目处理节点重入和存储连接 |
| 长任务与流式恢复 | HTTP 断线后任务和页面状态都需正确处理 | asyncio、SSE、AG-UI、Redis Streams | 执行、传输和事件记录分工；项目补回放边界与终态处理 |
| 上下文工程 | 稳定知识、动态事实和历史消息具有不同生命周期 | middleware、Skills/reference、Prompt Caching、Langfuse | 按调用组织信息、复用稳定前缀；项目补状态投影和成本归因 |
| 会话级评估 | 模型自述和单次请求不能证明完整任务成功 | Langfuse、确定性规则、LLM Judge、Evaluation Units | 证据聚合与语义判断；项目固定评分单元并检查覆盖 |

DeepAgents、LangChain、LangGraph 是不同抽象层次；SSE、AG-UI 是交互／传输协议；PostgreSQL、Redis 是存储组件；LLM Judge 是评价方法；TaskSnapshot、RunSupervisor、Evaluation Units 是项目概念。介绍技术方案时应说明每个组件承担的职责。

## 当前实现需要明确的事实

- Main DeepAgent 是当前根图，子 Agent 由 `SUBAGENT_SPECS` 统一注册，当前共有 8 类业务子 Agent。
- 当前 Main 装配同步 `CompiledSubAgent`；不能据此宣称业务 Agent 全并行执行。
- 选品查询工具覆盖 7 条产品线；查询工具覆盖、语义报文契约覆盖、真实端到端验收是不同口径。
- Main 使用活动类型确定后的 `effective_knowledge` 快照，middleware 将其与动态状态分开注入；Main 补充资料通过专用 reference 工具读取，领域子 Agent 使用自己的 Skills／参考资料。
- Main 对静态提示和知识块设置条件式缓存标记，动态状态每次重建；时间文本按秒生成并置于动态块。旧文档的 Main `/skills/` 路由和十分钟取整描述已按本地代码更正。
- PostgreSQL checkpoint 负责图状态恢复；启用 Redis RunBus 时，Redis Streams 支持运行中事件回放。
- 断线后继续运行依赖原进程中的任务仍存活，不等于进程故障后自动接管。
- 选品写入有预览门禁和会话内重复创建防护；不等于强授权令牌、跨会话幂等或外部系统 Exactly-once。
- 评估有基于产物证据的任务成功判定，以及 LLM Judge；没有证据时应保留不可评估状态。
