# 技术亮点 02：语义契约与可靠工具执行

## 已实现机制

选品 Agent 将自然语言理解、实体解析、语义定义、报文构造、预览和写入分开。查询工具接入 HOTEL、FLIGHT、TNT、PKG_TOUR、CRUISE_SHIP、CAR_RENTAL、TRAIN 七条产品线；具体创建能力还要核对 `SPEC_BY_PRODUCT_LINE`、builder 和 E2E，不以工具数量代替验收。

模型提交业务语义，Pydantic 契约和 builder 决定字段、层级和具体报文。原始 upsert 工具从模型工具集合中过滤，写入收敛到 `upsert_selection_pools`。工具校验预览记录和活动上下文，执行层汇总逐池结果。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

用户说“新建一个符合这些条件的酒店选品池”，实际接口却需要产品线、数据源、指标 key、操作符、实体 ID 和嵌套字段。模型可能理解了需求，却写错字段层级；也可能生成完全合法的 JSON，却用了另一个产品线的枚举。

更新场景更危险：用户只要求修改一个 tab 的规则，远端接口却按整个 tab 列表替换。遗漏旧 tab 可能产生删除效果。问题因此包含三层：**自然语言转业务意图、业务意图转合法报文、合法报文是否允许在当前状态执行**。

### 2. 使用哪些技术，各自负责什么

| 技术或方法 | 解决的问题 | 对应实现 |
|---|---|---|
| LLM Tool Calling | 选择工具并提供候选参数 | 领域 Agent 的工具集合 |
| Pydantic v2 | 运行时结构校验与字段归一化 | `BasePoolSpec`、各产品线 Spec、validators |
| 确定性 builder 与 guard | 把业务语义映射为报文，验证领域限制 | `pool/builder.py`、`pool/guards.py` |
| LangChain ToolMessage | 将可修正错误反馈到 Agent 循环 | 工具的成功／错误消息 |
| LangGraph Command | 提交工具执行产生的状态更新 | 草稿、预览记录与执行结果更新 |
| 统一写入入口 | 检查执行前置条件、处理逐池结果 | `upsert_selection_pools` |

builder、guard 和写入门禁是项目代码，不是引入 Pydantic 后自动获得的能力。

### 3. Pydantic 的特点与使用边界

**类型声明与运行时校验结合。** Python 类型标注本身不会在每次传参时阻止非法值；Pydantic 的模型校验会实际解析输入并检查约束，也支持序列化和生成 JSON Schema。它默认可能进行类型转换，并不等于所有字段都启用了 strict mode。[模型机制](https://docs.pydantic.dev/latest/concepts/models/)

**字段级和模型级规则分工。** `field_validator` 适合归一化单个字段，例如项目将部分数组字段的 `null` 转为 `[]`；`model_validator` 适合跨字段约束，例如 `mode=update` 必须存在 `schema_id`。不同产品线通过各自模型表达差异。[校验器机制](https://docs.pydantic.dev/latest/concepts/validators/)

注意两处实现细节：一是并非所有 Spec 都设置 `extra="forbid"`，不能宣称全部未知字段都会拒绝；二是选品草稿工具接收的输入包含裸 `list[dict]`，不能因为内部用了 Pydantic，就推断每个嵌套规则已经作为完整 JSON Schema 暴露给模型。代码注释明确说明部分字段说明来自工具 docstring 与 Skill。

### 4. 一条需求经过哪些边界

以“新建酒店池，按城市和星级筛选”为教学示例，不使用虚构的真实 ID：

1. **语义层**：模型识别产品线和筛选意图；存在歧义时澄清。
2. **实体层**：查询工具解析城市等真实业务实体，不让模型凭记忆编造 ID。
3. **契约层**：输入进入对应产品线 Spec，检查结构、枚举和 create/update 条件。
4. **构造层**：builder 根据指标定义、数据源和产品线构造报文，guard 检查适用性；模型无需自行拼装所有底层字段。
5. **交互层**：预览展示用户条件、系统约束、推导和默认值，并等待回复。
6. **写入层**：统一工具检查预览记录与活动上下文；对会话内已经成功的新建池跳过，对其他池执行并汇总结果。

如果第 3 或第 4 步发现可修复错误，错误通过 ToolMessage 回到模型。这个循环的意义是让模型修正输入，而不是让模型拥有跳过校验的权限。

### 5. 为什么不只依赖 prompt 或 JSON Schema

| 约束方式 | 能约束什么 | 仍然缺少什么 |
|---|---|---|
| prompt 要求“先预览” | 给模型行为指导 | 无法阻止偶发的直接写入调用 |
| JSON Schema／类型校验 | 字段形状、部分取值约束 | 无法证明 ID 属于用户、数据源支持该指标 |
| builder + 业务 guard | 确定性报文映射与领域规则 | 无法单独证明用户确认了本次完整内容 |
| 写入门禁 + 会话产物检查 | 执行前置事实与部分重复创建防护 | 不构成跨会话幂等或分布式事务 |

技术贡献在于把这些约束放到合适的位置。模型承担语义不确定性，代码承担明确规则。代价是每条产品线的契约和映射都要维护；接口升级时需要同步验证。预览凭证按池名记录、远端成功而本地未记录等边界仍然存在。

## 代码实现拆解

### 从语义参数到报文的真实调用链

模型调用 `draft_selection_pools(pools=...)`，传入的是 `list[dict]`。框架注入 `InjectedState` 和 `InjectedToolCallId`，不需要模型生成运行状态与工具调用 ID。草稿工具逐项调用 `_to_draft`，实际分层顺序如下。

源码节选：[draft.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/draft.py#L283)（第 283–324 行；片段省略外围上下文，不是独立运行脚本）。

```python
def _to_draft(
    raw: dict[str, Any], index: int, state: dict[str, Any]
) -> tuple[PoolDraftItem, BasePoolSpec | None]:
    """整条链路都在 try 内：任何失败都必须转成 in-band 的错误文本。

    两段 try 的兜底面不同：契约校验只抛 ``ValidationError``（模型写错字段）；构造与
    护栏会读磁盘上的注册表 Markdown（``IndicatorRegistryError``）并调 SOA 侧配置，
    所以留一个更宽的兜底。二者都不允许把异常抛回 agent loop——模型只会看到
    "Error invoking tool"，拿不到可操作的原因。
    """
    label = _label(raw, index)
    spec_class, line_errors = _line_errors(raw)
    errors = [*_contract_errors(raw, spec_class), *line_errors]
    if errors:
        return _failed(label, errors), None

    try:
        spec = _spec_of(raw, spec_class)
    except ValidationError as exc:
        logger.error("[selection] pool definition invalid for {}: {}", label, exc)
        return _failed(label, [f"pool definition invalid: {exc}", *_nested_extra_key_errors(exc, spec_class)]), None

    try:
        payload, static_config, build_errors = build_request(spec, _build_context(spec, state))
        guard_errors = validate_data_source(spec.product_line, static_config) if not build_errors else []
    except Exception as exc:  # noqa: BLE001 - 工具层兜底，错误必须 in-band 回灌模型
        logger.error("[selection] draft guard failed for {}: {}", spec.name, exc)
        return _failed(spec.name, [f"draft validation failed: {exc}"]), None

    if build_errors or guard_errors:
        return _failed(spec.name, [*build_errors, *guard_errors]), None

    return (
        PoolDraftItem(
            status=_STATUS_DRAFTED,
            pool_name=spec.name,
            payload=payload,
            static_config=static_config,
            schema_id=spec.schema_id,
        ),
        spec,
    )
```

`_spec_of` 调用对应产品线模型的 `model_validate`；`build_request` 根据 `spec.product_line` 分派构造器；`validate_data_source` 再检查数据源枚举及招商前置条件。失败被包装为 failed 草稿，通过 `_summary` 放进 ToolMessage；一次工具返回可以同时包含成功和失败池，不能只看 ToolMessage 的 status 判断每个池都合法。

@model_validator(mode="after")
def _update_requires_schema_id(self) -> BasePoolSpec:

### 写入入口读取 state，而不是再次让模型拼 payload

源码节选：[upsert.py](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L129)（第 129–180 行；片段省略外围上下文，不是独立运行脚本）。

```python
@tool
async def upsert_selection_pools(
    tool_call_id: Annotated[str, InjectedToolCallId],
    state: Annotated[dict, InjectedState],
) -> Command:
    """Create or update the selection pools on the campaign platform.

    Only call this after preview_selection_pools has shown these exact pools
    to the user and the user confirmed them. Per-pool results come back —
    read them and decide whether to retry or explain the failure.

    Returns:
        Per-pool outcome. Failures carry their upstream error text.
    """
    pools, drafts = _restore(state)

    if not pools:
        return _reply(_NO_POOLS, tool_call_id, error=True)

    pending, skipped = _partition_by_created(pools, drafts, state)
    if not pending:
        return _reply(
            f"These pools were already created in this session: {skipped}. " "Nothing was written again.",
            tool_call_id,
        )

    missing = _unpreviewed(pools, state)
    if missing:
        return _reply(
            f"These pools have not been previewed to the user yet: {missing}. "
            "Call preview_selection_pools first.",
            tool_call_id,
            error=True,
        )

    if _campaign_context_missing(state):
        return _reply(_CTX_MISSING, tool_call_id, error=True)

    try:
        output = create_selection_pools(drafts=drafts, pools=pending, state=state)
    except Exception as exc:  # noqa: BLE001 - 工具层兜底，错误必须 in-band 回灌模型
        logger.error("[selection] upsert failed: {}", exc)
        return _reply(f"upsert failed: {exc}", tool_call_id, error=True)

    return _reply(
        output.model_dump_json(),
        tool_call_id,
        **{
            SELECTION_OUTPUT_FIELD: output,
            UPSERT_AUDIT_FIELD: _audit(state, pools),
        },
    )
```

函数开头先 `_restore` 草稿和池输入，再用 `_partition_by_created` 划分 pending/skipped。实际写入调用 `create_selection_pools(drafts=drafts, pools=pending, state=state)`；[_upsert_one](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/upsertor.py#L195) 补权限头、活动 ID 等上下文，调用 SOA 并从返回中提取 schema ID。结果进入 `selection_output`，最终由 [finalize_selection_node](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L294) 转成任务快照并合并 `artifacts.selection_pools`，供后续重复创建检查使用。

这条链路不是“LLM 一次生成接口 JSON 并调用”：参数由模型提出，报文由代码构造，中间产物存入 state，预览通过 interrupt 等回复，写入工具从已保存草稿读取。当前预览记录按池名保存，未绑定完整报文摘要。去重也要求成功记录已经进入 artifacts：upsert 工具本身只更新 selection_output 和审计字段，artifacts 在 finalize 阶段合并。因此不能仅凭一次工具返回成功，就保证同一内层 Agent 循环立即重试时也能被这层 artifacts 检查拦住；这是按读写顺序推导出的限制，未通过运行故障场景验证。

## 当前 Agent 开发议题与提问方式

本篇关注 Structured Output 之外的业务正确性、工具发现与工具数量膨胀、权限、HITL 内容绑定、幂等和错误恢复。官方工具工程资料讨论了按需发现与程序化工具调用，MCP 规范定义工具的输入结构与调用形式；它们不替应用完成业务校验。选题参考：[Introducing advanced tool use](https://www.anthropic.com/research/advanced-tool-use)（2025-11-24）、[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)（规范版本 2025-11-25）。

本项目证据是语义 Spec、builder、guard 与统一写入边界。动态 Tool Search、Programmatic Tool Calling 和跨系统 Exactly-once 未在本轮核实为已实现能力。

## 技术问题与回答

### Q1：Function Calling 和 Structured Output 已经能生成 JSON，为什么还需要语义契约与 builder？

**回答思路：** 结构合法与业务正确是不同问题。工具调用可以提供候选参数，JSON Schema 可以约束形状，builder 则把业务语义转换成产品线报文，guard 处理跨字段与数据源规则。本项目保留模型对需求的理解，把确定字段映射交给可测试代码。

**代码如何实现：** `draft_selection_pools` 明确拒绝模型直接提交 payload/static_config；`_to_draft` 依次做语义校验、构造和 guard。`build_request` 只是按产品线分派，真正酒店报文在 `builders/tabbed.py` 中构造。模型只填规则意图，operatorKey 由注册表查出。实现位置：[_to_draft](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/draft.py#L283)、[build_request](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/builder.py#L38)、[_build_rules](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/builders/tabbed.py#L152)。

**深入追问：** 如果模型一次生成的 JSON 全部通过类型校验，还会错在哪里？可能选错实体、使用不适用指标、丢失旧 tab 或绑定错活动；这些不能由 JSON 合法性保证。

### Q2：Agent 幻觉怎样在工具边界拦截？Pydantic 校验通过为什么仍可能写错业务？

**回答思路：** 把风险拆成语法、结构、领域规则、真实实体和授权五层。Pydantic 主要处理结构及已编码规则，builder/guard 校验领域限制，真实查询和写接口承担外部事实与权限边界。项目不能只凭“参数是整数”就认为 ID 正确。

**代码如何实现：** `BasePoolSpec._update_requires_schema_id` 能拒绝缺少更新 ID，但不知道某个指标适用于哪个数据源。`_build_rules` 查询指标对应的操作符，查不到就返回错误；`validate_data_source` 额外拒绝非法数据源以及没有 sourcing_rule_ids 的招商数据源。实现位置：[_update_requires_schema_id](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/spec.py#L96)、[_build_rules](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/builders/tabbed.py#L152)、[validate_data_source](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/guards.py#L103)。

**深入追问：** 要证明幻觉风险下降，应测什么？使用不存在实体、错产品线枚举、缺少前置条件和歧义需求等固定输入，比较拒绝率、误拒率及最终结果，不能只统计报错数量下降。

### Q3：MCP 的工具 Schema 能统一所有业务吗？为什么还要按产品线定义契约？

**回答思路：** MCP 提供工具暴露和调用协议，不替业务定义所有语义。产品线的字段族、枚举和更新规则不同，仍需明确契约与转换逻辑。当前选品使用产品线 Spec 和 builder 分派；不能因为接入协议标准化，就把互不适用字段合成一个巨大的可选参数模型。

**代码如何实现：** `BasePoolSpec` 定义 name/product_line/mode/schema_id；HotelPoolSpec、TrainPoolSpec 等声明各自产线字段，builder 用映射表选择实现。还要区分 Pydantic 的 extra 策略与草稿层 `_contract_errors`：后者按契约字段检查原始入参，不能只看基类是否配置 extra=forbid。实现位置：[BasePoolSpec](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/spec.py#L77)、[_contract_errors](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/draft.py#L64)、[build_request](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/builder.py#L38)。

**深入追问：** 是不是每个产品线都应复制一套实现？应共享真实一致的身份、create/update 语义和可复用转换；只有结构或规则确实不同的部分才分开，避免同义规则漂移。

### Q4：Agent 只靠 prompt 写“先确认再执行”够吗？如何实现最小工具权限？

**回答思路：** 先缩小模型可调用工具集合，再在唯一写入边界检查必要条件。当前过滤原始 upsert 工具、保留统一写入口，并检查预览记录和活动上下文。工具可见性限制与真实服务端授权是两层能力，都不能仅由模型承诺。

**代码如何实现：** `_strip_upsert_tools` 从产线工具集移除原始写工具；统一 upsert 读取 state 的 `selection_previewed_keys`，`_unpreviewed` 发现遗漏就返回 error ToolMessage。测试在没有凭证时 mock create_selection_pools，并断言 `create.assert_not_called()`。实现位置：[_strip_upsert_tools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/agent.py#L67)、[_unpreviewed](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L62)、[test_upsert_rejected_without_preview_credential](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_upsert_tool.py#L86)。

**深入追问：** MCP 工具声明 readOnlyHint 就能当权限控制吗？声明只描述预期行为，不能代替服务端认证、授权及副作用约束；该项目也不能凭工具名称判断安全。

### Q5：Human-in-the-loop 怎样防止“用户确认的是旧草稿，Agent 写入的是新内容”？

**回答思路：** 确认应绑定被审阅内容，而非只记录“发生过一次确认”。当前项目按池名记录预览经历，没有绑定完整 payload 摘要，因此需要主动说明边界。草稿版本、摘要、操作者与有效期绑定可以作为增强设计，但本次没有实现。

**代码如何实现：** 预览恢复后把池名合并到 `selection_previewed_keys`；写入时 `_unpreviewed` 比较的仍是 `_pool_key(pool.name)`。草稿工具会按同一 key 覆盖 `selection_drafts`，这两个入口没有用 payload hash 比较前后内容，所以代码只能证明池名经过预览流程。实现位置：[preview_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/preview.py#L139)、[_unpreviewed](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L62)、[draft_selection_pools](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/draft.py#L365)。

**深入追问：** 确认后哪些变化必须重新确认？任何影响业务含义或副作用范围的字段变化都应考虑失效策略；仅靠池名不变无法证明用户确认仍适用。

### Q6：工具错误要抛异常，还是返回给模型自我修正？如何防止无限修复循环？

**回答思路：** 可操作的输入错误应返回具体字段、原因和合法范围，让模型修正；中断应作为控制流传播，执行结果未知不应伪装成参数问题。项目已有 in-band ToolMessage 与异常边界，但“错误可见”不等于有完整重试预算和停止策略。

**代码如何实现：** `_to_draft` 捕获 ValidationError 和构造/guard 异常，生成包含原因的 failed 草稿；统一 upsert 的 `_reply` 则构建 ToolMessage，并通过 `Command(update={"messages": [...]})` 回到图状态。模型可以据此修参数；未知错误仍不应被当成可无条件重试。实现位置：[_to_draft](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/draft.py#L283)、[_reply](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L108)。 公共边界还有 [ToolErrorGuardMiddleware](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/tool_error_guard.py#L22)，将 ValueError、RuntimeError、OSError 转成 error ToolMessage；它不是统一的重试预算控制器。

**深入追问：** 为什么不能捕获所有异常后让模型继续？这可能吞掉程序缺陷或恢复中断，也可能导致重复外部写入；应按错误类型定义可修复与必须停止的边界。

### Q7：工具超时或部分成功后，怎样实现 Agent 重试幂等？Exactly-once 能直接承诺吗？

**回答思路：** 先确认哪些资源已成功，再区分 create 与 update，并处理远端成功、本地未记录的未知窗口。当前去重读取 artifacts 中成功池名，仅覆盖已记录的新建结果；同一内层循环尚未 finalize 的结果不能据此保证去重，更不能承诺跨会话 Exactly-once。

**代码如何实现：** `_created_keys` 只收集 artifacts 中 status 为真且带 schema_id 的池名；`_partition_by_created` 还检查草稿 payload 没有 schemaId，才跳过已成功的新建池。带 schemaId 的 update 仍执行。测试分别断言 create 不调用、update 仍调用一次。实现位置：[_partition_by_created](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L83)、[test_already_created_pool_is_not_written_twice](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_upsert_tool.py#L201)、[test_update_pool_is_still_written_even_if_artifact_exists](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_upsert_tool.py#L220)。

**深入追问：** 若接口不支持幂等键怎么办？可讨论业务唯一键、查询回查、执行记录与人工处置；要明确这些是增强方案，不是本项目已有的统一保障。

### Q8：Agent 修改已有资源时，为什么“只提交用户要求改的字段”反而可能删数据？

**回答思路：** 必须理解远端 API 的 PATCH 与全量替换语义。选品 tab 列表使用全量结构，旧 ID 和不变项缺失可能改变资源含义。Agent 应先读完整旧资源、应用局部意图、预览整体变化，再写入；工具描述和类型校验都应帮助模型识别更新语义。

**代码如何实现：** `TabSpec` 的字段说明明确记录 tab 列表的全量替换语义；`_build_tabs` 遍历 spec.tabs，把旧 tab_id 写进报文。builder 不会自动去远端补回模型漏掉的 tab，因此“查完整旧配置、保留旧 ID、再修改”仍是调用方必须遵循的流程。实现位置：[TabSpec](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/spec.py#L47)、[_build_tabs](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/pool/builders/tabbed.py#L184)。

**深入追问：** 并发有人修改旧资源怎么办？仅查询后再写仍有过期窗口；版本号、条件写或冲突提示是可讨论方案，本次没有证明外部系统已提供这些能力。

### Q9：工具数量膨胀时，Tool Search、批处理、串行调用分别解决什么？

**回答思路：** Tool Search 影响工具发现和输入规模，批处理减少调用往返，串行控制共享状态与副作用顺序。项目当前有工具集合过滤、去重与默认串行配置，不能将其称为已经接入动态 Tool Search 或 Programmatic Tool Calling。先定位瓶颈，再决定优化哪一层。

**代码如何实现：** 当前实际声明中，`selection_query_result` 已使用 `merge_query_result`，`task_status` 使用 `merge_task_status`；草稿、预览和输出等字段仍没有相同合并机制。文件头的旧描述不能覆盖字段声明。即使补上 reducer，两个 upsert 同时调用 `_created_keys` 读到旧产物，仍可能重复远端写入。实现位置：[SelectionAgentState](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/agent_state.py#L99)、[_created_keys](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L67)、[_partition_by_created](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/tools/upsert.py#L83)。 工具发现方面，[_query_tools_for_all_lines](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/agent.py#L72)按工具名合并去重静态产线工具；MCP 通用加载器 [get_mcp_tools_for_skills](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/mcp_tools.py#L114)使用 client.get_tools() 后按配置过滤。这些代码不等于接入按需 Tool Search。

**深入追问：** 工具越少越好吗？过度裁剪会让任务无法完成；应比较工具选择正确率、调用轮数、任务覆盖和费用，并验证必要工具仍可发现。

### Q10：怎样为可执行 Agent 做工具层评测，避免一次 E2E 成功就宣布可靠？

**回答思路：** 将契约、报文转换、门禁、重复执行、部分失败和真实业务 E2E 分层验证。项目已有确定性测试作为入口，应再用固定任务集评估多次实际执行。mock 单测证明本地分支，真实集成验证环境与协议，二者不能互相替代。

**代码如何实现：** 现有 builder 测试检查规则映射、未知指标和数据源不适用时的错误；upsert 测试检查无预览不调用 SOA、已创建跳过而 update 仍写。它们分别验证报文转换和执行边界；集成 E2E 才验证真实模型与远端接口，本次没有执行任何业务测试。实现位置：[test_rules_become_indicator_rule_list](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_poolspec_builder.py#L135)、[test_indicator_unavailable_on_that_data_source_is_rejected](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_poolspec_builder.py#L159)、[test_upsert_rejected_without_preview_credential](../../../../../Workspace/ibu_campaign_copilot/tests/deepagent/selection/test_upsert_tool.py#L86)。

**深入追问：** 如果模型更新导致工具参数分布变化，哪些测试最先发现？固定无效输入与边界样例可检测结构退化，真实 Agent 任务集能检测工具选择与澄清变化；两类都要保留。

## 可展开的案例
