# 技术亮点 01：多 Agent 编排与状态契约

## 已实现机制

Main 使用 `create_deep_agent` 构建，是公共链路的根图。`SUBAGENT_SPECS` 注册招商、选品、优惠券、秒杀、图片、页面、报名通知、广告投放 8 类子 Agent，通过同步 `CompiledSubAgent` 暴露给 Main。

模型维护 `ActivityPlan` 并决定任务委派。计划更新通过类型化操作实现，包含节点、页面、模块和状态更新；相关操作按批次校验，失败时不提交半份计划。计划顶层节点和相对顺序存在明确约束，因此这里是受业务约束的动态编排。

子 Agent 包装层执行输入投影和结果校验：消息只保留本次任务消息，业务状态通过契约传递；结果必须提供一致的 `TaskSnapshot` 与 `task_status`，不能改动其他任务的状态或未授权产物字段。该机制是应用层状态边界，不是进程安全沙箱。

## 问题、技术选型与框架原理

### 1. 要解决什么问题

以“搭建一场营销活动”为例，执行过程可能涉及活动建壳、招商、选品、图片和页面。用户却可能只想修改选品条件，或者在页面阶段返回调整活动信息。困难有两类：**下一步做什么需要理解语义，执行后的状态能否接收则需要确定性判断**。

如果全放进一个 Agent，各领域的工具说明、历史消息和中间草稿会相互干扰；如果写成不可变的顺序工作流，又难以表达补充、跳步和修改。这是拆分 Main 与领域子 Agent 的设计动因分析，并非已经测量出的性能收益。

### 2. 使用哪些技术，各自负责什么

| 技术或组件 | 所处层次 | 在本项目中的职责 |
|---|---|---|
| DeepAgents | Agent 能力封装 | `create_deep_agent` 构建 Main，`task()` 委派注册的领域 Agent |
| LangChain | 模型、消息、工具和 middleware 抽象 | 统一模型调用与工具反馈，提供 `Runnable` 等组合接口 |
| LangGraph | 有状态执行运行时 | 执行编译图，处理状态更新、嵌套调用、中断和 checkpoint |
| Pydantic | 数据契约校验 | 校验任务快照、计划与产物结构 |
| 项目注册表与包装层 | 业务规则 | 定义领域边界、允许回写字段和失败结果 |

这些不是四套并排运行的编排系统：DeepAgents 基于 LangChain 的 Agent 构件，并使用 LangGraph 运行时。其预置能力包括任务规划、子 Agent 委派和上下文管理；是否启用、如何限制仍由应用装配决定。[框架层次与能力](https://docs.langchain.com/oss/python/deepagents/overview)

### 3. 框架特点为什么适合这个问题

**DeepAgents 提供委派入口，领域流程仍可自定义。** `CompiledSubAgent` 可以包装已经构建好的 runnable／图，不要求每个领域都采用相同的一段 prompt。项目由 `_build_subagents` 将领域图包装后注册，Main 通过统一入口调用。这里的“同步子 Agent”表示父任务等待领域结果，不等于 Python 只能用同步函数，也不表示执行运行在独立进程。[CompiledSubAgent](https://docs.langchain.com/oss/python/deepagents/subagents)

**LangGraph 将执行状态显式化。** 消息、任务状态、活动信息和产物不必全藏在自然语言历史中。状态通道和合并规则提供承载机制；哪些字段能改、多个结果如何判定冲突，仍然是应用要定义的语义。添加 reducer 只能指定某类数据如何合并，不能自动解决两个外部写操作的竞争。

**结构化契约让结果可检查。** 项目不仅让子 Agent 返回“已完成”，还检查 `structured_response` 与 `task_status` 是否一致、任务名称是否匹配，以及产物变化是否属于授权字段。这些规则来自 `state_driven_subagent.py`，不能归功于框架默认行为。

### 4. 用一个具体执行过程串起来

1. Main 根据用户目标和 `ActivityPlan` 决定委派选品任务。
2. `prepare_input` 复制输入状态，将对话消息缩到本次任务消息，并应用领域输入投影。
3. 领域图查询数据、生成草稿、等待确认并执行写入。
4. 若返回中断，包装层只向上传递必要消息和中断信息；若正常结束，则校验 `TaskSnapshot` 和可回写产物。
5. Main 收到合规结果后继续组织业务步骤；计划更新和外部资源是否真实存在仍是不同判断。

例如，选品 Agent 返回成功，却同时改了页面产物：即使输出 JSON 类型合法，包装层也会检查出未授权产物字段。框架负责运行子任务，项目规则负责拒绝这个结果。

### 5. 选型取舍与技术贡献

| 方案 | 更合适的条件 | 相对于本项目方案的取舍 |
|---|---|---|
| 单 Agent + 全部工具 | 领域少、工具少、上下文较短 | 装配简单，但所有领域细节进入同一决策上下文 |
| 固定工作流 | 步骤稳定、分支明确、强调可预测性 | 容易验收；灵活修改需求需要显式建模分支 |
| Main + 领域子 Agent | 各领域有独立规则与交互闭环 | 边界清晰，但增加委派、状态契约和调试成本 |

这里最有价值的工程工作是**定义和执行跨 Agent 契约**。采用框架能复用运行机制，但业务结果一致性、输入裁剪与副作用顺序仍需自己处理；是否拆分带来质量提升，必须通过固定任务集验证。

            get_destination_resource_package,
            load_campaign_reference,
            upload_markdown_to_nos,
            unpack_archive_tool,
            read_attachment,
            resolve_campaign_themes,
            get_campaign_theme_options,

            get_sourcing_rules,
            query_flight_sourcing_goods,
            get_coupons,
            get_flash_sales,
            search_adspaces_tool,
            get_adspace_tool,
        ],
        permissions=_FS_PERMISSIONS,

### 状态怎样变成可验证的结果

源码节选：[task_snapshot.py](../../../../../Workspace/ibu_campaign_copilot/campaign/schemas/state/contracts/task_snapshot.py#L43)（第 43–51 行；片段省略外围上下文，不是独立运行脚本）。

```python
@model_validator(mode="after")
def validate_status(self) -> Self:
    if self.status is TaskStatus.FAILED and self.error is None:
        raise ValueError("failed snapshot requires error")
    if self.status is not TaskStatus.FAILED and self.error is not None:
        raise ValueError("only failed snapshot may contain error")
    if self.status in _WAITING_STATUSES and not self.blocking_reason:
        raise ValueError("waiting snapshot requires blocking_reason")
    return self
```

这是 Pydantic 的模型级校验：失败没有 error、非失败却带 error、等待没有 blocking_reason，都会被拒绝。`merge_task_status` 再按任务名覆盖最新结果，并校验字典 key 与 `snapshot.task` 一致。它是一张最新状态表，不是事件历史表。

ActivityPlan 走另一条更新路径：模型调用 [update_activity_plan](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/tools/update_activity_plan.py#L23) → [apply_activity_plan_operations](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/activity_plan_ops.py#L416) 在深拷贝上执行整批操作 → 全部成功后返回 `_tool_update(activity_plan=merged_plan)`。异常分支只返回错误消息，不提交半份计划。[test_failed_batch_does_not_mutate_current_plan](../../../../../Workspace/ibu_campaign_copilot/tests/agent/main/test_activity_plan_ops.py#L343) 先执行有效状态修改，再执行删除不存在模块，并断言原计划与修改前完全相同；这是原子性的测试源码证据，本次未运行。

本篇将题目对齐 Harness Engineering、单 Agent 与多 Agent 取舍、规划与执行边界以及跨系统协作。2026 年的 Harness 工程文章讨论了任务分解、产物交接和评价机制，A2A 官方文档明确了 Agent 互操作与 MCP 工具接入的分工。选题参考：[Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps)（2026-03-24）、[A2A 与 MCP 的职责比较](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)（查阅于 2026-10-26）。

## 技术问题与回答

### Q1：更强的单模型已经能调工具，为什么还要多 Agent？怎样证明拆分值得？

**回答思路：** 先用单 Agent + Tools 作为对照，再分析领域工具、上下文和状态边界。这个项目拆分的主要动机是把选品、页面等业务闭环分开，不是宣称 Agent 数量越多效果越好。应在相同模型、任务集与预算下比较成功率、Token、延迟和跨领域错误，才有证据说明委派成本值得。

**代码如何实现：** 项目把八个业务规格集中在 `SUBAGENT_SPECS`；`_build_subagents` 为每个规格创建带名称、描述和 runnable 的 `CompiledSubAgent`。选品自己的图仍能维护草稿和确认闭环，Main 只通过统一委派入口使用它。另有名为 `general-purpose` 的拒绝哨兵，不能把它误计为第九个业务 Agent。实现位置：[_build_subagents](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L59)、[compile_subagent_graphs](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagent_registry.py#L105)。

**深入追问：** 如果业务只有两三个只读工具，还要拆八个 Agent 吗？未必。若单 Agent 已达标，应减少不必要委派；本项目八类能力是实现事实，不是最佳数量的实验结论。

### Q2：ReAct、Plan-and-Execute 与固定 Workflow 怎么选？这个项目到底把决策交给谁？

**回答思路：** 可以从“谁决定下一步”解释：Main 由模型在工具循环中选择下一步，ActivityPlan 表达业务计划，确定性代码限制非法状态和写入。它有计划、有动作和工具反馈，但不能仅凭这些就认定实现了某篇论文的完整 ReAct 或 Plan-and-Execute 算法；选品子图仍有固定 selection/finalize 边界。

**代码如何实现：** Main 的工具列表包含 `update_activity_plan`，并把 `subagents=_build_subagents(graphs)` 交给 `create_deep_agent`，没有在这里为每项业务手写路由边。领域内部可以有固定图：选品实际注册 `START → selection → finalize → END`，不存在函数头旧说明中的独立 execute 节点。实现位置：[build_main_agent](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L198)、[build_subagent_selection](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L333)。

**深入追问：** 哪些步骤不该交给模型自由决定？结构校验、授权、产物归属和外部写入前置条件应由代码执行。用户是否改变业务目标则需要语义理解，两者可以共存。

### Q3：Agent Harness 与模型能力有什么区别？换一个更强模型能替代编排层吗？

**回答思路：** Harness 指模型周围的工具执行、上下文、状态、恢复和结果处理机制。本项目的注册表、包装层、TaskSnapshot 与计划工具属于这层工程。更强模型可能改善委派选择，却不会自动补齐业务字段校验和异常恢复；升级模型仍要验证工具行为与契约兼容。

**代码如何实现：** `SELECTION_SPEC` 把选品 builder、`project_selection_input` 和允许回写的 `selection_pools` 产物绑定在一起。Main 持有 `update_activity_plan`；选品的 `finalize_selection_node` 产出 TaskSnapshot 和 artifacts，不直接改 ActivityPlan。实现位置：[project_selection_input](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L357)、[finalize_selection_node](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L294)、[update_activity_plan](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/tools/update_activity_plan.py#L23)。

**深入追问：** 怎样判断问题出在模型还是 Harness？沿调用记录区分错误委派、错误参数、合法输入被错误拒绝和执行结果丢失，再用固定案例重放边界或生成新会话比较；本次未完成归因实验。

### Q4：子 Agent 的上下文隔离，是否就等于安全沙箱？如何防止跨 Agent 状态污染？

**回答思路：** 上下文隔离减少不相关历史进入子任务；状态回写限制控制子任务能改变哪些业务字段；安全沙箱限制进程、网络和文件访问。这是三类不同边界。项目可证明消息裁剪和结果字段校验，不能把 deepcopy 或子图封装称为进程级安全隔离。

**代码如何实现：** `prepare_input` 先 deepcopy，再把 `messages` 缩到本次 HumanMessage，并执行领域投影；`_finish_result` 仅选择声明的结果字段，比较原始与返回的 Artifacts，发现 `unauthorized` 就抛错。注意它复制了共享 state，不能宣称输入字段已经完全最小化。实现位置：[prepare_input](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L218)、[_finish_result](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L129)。

**深入追问：** 如果子 Agent 已在远端创建了错误资源，事后拒绝回写能撤销吗？不能。结果合并校验只控制本地状态，外部副作用必须在执行前校验，并考虑幂等或补偿。

### Q5：多 Agent 协作应该传自然语言摘要，还是结构化状态与产物引用？

**回答思路：** 自然语言适合解释，结构化状态适合执行判断。项目通过 TaskSnapshot 表达状态、阻塞原因、错误和产物引用，Main 再据此继续处理；同时保留摘要供人和模型理解。契约能阻止形状矛盾，不能证明所有自然语言内容或产物本身都正确。

**代码如何实现：** `validate_status` 把失败与 error、等待与 blocking_reason 绑定；`_validate_result` 还要求 `structured_response` 与 `task_status[task]` 相等。`merge_task_status` 使用 `merged[key] = value` 覆盖旧快照，所以不能把它当完整审计日志。实现位置：[validate_status](../../../../../Workspace/ibu_campaign_copilot/campaign/schemas/state/contracts/task_snapshot.py#L44)、[_validate_result](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L84)、[merge_task_status](../../../../../Workspace/ibu_campaign_copilot/campaign/schemas/state/contracts/task_snapshot.py#L54)。

**深入追问：** “结构化输出成功”是否等于“业务完成”？不等于。还要验证任务标识、状态一致性和对应产物；下游也不能把别的任务产物拿来当成功依据。

### Q6：Agent 自动规划怎样避免“计划显示完成，业务其实没完成”？

**回答思路：** 计划是决策与进度视图，执行结果是另一个证据源。当前 Main 显式更新 ActivityPlan，领域任务返回 TaskSnapshot 和产物，两者不会天然保持一致。回答时应指出现有类型校验能保证什么，并把产物对账、计划一致性评估作为进一步验证方向。

**代码如何实现：** `update_activity_plan` 只从 `state["activity_plan"]` 计算新计划；子 Agent 包装层返回的是 `structured_response` 和本任务 `task_status`。这两个通道没有在上述函数中自动互相派生。即使计划被设为 completed，也不能替代领域输出的产物证据。实现位置：[update_activity_plan](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/tools/update_activity_plan.py#L23)、[_finish_result](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/state_driven_subagent.py#L129)。

**深入追问：** 能不能直接用 TaskSnapshot 自动推动所有计划节点？任务与页面、模块、语言维度可能并非一一对应，需先定义映射和完成条件；当前代码没有通用自动对账机制。

### Q7：长任务不断 Replanning，如何避免一次错误修改破坏整个计划？

**回答思路：** 将计划修改表达为有限的类型化操作，对副本执行整批变更，全部成功才发布新计划。项目还明确省略、清空、替换的差异。这能约束一次本地计划变换，不能保证模型重新规划的业务选择正确，也不形成跨外部系统事务。

**代码如何实现：** `apply_activity_plan_operations` 先 deepcopy 当前计划，逐条 `_apply_operation`，最后重新规范化与检查结构，再返回结果。若第二条失败，调用方拿不到 merged_plan，原对象也未修改。测试专门构造“先改状态，再删除不存在模块”的失败批次。实现位置：[apply_activity_plan_operations](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/activity_plan_ops.py#L416)、[test_failed_batch_does_not_mutate_current_plan](../../../../../Workspace/ibu_campaign_copilot/tests/agent/main/test_activity_plan_ops.py#L343)。

**深入追问：** 为什么不让模型每轮重写整个计划？全量重写更容易误删未完成约束；但增量操作也会受上下文遗漏影响，需要测试父子结构和保留字段。

### Q8：多 Agent 并行为什么可能更慢甚至出错？应该优先并行哪些操作？

**回答思路：** 总耗时受关键依赖链、模型调用、工具等待和结果合并影响，不能按 Agent 数量推导加速比。共享状态读改写和有副作用操作并行会产生冲突。本项目限制模型并行工具调用；可优先评估互不依赖的只读查询，写入和确认需先补足并发安全。

**代码如何实现：** `_disable_parallel_tool_calls` 仅对 ChatAnthropic 修改请求，把 `tool_choice.disable_parallel_tool_use` 设为 true；选品默认模型另传 `serial_tool_use=True`。这两处是模型调用配置，不是数据库锁，也不证明所有外部写接口都实现了互斥。实现位置：[_disable_parallel_tool_calls](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L180)、[build_selection_deep_agent](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/agent.py#L200)。

**深入追问：** 加 reducer 后是否就能开启并行写入？reducer 只能规定状态合并；并行工具仍可能同时看到旧产物并重复远端创建，需要独立的互斥或幂等设计。

### Q9：所谓 Self-healing Agent 应该自动重试到什么程度？如何避免错误恢复扩大副作用？

**回答思路：** 先区分可修正输入错误、执行失败、结果未知和正常中断。当前包装层将普通异常转为可重试快照，但不自动证明重试安全。合理的恢复还需要预算、同类错误计数和结果回查；这些应作为扩展设计，不能因为返回 retryable=True 就称为完整自愈。

**代码如何实现：** `_build_subagents` 同时包装 invoke 和 ainvoke：遇到 `GraphBubbleUp` 原样抛出，普通 Exception 转为 `_task_failure_result`。后者生成 FAILED 快照及 retryable 错误，供下一轮处理。它记录失败，不会自动执行重试或确认远端是否已经写成功。实现位置：[_build_subagents](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L59)、[_task_failure_result](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L153)。

**深入追问：** 什么时候应转人工？超过预算、同因错误反复出现、权限不足或远端结果未知且无法安全回查时应停止自动推进；本项目未证明所有路径已有统一策略。

### Q10：MCP、A2A 与进程内子 Agent 有什么区别？新增领域是否一定需要 A2A？

**回答思路：** MCP 面向工具与资源接入，A2A 面向独立 Agent 之间的互操作；当前 CompiledSubAgent 是应用内委派。新增领域可以沿现有规格和 runnable 接入，并不自动需要网络协议。只有跨服务或跨团队协作确有需求时，再评估发现、认证、任务状态和通信协议。 [A2A 与 MCP 的职责比较](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)（查阅于 2026-10-26）对这两个协议层次作了区分。

**代码如何实现：** 照选品实现可以看到完整接入点：领域 build 函数返回编译图，`SELECTION_SPEC` 声明 task、graph_id、snapshot_model、投影和回写集合，注册表编译它，Main 包装 runnable。新增领域必须明确同样的边界，不能只在 prompt 里加一个名称。实现位置：[build_subagent_selection](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagents/selection/graph.py#L333)、[compile_subagent_graphs](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/subagent_registry.py#L105)、[_build_subagents](../../../../../Workspace/ibu_campaign_copilot/campaign/agent/main/agent.py#L59)。 这里执行的是本地 runnable.invoke/ainvoke，并没有在这条委派链中使用 A2A 的能力发现和远程任务协议。

**深入追问：** 如何证明项目已经支持 A2A？需要真实协议端点、能力发现和任务交互证据；本次核对到的是本地注册与调用，不能把 task() 换个说法就称为 A2A。
