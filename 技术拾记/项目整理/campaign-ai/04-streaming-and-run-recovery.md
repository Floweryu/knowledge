# 技术亮点 04：长任务与流式恢复

## 已实现机制

启用 Redis RunBus 时，`start_run` 启动进程内独立任务执行图，HTTP 流从本地队列读取事件。客户端断开时解除队列连接，后台任务继续运行；重连根据 Redis 中的运行信息选择实时回放或历史记录回放。

Redis 保存事件流、快照、运行元信息及控制消息；PostgreSQL checkpoint 保存图执行状态，二者职责不同。高频增量帧使用批量写入，结构性事件触发及时刷新。运行中快照采用明确的回放游标策略，避免丢失成对事件的开始帧。

## 简历表述

> 将 Agent 执行生命周期与 SSE 连接解耦，基于 Redis Streams 实现运行中事件回放和断线重连，处理成对事件边界、增量批量写入、停止控制与终态恢复。

## 技术问题与回答

### Q1：SSE 不是已经支持流式了吗，为什么还要 supervisor？

**回答思路：** 流式传输解决逐步展示，独立执行任务解决连接断开后业务是否继续运行。如果图执行直接依附 HTTP generator，客户端取消可能终止整条执行。supervisor 将图放到独立 asyncio Task，HTTP 只消费输出。

**深入追问：** 这是不是独立任务服务？不是，执行仍在原进程中。HTTP 生命周期隔离和进程故障隔离是不同层次。

### Q2：为什么既有本地队列，又有 Redis Streams？

**回答思路：** 本地队列服务当前连接的事件消费；Redis 让后续请求可以读取运行信息与历史事件，也使重连不必命中原进程。两者分别满足当前传输与跨请求恢复需求。

**深入追问：** 所有帧都先持久化再给客户端吗？不能这样概括。高频 delta 会缓存在批量器里，`push` 返回时未必已经写入 Redis；结构帧则走及时刷新。需要以代码为准，不能只照搬“Redis-first”的注释。

### Q3：checkpoint 和事件回放为什么不能合并成一套？

**回答思路：** checkpoint 记录图的状态与恢复点，事件流记录前端需要的文本、工具调用和执行状态。图已经持久化不代表前端收到完整文本；前端看到了“执行中”也不代表图状态可恢复。两类数据服务不同消费者。

**深入追问：** 是否有跨存储事务？当前没有据此证明 PostgreSQL、Redis、会话记录和外部业务写入在一个事务内，因此恢复逻辑需要处理不同步窗口。

### Q4：重连为什么不能简单从最后一条收到的消息后继续？

**回答思路：** AG-UI 事件包含交错的 start/content/end。游标若落在工具 start 之后、end 之前，而恢复快照没有完整表达该未结束工具，前端可能只收到孤立的 end。项目运行期快照不推进本轮回放游标，通过本轮事件回放保持结构边界。

**深入追问：** 代价是什么？回放数据量增加，且依赖事件仍在保留范围内。增量合并可降低数据量，但不能保证任意长会话、无限时间离线都完整恢复。

### Q5：为什么只合并部分 delta 帧？

**回答思路：** 同一消息或工具调用的相邻文本增量可以拼接；start/end、终态、快照等事件承担协议边界，必须保序且及时处理。批量器对文本、推理文本和工具参数增量进行处理，按事件关联 ID 区分。

**深入追问：** 能跨多个消息 ID 合并吗？不能。相同类型但不同 messageId/toolCallId 的事件属于不同对象，合并会破坏关联。相同 ID 下不同事件类型也不能任意混合。

### Q6：前端消费太慢会拖住 Agent 吗？

**回答思路：** 本地队列有容量限制，投递使用非阻塞方式，满时记录告警，而不是无限等待客户端。这保护执行任务，但慢客户端可能缺少实时帧，需要恢复策略补足。

**深入追问：** Redis 故障时内存是否无限增长？批量器也有容量上限，达到上限会丢弃旧的可批量增量。这是可用性与完整性的取舍，不应宣传成无损传输。

### Q7：用户点击停止，能立即停止所有接口调用吗？

**回答思路：** 当前通过控制流通知 worker，设置 stop_event，并在消费事件边界检查，关闭底层 generator、发送停止终态。它是协作式停止，响应速度依赖当前任务何时返回控制权。

**深入追问：** 已发出的 SOA 请求会回滚吗？不会因为本地停止自动回滚。已经发生的业务副作用需要另行查询或补偿；长时间阻塞的调用也可能延迟停止生效。

### Q8：原 Pod 崩溃后，新 Pod 能继续这个任务吗？

**回答思路：** 不能据当前架构承诺自动接管。Redis 可以支持读取已持久化事件，checkpoint 可以提供恢复依据，但进程内 asyncio Task 已经消失。自动接管还需要任务领取、租约、重试调度和副作用幂等。

**深入追问：** 你会怎样扩展？可讨论持久任务队列、worker 租约与 fencing token、结果未知回查及执行幂等；这些是建议方案，不能写进当前项目已实现清单。

### Q9：重连时缺终态事件怎么处理？

**回答思路：** 项目重新读取最新运行状态，尝试取 Stream 最后一帧；必要时再读取 checkpoint 中的 pending interrupt 信息重建终态表达。这样可以处理终态写入与 tail 退出之间的时间窗口。

**深入追问：** 是否能直接把结束状态改成成功？不能。finished、error、stopped、等待确认是不同语义。恢复需要保留原始结果，不能因前端没收到错误就展示成功。

### Q10：怎么验证断线恢复，而不是只测试正常流？

**回答思路：** 测试执行中主动 detach、后台是否继续、重连快照和事件顺序、交错工具事件、停止信号、缺失快照与终态兜底。再通过集成测试覆盖代理超时、真实 Redis 延迟、慢客户端和进程退出。

**深入追问：** 应看哪些指标？建议关注重连成功率、恢复耗时、队列满次数、增量丢弃数、事件回放长度和停止生效延迟。这是建议采集口径，本文没有给出已上线的完整指标集或数值。

## 可展开的案例
